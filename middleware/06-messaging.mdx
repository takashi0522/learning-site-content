## なぜ非同期にするのか

同期呼び出しでは、**呼び出し先の障害と遅延が、そのまま呼び出し元に伝播します**。

```text
同期:  Web ──► 決済 ──► メール送信
                          ↑ ここが 10 秒かかると、Web の応答も 10 秒かかる
                          ↑ ここが落ちると、注文自体が失敗する

非同期: Web ──► 決済 ──► [キュー] ──► メール送信ワーカー
                              ↑ メール送信が落ちても注文は成立する
                              ↑ 復旧後に溜まった分を処理できる
```

得られるものは 3 つです。

- **疎結合** … 送信側は受信側の状態を知らなくてよい
- **バースト吸収** … 瞬間的な負荷をキューが受け止める
- **リトライ** … 失敗しても再処理できる

代わりに、**「いつ処理されるか分からない」「重複するかもしれない」**という性質を受け入れる必要があります。

## Kafka の構造

Kafka は「キュー」というより**追記型のログ**です。この違いが挙動のすべてを説明します。

```text
Topic: orders
├── Partition 0  [ 0 ][ 1 ][ 2 ][ 3 ][ 4 ]...    ← オフセットが振られた追記ログ
├── Partition 1  [ 0 ][ 1 ][ 2 ]...
└── Partition 2  [ 0 ][ 1 ][ 2 ][ 3 ]...
                              ↑
                 コンシューマは「自分がどこまで読んだか」を
                 オフセットとして記録する
```

**読んでもメッセージは消えません。** 保持期間（`retention.ms`）が過ぎるまで残り、別のコンシューマが最初から読み直すこともできます。

<Callout type="note" title="Kafka と RabbitMQ の違い">

| | **Kafka** | **RabbitMQ** |
| --- | --- | --- |
| 実体 | **追記ログ**（消えない） | **キュー**（消費したら消える） |
| 再読 | **可能**（オフセットを戻す） | 不可 |
| 順序保証 | パーティション内 | キュー内 |
| ルーティング | 単純（トピック） | **柔軟**（Exchange / ルーティングキー） |
| スループット | **非常に高い** | 中程度 |
| 向く用途 | ログ収集、イベント基盤、ストリーム処理 | **タスクキュー**、複雑なルーティング |

「あとから作ったサービスが、過去のイベントを最初から読み直す」という使い方ができるかどうかが、設計上の大きな分かれ目です。**イベント駆動の基盤なら Kafka、ジョブの分配なら RabbitMQ** という選び分けが素直です。

</Callout>

## パーティションが並列度を決める

**ここが Kafka で最も重要な設計判断です。**

<Figure name="kafka-partitions" caption="パーティション数が、そのグループで出せる並列度の上限になる" />

**1 つのパーティションは、同じコンシューマグループ内の 1 コンシューマだけが読みます。**

```text
コンシューマの並列度の上限 = パーティション数
```

---

<h2 className="slide-cont">パーティションが並列度を決める（続き）</h2>

<Callout type="pitfall" title="パーティション数は後から減らせない">

「処理が追いつかないからコンシューマを増やそう」としても、**パーティション数を超えて増やしても無意味**です。

さらに厄介なことに、**パーティション数は増やせても減らせません**。

```bash
# 増やすのは可能
kafka-topics.sh --alter --topic orders --partitions 12 --bootstrap-server localhost:9092
```

そして**増やすと順序が壊れます**。キーによるパーティション割り当ては `hash(key) % パーティション数` で決まるため、パーティション数が変わると同じキーが別のパーティションへ行くようになります。

```text
変更前: hash("user-42") % 3 = 0  → Partition 0
変更後: hash("user-42") % 12 = 6 → Partition 6
        → Partition 0 に残っている過去のメッセージとの順序関係が失われる
```

**将来の並列度を見込んで、最初から多めに作る**のが定石です（ただし多すぎるとブローカーのファイル数とリバランス時間が増えます）。

</Callout>

### 順序保証の範囲

**順序が保証されるのはパーティション内だけです。** トピック全体の順序は保証されません。

```text
「同じユーザーの操作は順番に処理したい」
  → ユーザー ID をキーにする
  → 同じキーは必ず同じパーティションへ行く
  → そのユーザーに関しては順序が保たれる
```

キーを指定しなければラウンドロビンで分散され、順序は保証されません。**何を単位に順序を守りたいかを決めて、それをキーにする**のが設計の要点です。

## 配信保証と acks

書き込みの耐久性は、**プロデューサの `acks` とトピックの `min.insync.replicas` の組み合わせ**で決まります。

```text
Partition 0
├── Leader    (broker 1)
├── Follower  (broker 2)   ┐ ISR (In-Sync Replicas)
└── Follower  (broker 3)   ┘
```

| `acks` | 応答を返すタイミング | 失われる条件 |
| --- | --- | --- |
| `0` | 送信した時点 | **ネットワークで消えても気づかない** |
| `1` | **リーダーが書いた時点** | リーダーが複製前に落ちると失われる |
| **`all`** | **ISR 全体が書いた時点** | ISR 全滅時のみ |

---

<h2 className="slide-cont">配信保証と acks（続き）</h2>

<Callout type="warning" title="acks=all だけでは足りない">

`acks=all` は「**ISR に入っているレプリカ全部**が書いた」ことを意味します。問題は、**ISR が 1 つに縮退していても条件を満たしてしまう**ことです。

```text
replication.factor = 3
ISR が遅延で 1 つ（リーダーのみ）に縮退
  → acks=all でもリーダー 1 台の書き込みで成功が返る
  → そのリーダーが落ちればデータは失われる
```

これを防ぐのが `min.insync.replicas` です。

```bash
# トピック側で最低限必要な ISR 数を指定する
kafka-configs.sh --alter --entity-type topics --entity-name orders \
  --add-config min.insync.replicas=2 --bootstrap-server localhost:9092
```

```text
耐久性の定番構成:
  replication.factor  = 3
  min.insync.replicas = 2
  acks                = all

  → 2 台に書けなければ書き込みを失敗させる（1 台の障害には耐える）
```

**この 3 つはセットで考えてください。** `acks=all` だけ設定して安心している構成は少なくありません。

</Callout>

## 重複は前提にする

Kafka の既定は **at-least-once**（最低 1 回）です。つまり**重複しうる**ということです。

```text
コンシューマが処理を完了
      ↓
オフセットをコミットする前にクラッシュ
      ↓
再起動後、同じメッセージをもう一度読む  ← 重複処理
```

オフセットのコミットを処理の前にすれば重複は防げますが、今度は**処理前にクラッシュするとメッセージを失います**（at-most-once）。

<Callout type="field">

**実務では「重複してもよいように作る」のが現実的な解です。**

- 処理に**冪等性**を持たせる（同じメッセージを 2 回処理しても結果が変わらない）
- メッセージに一意な ID を持たせ、**処理済み ID を記録**して 2 回目をスキップする
- DB 側で一意制約を張り、重複挿入を弾く

Kafka にはトランザクションによる exactly-once の仕組みもありますが、**Kafka 内で完結する処理（Kafka → Kafka）**に限られます。外部の DB や API を呼ぶ処理では、結局アプリ側で冪等性を担保する必要があります。

ネットワークコース レッスン 6 やミドルウェアコース レッスン 2 で触れた「非冪等なリクエストを再送しない」という話と、同じ構造の問題です。

</Callout>

## コンシューマ遅延が最重要の指標

Kafka 運用で最初に監視すべきは **consumer lag**（未処理のメッセージ数）です。

```bash
kafka-consumer-groups.sh --describe --group order-processor \
  --bootstrap-server localhost:9092
```

```text
TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG      CONSUMER-ID
orders  0          1048221         1048225         4        consumer-1
orders  1          982114          1204887         222773   consumer-2   ← 遅れている
orders  2          1051002         1051010         8        consumer-3
```

| 状態 | 意味 |
| --- | --- |
| LAG が小さく安定 | 正常 |
| **LAG が増加し続ける** | **処理能力不足**。コンシューマかパーティションを増やす |
| **特定パーティションだけ大きい** | **キーの偏り**、またはそのコンシューマの不調 |
| LAG が急減 | リバランスやオフセットのリセットが起きた可能性 |

---

<h2 className="slide-cont">コンシューマ遅延が最重要の指標（続き）</h2>

<Callout type="pitfall" title="リバランスによる停止">

コンシューマが増減すると、パーティションの割り当てを決め直す**リバランス**が起きます。その間、**そのグループの処理は完全に停止します**。

問題は、**処理が遅いコンシューマが「死んだ」と誤判定されてリバランスを誘発する**ことです。

```text
max.poll.interval.ms （既定 5分）を超えて poll() が呼ばれない
  → ブローカーが「このコンシューマは死んだ」と判断
  → リバランス発生 → 全体が停止
  → 処理はさらに遅れる
  → また超過 → リバランス …（悪循環）
```

対策です。

```properties
# 1回の poll で取るメッセージ数を減らす（処理時間を短くする）
max.poll.records=100

# 処理に時間がかかるなら間隔を伸ばす
max.poll.interval.ms=600000
```

**「LAG が増えているのでコンシューマを増やしたら、かえって遅くなった」**という場合、リバランスの多発を疑ってください。コンシューマグループのリバランス回数をメトリクスとして取っておくと判断できます。

</Callout>

## 保持期間とディスク

```bash
# トピックの保持設定
kafka-configs.sh --describe --entity-type topics --entity-name orders \
  --bootstrap-server localhost:9092
```

```text
retention.ms=604800000        # 7日
retention.bytes=-1            # サイズ上限なし
segment.bytes=1073741824      # 1GB ごとにセグメント分割
```

<Callout type="warning">

**Kafka は読まれたかどうかに関係なく、保持期間まで保持します。** コンシューマが止まっていても、逆に全員が読み終わっていても、ディスクは保持設定どおりに消費されます。

```text
1日 500GB 流入 × 保持 7日 × レプリケーション 3 = 10.5TB
```

保持期間を延ばす判断は、**そのままディスク容量の判断**です。運用コース レッスン 4 の容量逼迫が、ここでは設定ミス 1 つで発生します。

逆に、**保持期間より長く止まっていたコンシューマは、読めなかったメッセージを永久に失います**。長期停止からの復旧では、LAG だけでなく「消えた分があるか」も確認してください。

</Callout>

## まとめ

- 非同期化で得るのは**疎結合・バースト吸収・リトライ**。代償は遅延と重複
- Kafka は**キューではなく追記ログ**。読んでも消えず、読み直せる
- **コンシューマの並列度の上限 = パーティション数**
- パーティションは**減らせない。増やすと順序が壊れる**。最初から多めに設計する
- 順序保証は**パーティション内のみ**。守りたい単位をキーにする
- 耐久性は **`replication.factor=3` + `min.insync.replicas=2` + `acks=all`** をセットで
- 既定は **at-least-once**。**重複を前提に冪等な処理を書く**
- **consumer lag が最重要指標**。増加は処理能力不足、偏りはキーの偏り
- 処理が遅いとリバランスが多発し、さらに遅くなる悪循環に陥る
- 保持期間の設定は、そのままディスク容量の設計
