## ラックに載る台数を決めるのは電力

「42U のラックだから 1U サーバーが 42 台」とはなりません。**実際の制約は電力です。**

```text
ラックの給電容量が 6kW の場合

  1U サーバー (400W)  →  6,000 ÷ 400 = 15 台   （42U あっても 15 台）
  GPU ノード (10kW)   →  1 台も載らない
```

サーバーの見積もりでは、**U 数より先に消費電力を確認する**のが正しい順序です。

### 19 インチラックの基本

| 項目 | 値 |
| --- | --- |
| 幅 | 19 インチ（マウント穴の間隔。外寸は 600mm が多い） |
| 1U | **44.45mm**（1.75 インチ） |
| 高さ | 42U が標準。47U、48U もある |
| 奥行 | 1000mm / 1200mm。**GPU ノードは深い**ので要確認 |
| 耐荷重 | 500〜1500kg。GPU ノードは 1 台 100kg 超もある |

<Callout type="pitfall">

**奥行きと耐荷重は見落とされやすい項目です。**

高密度な GPU ノードや大容量ストレージは、一般的なサーバーより深く、重くなります。既設のラックに入らない、あるいはラック全体の耐荷重を超える、という事態が実際に起きます。

発注前に、**筐体の外寸（奥行き）と重量をデータシートで確認し、ラックの仕様と突き合わせてください。**

</Callout>

## ブレーカー容量と、実際に使える電力

ここが最も間違えやすい計算です。**ブレーカーの定格をそのまま使ってはいけません。**

### 連続負荷は定格の 80% まで

サーバーのように常時電流が流れる「連続負荷」では、**ブレーカー定格の 80% までに抑える**のが設計上の原則です（多くの電気規格で定められています）。残り 20% は安全余裕で、これを超えるとブレーカーが落ちるリスクが高まります。

```text
単相 200V 30A のブレーカー

  定格      : 200V × 30A = 6,000 VA = 6.0 kVA
  使用可能  : 6.0 kVA × 0.8 = 4.8 kW    ← これが実質の上限
```

### 三相の場合

```text
三相 200V 30A

  定格      : 200V × 30A × √3 = 10,392 VA ≒ 10.4 kVA
  使用可能  : 10.4 × 0.8 ≒ 8.3 kW
```

<h2 className="slide-cont">ブレーカー容量と、実際に使える電力（続き）</h2>

<Callout type="field">

**「30A の回線だから 6kW 使える」と考えると、現地で確実にブレーカーが落ちます。**

さらに、起動時には定常時を超える電流（突入電流）が流れます。**ラック内の全サーバーを同時に電源投入すると、定常負荷が収まっていてもブレーカーが落ちる**ことがあります。

停電復旧後の一斉起動は、この典型です。BIOS の電源復帰設定（`Power On` / `Last State` / `Stay Off`）を確認し、必要なら起動を分散させてください。

```bash
# BMC 経由で電源復帰ポリシーを確認する
ipmitool chassis policy list
ipmitool chassis status | grep -i "Power Restore"
```

</Callout>

## PDU と A/B 給電

**PDU**（Power Distribution Unit）はラック内に電源を配る機器です。種類で運用のしやすさが変わります。

| 種類 | できること |
| --- | --- |
| **Basic** | 電源を配るだけ |
| **Metered** | PDU 全体の電流・電力を計測できる |
| **Metered by outlet** | **コンセント単位で計測できる**。容量管理に有効 |
| **Switched** | コンセント単位で遠隔 ON/OFF できる。**現地に行かず電源断できる** |

<Callout type="tip">

**Switched PDU は、遠隔運用において BMC に次ぐ保険です。**

BMC が応答しなくなった、OS もハングしている、という状態でも、PDU からコンセント単位で電源を落とせば強制的にリセットできます。無人拠点や遠隔地のサーバーでは、導入する価値が明確にあります。

Metered by outlet があれば、「どのサーバーが何 W 使っているか」を機器を触らずに把握でき、容量計画の精度が上がります。

</Callout>

### A/B 系統に分ける

ハードウェアコース レッスン 6 で触れたとおり、**PSU を 2 台積んでも、給電元が同じなら冗長になりません**。

<Figure name="ab-power-feed" caption="A/B 2 系統給電。冗長かどうかは、上流がどこまで分かれているかで決まる" />

この構成では、A 系統がまるごと落ちても B 系統で動き続けます。

---

<h2 className="slide-cont">PDU と A/B 給電（続き）</h2>

<Callout type="warning" title="A/B 構成では各系統を 50% 以下に抑える">

**冗長構成では、片系統が落ちたときに残りの系統が全負荷を引き受けます。**

```text
A 系統: 4.0 kW、B 系統: 4.0 kW で運用（各系統の上限 4.8 kW）
   ↓
A 系統が停止
   ↓
B 系統に 8.0 kW がかかる  →  上限 4.8 kW を超えてブレーカーが落ちる
   ↓
ラック全体が停止           ← 冗長にしたはずが全損
```

**冗長を成立させるには、各系統の負荷を上限の 50%（= 定格の 40%）以下に抑える必要があります。**

つまり 30A 回線 2 本の A/B 構成で、実際に使えるのは 4.8kW であって 9.6kW ではありません。この誤解は、**冗長化したつもりが片系障害で全停止する**という最悪の結果につながります。

```bash
# 実際の消費電力を継続的に記録し、余裕を確認する
ipmitool sensor get 'Pwr Consumption'
ipmitool dcmi power reading
```

</Callout>

## UPS と発電機

```text
商用電源 ──┬─► UPS ──► IT 機器      通常時
           │
           └─► 停電
                  ↓
           UPS のバッテリで数分〜数十分つなぐ
                  ↓
           発電機が起動して引き継ぐ（数十秒〜数分）
```

UPS の役割は「長時間動かすこと」ではなく、**発電機が立ち上がるまでの数十秒をつなぐこと**、および**瞬断・電圧変動から機器を守ること**です。

| 方式 | 特徴 |
| --- | --- |
| **常時インバータ（オンライン）** | 常に変換を通す。瞬断ゼロ、波形も安定。**データセンター標準** |
| ラインインタラクティブ | 通常は商用をそのまま通し、異常時に切り替え。安価だが切替時間がある |

<Callout type="field">

**UPS のバッテリは消耗品です。** 数年で容量が落ち、いざというときに想定時間を持ちません。

- バッテリの交換時期を管理台帳に載せる
- 定期的にバッテリテストを実施する（UPS 側の機能）
- **テスト自体がリスクを伴う**ため、実施計画は慎重に立てる

「UPS があるから停電は大丈夫」と思っていたら、バッテリが劣化していて数秒しか持たなかった、というのは実際にある話です。

</Callout>

## 電力を実測する

設計値だけでなく、**実際の消費電力を測る**ことが容量管理の基礎になります。

```bash
# BMC 経由（ハードウェアコース レッスン 6）
ipmitool sensor get 'Pwr Consumption'
ipmitool dcmi power reading

# Redfish 経由
curl -sku admin:PASS https://10.0.100.21/redfish/v1/Chassis/1/Power | jq '.PowerControl[0]'
```

```text
{
  "PowerConsumedWatts": 412,
  "PowerCapacityWatts": 1600,
  "PowerMetrics": {
    "AverageConsumedWatts": 398,
    "MaxConsumedWatts": 587,      ← ピーク値。容量計画にはこちらを使う
    "MinConsumedWatts": 210
  }
}
```

**容量計画には平均ではなくピーク値を使ってください。** 平均で設計すると、負荷が集中したタイミングでブレーカーが落ちます。

### 電力上限を設ける

機器側で上限をかけて、ラック全体の予算内に収める方法もあります。

```bash
# 消費電力の上限を 500W に設定する（機種により対応状況が異なる）
ipmitool dcmi power set_limit 500
ipmitool dcmi power activate
```

## PUE: 施設全体の効率

```text
PUE = 施設全体の消費電力 ÷ IT 機器の消費電力
```

| PUE | 意味 |
| --- | --- |
| 1.0 | 理想（冷却や配電の損失がゼロ） |
| 1.1–1.3 | 効率の良い大規模データセンター |
| 1.5–2.0 | 一般的な施設、古い自社サーバールーム |

PUE 1.5 なら、**IT 機器が 100kW 使うとき、施設全体では 150kW 消費している**ことになります。差の 50kW は主に空調です。

自社でサーバールームを持つ場合、この比率を把握しておくと、電気代とラック増設の限界が見えてきます。

## まとめ

- **ラックに載る台数は U 数ではなく電力で決まる**
- 連続負荷は**ブレーカー定格の 80% まで**。200V 30A は 4.8kW が上限
- **A/B 冗長では各系統を上限の 50% 以下に抑える**。でないと片系障害で全停止する
- 奥行き・耐荷重は発注前に確認する。GPU ノードは深く重い
- Switched PDU は BMC に次ぐ遠隔運用の保険
- UPS は発電機までの数十秒をつなぐもの。**バッテリは消耗品**
- 容量計画には**平均ではなくピーク消費電力**を使う
- 一斉起動時の突入電流でブレーカーが落ちることがある
