## 1 リクエストは 2 つの異なる処理

LLM の推論は、**性質のまったく違う 2 段階**でできています。ここを分けて考えないと、チューニングの方向を誤ります。

```text
① Prefill（プロンプト処理）
   入力トークン全体を一度に処理する
   → 行列積が大きい → 演算器を使い切れる → 演算律速

② Decode（生成）
   1 トークンずつ、前の出力を入力にして繰り返す
   → 1 回の計算は小さいが、毎回モデル全体の重みを読む
   → メモリ帯域律速
```

| | **Prefill** | **Decode** |
| --- | --- | --- |
| 律速 | **演算性能 (FLOPS)** | **メモリ帯域** |
| 並列度 | 高い（全トークン同時） | **低い（1 トークンずつ）** |
| 効く指標 | **TTFT**（最初の 1 文字までの時間） | **トークン間レイテンシ** |
| GPU の使われ方 | Tensor コアが埋まる | **演算器はほぼ遊ぶ** |

<h2 className="slide-cont">1 リクエストは 2 つの異なる処理（続き）</h2>

<Callout type="field">

**Decode がメモリ帯域律速だという点が、推論基盤の設計を決めます。**

1 トークン生成するたびに、モデルの全パラメータを VRAM から読み出す必要があります。

```text
70B モデル (FP16 = 140GB) を H100 SXM (3.35 TB/s) で動かす場合

  1 トークンあたり最低       140GB ÷ 3350GB/s ≒ 42 ms
  → 単一リクエストなら 毎秒 24 トークンが上限
```

**演算性能をいくら上げても、この上限は変わりません。** だから推論では「バッチにまとめて、1 回の重み読み出しで複数リクエストを同時に進める」ことが決定的に効きます。

レッスン 4 で見た `SM_ACTIVE` が低いのに遅い、という状況の典型がこれです。

</Callout>

## KV キャッシュ

Decode で毎回すべてを計算し直さないために、過去のトークンの中間状態（Key と Value）を保持します。これが **KV キャッシュ**で、**VRAM をモデル本体とは別に食います**。

```text
1 トークンあたりのサイズ
  = 2 (K と V) × 層数 × KVヘッド数 × ヘッド次元 × バイト数

例: 70B クラス（80 層、KV ヘッド 8、ヘッド次元 128、FP16）
  = 2 × 80 × 8 × 128 × 2 = 327,680 バイト ≒ 320 KB / トークン

コンテキスト 4,096 トークンなら 1 リクエストで約 1.3 GB
```

<Callout type="warning" title="同時実行数は KV キャッシュで決まる">

```text
H100 80GB で 70B モデル (INT8 で 70GB) を動かす場合

  VRAM 80GB − モデル 70GB = KV キャッシュに使えるのは 10GB
  1 リクエスト 1.3GB → 同時に 7 リクエスト程度が上限
```

**GPU を増やしてもモデルが同じなら、増えるのは KV キャッシュの余地です。** 「同時接続数が足りない」という問題は、演算性能ではなく VRAM の問題であることがほとんどです。

対処の方向は 3 つです。

- **モデルを量子化して空きを作る**（後述）
- **コンテキスト長の上限を制限する**（際限なく長い入力を許さない）
- GPU を増やす／VRAM の大きい GPU にする

長いコンテキストを許す設定は、そのまま同時実行数を削ることになります。**両方は取れません。**

</Callout>

## バッチングの方式

複数リクエストをまとめて処理することで、重み読み出しのコストを分散します。**ここでの方式の違いが、実効スループットを大きく変えます。**

```text
静的バッチング（素朴な実装）
  [A][B][C][D] をまとめて開始
  → 全部が終わるまで次のバッチを開始できない
  → 短い応答の A,B が終わっても、長い D を待つ間 GPU が遊ぶ

連続バッチング（continuous batching）
  1 トークン生成するごとにバッチを組み直す
  → 終わったリクエストは抜け、待っているリクエストが即座に入る
  → GPU が常に埋まる
```

**連続バッチングは、実測でスループットが数倍変わります。** vLLM、TensorRT-LLM、SGLang などの推論エンジンはいずれもこれを実装しています。

<Callout type="note" title="PagedAttention">

KV キャッシュを連続領域で確保すると、**「最大長ぶんを先に押さえる」ことになり、実際には使わない領域が無駄になります**（内部断片化）。

vLLM の PagedAttention は、KV キャッシュを固定サイズのブロックに分割し、必要になった分だけ割り当てます。Linux コース レッスン 3 で見た仮想メモリのページングと同じ発想です。

これにより、同じ VRAM でより多くの同時リクエストを収容できます。**自前でバッチ処理を書くより、実績のある推論エンジンを使うべき理由**がここにあります。

</Callout>

## 量子化

モデルの重みを低精度で保持し、**VRAM と読み出し量を減らします**。Decode がメモリ帯域律速である以上、**量子化は速度にも直結します**。

| 精度 | 70B のサイズ | 備考 |
| --- | --- | --- |
| FP16 / BF16 | 140 GB | 基準 |
| **FP8** | 70 GB | Hopper 以降のハードウェア対応あり |
| **INT8** | 70 GB | 広く使われる |
| INT4 (AWQ / GPTQ) | 35 GB | 劣化が出ることがある。要評価 |

```text
INT8 化の効果
  VRAM      : 140GB → 70GB （H100 1 枚に載る）
  読み出し量 : 半分  → Decode が約 2 倍速くなりうる
  KV の空き  : 大幅に増える → 同時実行数が増える
```

<Callout type="pitfall">

**量子化の劣化は「平均的には問題ない」で判断しないでください。**

ベンチマークのスコアが数%しか落ちていなくても、特定のタスク（コード生成、数値計算、長文の一貫性）で目立って崩れることがあります。

**自分たちの実際のプロンプトで評価してから採用してください。** 特に INT4 は、用途によって使えるかどうかが大きく分かれます。

なお KV キャッシュ自体も量子化できます（FP8 KV cache）。同時実行数を稼ぐ手段として有効ですが、こちらも品質への影響を確認してから使います。

</Callout>

## 見るべき指標

推論サービングでは、**スループットとレイテンシを別々に測ります**。

| 指標 | 意味 | 効くもの |
| --- | --- | --- |
| **TTFT** (Time To First Token) | 最初の 1 文字が返るまで | **体感の速さ**。Prefill とキュー待ち |
| **TPOT / ITL** | トークン間の間隔 | 読みやすさ。Decode の速度 |
| **スループット** | 全体の毎秒トークン数 | **コスト効率** |
| **キュー待ち時間** | バッチに入るまでの待ち | 負荷の指標 |

<Callout type="field">

**この 2 つは対立します。**

```text
バッチサイズを大きくする
  → スループット向上（GPU あたりのコストが下がる）
  → しかし TTFT は悪化（自分の番が来るまで待つ）

バッチサイズを小さくする
  → TTFT 改善
  → スループット低下（GPU が遊ぶ）
```

**「何を守るか」を先に決めてください。**

- 対話型（チャット、補完）→ **TTFT を SLO にする**。バッチ上限を抑える
- バッチ処理（要約、分類の一括実行）→ **スループット最優先**。待ち時間は許容する

この 2 つを同じエンドポイントで混ぜると、どちらの要件も満たせません。**用途ごとにデプロイを分ける**のが実務的な解です。

ミドルウェアコース レッスン 5 で扱ったとおり、平均ではなく **p95 / p99 の TTFT** を見てください。

</Callout>

## マルチ GPU での推論

モデルが 1 枚に載らない場合、レッスン 3 で扱った並列化を使います。

```text
テンソル並列 (TP)  : 層の行列を GPU 間で分割
  → 層ごとに All-Reduce が発生する
  → NVLink で繋がった GPU 内に閉じるのが原則
```

<Callout type="warning">

**推論のテンソル並列は、学習以上に通信レイテンシに敏感です。**

Decode では 1 トークンごとに層の数だけ集合通信が起きます。80 層のモデルなら 1 トークンあたり数十回です。1 回が 10μs でも、積み上がるとトークン間レイテンシを支配します。

- **ノードをまたぐテンソル並列は避ける**（NVLink の範囲に収める）
- PCIe 接続の GPU で TP を組むと、1 枚で動かすより遅くなることがある

レッスン 1 の `nvidia-smi topo -m` で、TP に使う GPU が `NV#` で繋がっていることを確認してください。

</Callout>

## 速度を上げる他の手段

| 手法 | 内容 |
| --- | --- |
| **投機的デコード** | 小さいモデルが数トークン先読みし、本体がまとめて検証する |
| **プレフィックスキャッシュ** | 共通の system prompt の KV を使い回す |
| **CUDA Graphs** | 小さなカーネル起動のオーバーヘッドを削る（レッスン 6） |
| チャンク化プレフィル | 長い prefill を分割し、decode を止めないようにする |

<Callout type="tip">

**プレフィックスキャッシュは、実運用で効果が出やすい割に見落とされがちです。**

全リクエストが同じ長い system prompt を持つ構成では、その部分の prefill が毎回繰り返されています。KV を共有すれば、その計算がまるごと消えます。

vLLM では `--enable-prefix-caching` で有効になります。**まず測って、効くなら入れる**という順序で検討してください。

</Callout>

## まとめ

- 推論は **prefill（演算律速）と decode（メモリ帯域律速）**の 2 段階
- **Decode の速度上限は「モデルサイズ ÷ メモリ帯域」**。演算性能では改善しない
- **同時実行数は KV キャッシュの空きで決まる**。長いコンテキストを許すと同時数が減る
- **連続バッチング**でスループットが数倍変わる。自前実装より推論エンジンを使う
- 量子化は VRAM と読み出し量を減らし、**速度にも効く**。ただし品質は自分のプロンプトで評価する
- **TTFT とスループットは対立する**。守る指標を先に決め、用途ごとにデプロイを分ける
- `gpu_cache_usage_perc` と `num_requests_waiting` が容量の指標
- 推論のテンソル並列は通信レイテンシに敏感。**NVLink の範囲に収める**
