## Linux にとっての「プロセス」

多くの教科書は「プロセス」と「スレッド」を別物として説明しますが、Linux カーネルの内部では**どちらも同じ `task_struct` という構造体**で表現されています。違いは、どのリソースを他と共有しているかだけです。

| 生成方法 | アドレス空間 | ファイル記述子表 | 呼び名 |
| --- | --- | --- | --- |
| `fork()` | 複製する | 複製する | プロセス |
| `pthread_create()` | 共有する | 共有する | スレッド |

どちらも内部では `clone()` システムコールを呼んでおり、渡すフラグ（`CLONE_VM`、`CLONE_FILES` など）が違うだけです。

<Callout type="note" title="スケジューリングの単位">

スケジューラが選ぶのは「プロセス」ではなく `task_struct` 単位、つまり実質スレッド単位です。`top` でプロセスの CPU 使用率が 400% と表示されるのは、4 本のスレッドがそれぞれ別のコアで走っているからです。

</Callout>

## プロセスの状態を読む

`ps` の `STAT` 列に出る 1 文字が、切り分けの出発点になります。

| 記号 | 状態 | 意味 | よくある原因 |
| --- | --- | --- | --- |
| `R` | Running / Runnable | 実行中、または実行可能で順番待ち | CPU を使っている、または CPU が足りない |
| `S` | Interruptible Sleep | シグナルで起こせる待ち | ソケット待ち、`sleep`、イベント待ち |
| `D` | Uninterruptible Sleep | シグナルでも起こせない待ち | ディスク I/O、NFS のハング |
| `Z` | Zombie | 終了済みだが親が回収していない | 親プロセスが `wait()` を怠っている |
| `T` | Stopped | `SIGSTOP` などで停止中 | デバッガ、`Ctrl+Z` |

```bash
# 状態別にプロセスを数える。障害時にまずこれを見る
ps -eo stat --no-headers | cut -c1 | sort | uniq -c | sort -rn

# D 状態のプロセスだけを、何を待っているかと一緒に出す
ps -eo pid,stat,wchan:30,comm | awk '$2 ~ /^D/'
```

<Callout type="warning" title="D 状態は kill できない">

`D` 状態のプロセスには `SIGKILL` すら届きません。シグナル処理はカーネルからユーザー空間へ戻るタイミングで行われますが、`D` のタスクはカーネル内部で I/O 完了を待って停止しているためです。

したがって「`kill -9` したのに消えない」場合、そのプロセスは高確率で `D` 状態です。原因はプロセス側ではなくストレージ側（デバイス応答なし、NFS サーバーの停止など）にあります。プロセスを追いかけても解決しません。

</Callout>

## スケジューラ: 誰に CPU を渡すか

実行可能（`R`）なタスクが CPU 数より多いとき、誰を走らせるかを決めるのがスケジューラです。

長らく **CFS**（Completely Fair Scheduler）が使われてきました。CFS は各タスクに `vruntime`（仮想実行時間）を持たせ、**最も vruntime が小さいタスク**を次に走らせます。たくさん走ったタスクは vruntime が伸びるので、自然と後回しになります。`nice` 値は vruntime の進む速さに重みを掛ける仕組みで、`nice -19`（低優先度）のタスクは vruntime が速く進み、順番が回りにくくなります。

Linux 6.6 以降、この CFS は **EEVDF**（Earliest Eligible Virtual Deadline First）に置き換えられました。EEVDF は公平性に加えて「各タスクに仮想的な締め切りを与え、締め切りが最も近いものを優先する」考え方を取り入れており、対話的なタスクの応答性が改善されています。

```bash
# 現在のカーネルのスケジューラ関連パラメータ
sysctl -a --pattern 'kernel.sched' 2>/dev/null | head

# プロセスごとのスケジューリングポリシーと優先度
chrt -p 1234
```

<Callout type="field">

通常のサーバー用途で `nice` やリアルタイムポリシー（`SCHED_FIFO` など）に手を出す機会はほとんどありません。リアルタイムポリシーは優先度の高いタスクが CPU を手放さないとシステム全体が固まるため、安易に設定すると復旧できなくなります。CPU の配分を制御したい場合は、次のレッスン以降で扱う **cgroup の CPU コントローラ**を使うほうが安全で確実です。

</Callout>

## ロードアベレージの正体

ここが Linux でいちばん誤解されるところです。

```bash
cat /proc/loadavg
# 出力例: 8.42 6.15 4.03 3/512 29845
#         ↑1分 ↑5分 ↑15分  ↑実行中/全タスク数  ↑最後に作られたPID
```

多くの UNIX では、ロードアベレージは「実行可能なタスク数の移動平均」です。しかし **Linux は `R` 状態に加えて `D` 状態のタスクも数えます**。

つまり Linux のロードアベレージは:

> 実行中・実行待ち（R）＋ 割り込み不可の待ち（D）のタスク数の移動平均

これが意味するのは、**ロードアベレージが高くても CPU が原因とは限らない**ということです。

| 状況 | CPU 使用率 | ロードアベレージ | 実際の原因 |
| --- | --- | --- | --- |
| CPU 過負荷 | 高い | 高い | 計算量、プロセス数 |
| ストレージ遅延 | **低い** | **高い** | ディスク、SAN、NFS |
| メモリ逼迫 | 中程度 | 高い | スワップイン待ち（これも D） |

<Callout type="pitfall">

「ロードアベレージが CPU コア数を超えたら CPU 増強」という判断は、Linux では誤りになりえます。ストレージが遅いだけの状態で CPU を増やしても改善しません。必ず `R` と `D` の内訳を確認してください。

</Callout>

## CPU 待ちと I/O 待ちを分ける

内訳を見るための具体的な手順です。

```bash
# 1. CPU そのものが飽和しているか (%idle と %iowait を見る)
mpstat -P ALL 1 5

# 2. ブロックデバイスが詰まっているか (%util, await)
iostat -xz 1 5

# 3. 状態別のタスク数の推移 (r 列 = 実行待ち, b 列 = 割り込み不可待ち)
vmstat 1 5
```

`vmstat` の先頭 2 列がそのまま答えになります。`r` が大きければ CPU 不足、`b` が大きければ I/O 待ちです。

### PSI: より直接的な指標

カーネル 4.20 以降では **PSI**（Pressure Stall Information）が使えます。これは「リソース不足によってタスクが待たされた時間の割合」を直接教えてくれます。

```bash
cat /proc/pressure/cpu
cat /proc/pressure/io
cat /proc/pressure/memory
```

```text
# /proc/pressure/io の例
some avg10=42.15 avg60=38.02 avg300=21.44 total=98234571
full avg10=18.33 avg60=15.71 avg300=9.02  total=41029384
```

- `some` … **いずれか**のタスクがそのリソース待ちで止まっていた時間の割合
- `full` … **すべて**のタスクが止まっていた時間の割合（＝システムが何も進んでいない）

---

<h2 className="slide-cont">CPU 待ちと I/O 待ちを分ける（続き）</h2>

`io` の `full avg10` が 18% なら、直近 10 秒のうち 18% の時間、システムは I/O 待ちで完全に停止していたことになります。ロードアベレージのような曖昧さがなく、リソースごとに分かれているため、原因の特定が一段速くなります。

<Callout type="tip">

監視基盤に入れる指標を選ぶなら、ロードアベレージより PSI の `some avg60` を推奨します。CPU・IO・メモリのどれが逼迫しているかが最初から分離されているため、アラートを受け取った時点で当たりがついています。

</Callout>

## まとめ

- Linux にとってプロセスとスレッドは同じ `task_struct`。違いは共有するリソースだけ
- `D` 状態は I/O 完了待ちで、`kill -9` も効かない。原因はプロセスの外にある
- スケジューラは CFS から EEVDF へ移行した。仮想時間で公平性を保つ考え方は共通
- **ロードアベレージは R + D**。CPU 使用率ではない
- 切り分けには `vmstat` の `r`/`b` 列、そして PSI が有効
