## VFS という共通の型

Linux は ext4・XFS・Btrfs・NFS・tmpfs・procfs など、性質のまったく違うファイルシステムを同じ `open()` / `read()` / `write()` で扱えます。これを可能にしているのが **VFS**（Virtual File System）という抽象層です。

VFS はすべてのファイルシステムに、次の 4 つのオブジェクトを実装するよう要求します。

| オブジェクト | 表すもの | 主な中身 |
| --- | --- | --- |
| **superblock** | マウントされたファイルシステム全体 | ブロックサイズ、総容量、inode 数 |
| **inode** | ファイルの実体（メタデータ） | サイズ、所有者、権限、タイムスタンプ、データの位置 |
| **dentry** | ディレクトリエントリ（名前と inode の対応） | ファイル名、親子関係 |
| **file** | 「開かれているファイル」 | 読み書き位置（オフセット）、アクセスモード |

重要なのは、**ファイル名は inode に含まれていない**という点です。名前は dentry が持っており、inode は名前を知りません。

## fd から実体までの経路

`open("/var/log/app.log", O_RDONLY)` が返す数字（ファイル記述子）から、実データまでは 3 段階を経由します。

<Figure name="fd-to-inode" caption="fd → file 構造体 → inode → データブロック。名前 (dentry) は inode とは別物" />

この 3 層構造が、いくつかの挙動を説明します。

- **`fork()` した親子で読み込み位置が共有される**
  fd 表は複製されますが、指している `file` 構造体は同じです。オフセットは `file` にあるので共有されます。
- **`dup()` した fd も位置を共有する**
  同じく `file` を共有するためです。
- **同じファイルを 2 回 `open()` すると位置は独立**
  `file` 構造体が別々に作られ、inode だけを共有します。

```bash
# あるプロセスが開いているファイルを、fd 番号付きで一覧する
ls -l /proc/1234/fd/

# ソケットやパイプも fd として現れる
lsof -p 1234
```

## 「削除したのに容量が空かない」

実務で最も遭遇する現象です。構造が分かっていれば一瞬で説明できます。

`rm` が実行するのは `unlink()` システムコールで、これは**ディレクトリエントリ（dentry）を消すだけ**です。inode とデータブロックが実際に解放されるのは、次の 2 条件が**両方**満たされたときです。

1. その inode を指すハードリンクが 0 になった
2. その inode を開いているプロセスが 0 になった

つまり、**あるプロセスが開いたままのファイルを `rm` しても、容量は戻りません**。名前だけが消え、プロセスは何事もなく書き込み続けます。

```text
$ df -h /var
Filesystem      Size  Used Avail Use%
/dev/sda2        50G   49G  1.0G  99%   ← 消したのに減らない

$ du -sh /var/log
2.1G  /var/log                          ← du では見えない
```

`du` はディレクトリを辿るので、名前が消えたファイルは数えられません。**`df` と `du` が食い違うときは、まずこれを疑います。**

```bash
# 削除済みだが開かれたままのファイルを探す
lsof +L1

# 出力例（NLINK が 0 なのが削除済みの証）
# COMMAND  PID  USER  FD  TYPE DEVICE     SIZE/OFF NLINK NODE NAME
# nginx   1234  root   5w  REG  253,2   48318382080     0  912 /var/log/nginx/access.log (deleted)
```

### 対処

---

<h2 className="slide-cont">「削除したのに容量が空かない」（続き）</h2>

```bash
# 方法1: プロセスにファイルを開き直させる（推奨）
systemctl reload nginx        # または kill -USR1 <pid>

# 方法2: 開いたままの fd 経由で中身だけ切り詰める（緊急時）
: > /proc/1234/fd/5
```

<Callout type="pitfall">

ログローテーションの設定ミスで頻発します。`logrotate` の `copytruncate` を使わずにファイルを `mv` + `rm` すると、アプリケーションは古い inode に書き続け、ディスクだけが埋まっていきます。`postrotate` でアプリにシグナルを送ってファイルを開き直させる設定になっているか確認してください。

</Callout>

## write は永続化ではない

`write()` が返ってきても、データはまだディスクにありません。書き込まれたのは**ページキャッシュ**（メモリ）です。

```text
write()  ──► ページキャッシュ（Dirty ページとしてマーク）
                   │
                   │ カーネルのライトバック処理が非同期に実行
                   ▼
              ディスク
```

この遅延書き込みがあるおかげで、小さな書き込みをまとめたり、同じブロックへの複数回の書き込みを 1 回にできます。代わりに、**書き込み直後に電源断が起きればデータは失われます**。

確実に永続化するには `fsync()` を呼ぶ必要があります。

```bash
# 未書き出し（Dirty）のデータ量を確認する
grep -E 'Dirty|Writeback' /proc/meminfo

# ライトバックの閾値
sysctl vm.dirty_background_ratio   # この割合を超えると非同期で書き出し開始（既定 10）
sysctl vm.dirty_ratio              # この割合を超えると write() がブロックされる（既定 20）
```

<Callout type="warning" title="dirty_ratio に達したときの挙動">

Dirty ページが `vm.dirty_ratio` に達すると、カーネルは**書き込みを行うプロセスを強制的に待たせて**（同期書き出しさせて）ページを減らします。

これが「普段は速いのに、時々書き込みが数秒固まる」という症状の正体です。メモリの多いサーバーほど既定の割合が示す絶対量が大きくなり、溜め込んだ末に一気に吐き出すため、スパイクが大きくなります。書き込みの多いサーバーでは `vm.dirty_background_bytes` などで絶対値指定に変えるのが有効です。

</Callout>

### データベースが fsync にこだわる理由

---

<h2 className="slide-cont">write は永続化ではない（続き）</h2>

トランザクションの永続性（ACID の D）は、`fsync()` がディスクへの到達を保証することに依存しています。ストレージ側の**書き込みキャッシュが電源保護されていない**場合、`fsync()` が成功を返してもデータが失われることがあります。

RAID コントローラの BBU（バッテリバックアップ）や、SSD の PLP（Power Loss Protection）は、まさにこの層を守るための仕組みです。ハードウェアの選定がデータ整合性に直結するのはここです。

## ジャーナリングと inode 枯渇

### ジャーナリング

クラッシュ時にファイルシステムの構造が壊れるのを防ぐため、変更内容を先にジャーナル領域へ書きます。ext4 には 3 つのモードがあります。

| モード | ジャーナルする対象 | 安全性 | 性能 |
| --- | --- | --- | --- |
| `journal` | メタデータ + データ | 最も高い | 最も遅い（二重書き込み） |
| `ordered` | メタデータのみ。ただしデータを先に書く | 既定。実用上十分 | 標準 |
| `writeback` | メタデータのみ。順序保証なし | クラッシュ後に古いデータが見えうる | 最も速い |

XFS はメタデータのみのジャーナリングで、大容量・並列書き込みに強い設計です。

### inode 枯渇

**容量が余っていてもファイルが作れなくなる**ことがあります。ext4 は `mkfs` 時に inode 数を固定するためです。

```bash
df -h    # Use% 45%  ← 容量には余裕がある
df -i    # IUse% 100% ← inode が枯渇している
```

小さなファイルを大量に作るキャッシュディレクトリやメールスプールで起こります。ext4 では後から増やせないため、`mkfs.ext4 -i` で作り直すか、inode を動的に確保する XFS を選ぶことになります。

<Callout type="tip">

マウントオプション `noatime` は、読み込みのたびに発生する atime（最終アクセス時刻）の更新を止めます。現在の既定は `relatime`（1 日 1 回程度に間引く）なので効果は昔ほど大きくありませんが、読み込みが極端に多いファイルサーバーでは今も有効です。

</Callout>

## まとめ

- VFS が superblock / inode / dentry / file の 4 つで差異を吸収している
- ファイル名は inode ではなく dentry が持つ。`rm` は名前を消すだけ
- 開かれたままのファイルを消すと `df` と `du` が食い違う。`lsof +L1` で特定する
- `write()` はページキャッシュまで。永続化には `fsync()` が必要
- `vm.dirty_ratio` 到達時の強制待機が、書き込みのスパイクの正体
