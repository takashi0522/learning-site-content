## なぜインフラ側がこれを知る必要があるか

コードを書かなくても、**「この処理を GPU に載せれば速くなるか」を判断する場面**は来ます。

```text
「このバッチ処理、GPU で速くなりませんか」
「GPU を入れたのに期待したほど速くならない」
「GPU インスタンスのコストに見合っていない」
```

これらに答えるには、**GPU が何を速くする装置なのか**を実行モデルのレベルで知っておく必要があります。レッスン 1 で構造を見ましたが、ここでは「どう実行されるか」を扱います。

---

## スレッド階層

CUDA のプログラムは、**同じコードを大量のスレッドが一斉に実行する**形で書かれます。

```text
カーネル起動（GPU で実行する関数を呼ぶ）
  └── Grid（全体）
        └── Block（数百スレッドの塊。1 つの SM に割り当てられる）
              └── Warp（32 スレッド。実行の最小単位）
                    └── Thread
```

| 単位 | 数の目安 | 対応するもの |
| --- | --- | --- |
| Thread | 数万〜数百万 | 処理する要素 1 つ |
| **Warp** | **32 スレッド固定** | **命令を一斉に実行する単位** |
| Block | 128〜1024 スレッド | SM に割り当てられる単位。共有メモリを共有 |
| Grid | Block の集合 | カーネル 1 回分 |

### warp が実行の単位

**ここが CPU との決定的な違いです。** GPU は 32 スレッドをひとまとめにして、**同じ命令を同時に実行**します（SIMT）。

```text
warp 内の 32 スレッドは、常に同じ命令を実行する
  → データは違ってよい（スレッドごとに別の要素を処理）
  → 命令は同じでなければならない
```

---

<h2 className="slide-cont">スレッド階層（続き）</h2>

<Callout type="warning" title="分岐は warp を半分ずつ動かす">

warp 内で条件分岐の結果が割れると、**両方の経路を順番に実行**します。

```text
if (x > 0) { A }   ← 20 スレッドが該当
else       { B }   ← 12 スレッドが該当

実行:
  ① A を実行（12 スレッドは待機）
  ② B を実行（20 スレッドは待機）
  → 所要時間は A + B。並列に処理されない
```

これを **warp divergence** と呼びます。**分岐が多いコードは GPU で速くなりません。** 最悪の場合、32 通りに分かれれば 32 倍の時間がかかります。

「if 文が多い業務ロジックを GPU に載せる」という発想がうまくいかないのは、この性質によります。

</Callout>

## メモリ階層とアクセスパターン

ハードウェアコース レッスン 1 で CPU のキャッシュを見ましたが、GPU にも階層があります。

| 階層 | 速度 | 範囲 |
| --- | --- | --- |
| レジスタ | 最速 | スレッドごと |
| **共有メモリ / L1** | 非常に速い | **Block 内で共有**（明示的に使う） |
| L2 | 速い | GPU 全体 |
| **グローバルメモリ (VRAM)** | 遅い（数百サイクル） | GPU 全体 |

### コアレッシング

**GPU のメモリアクセスで最も効くのがこれです。**

```text
良い（coalesced）:
  thread 0 → addr 0
  thread 1 → addr 4      連続したアドレス
  thread 2 → addr 8      → warp 全体で 1 回の転送にまとまる
  ...

悪い（散在）:
  thread 0 → addr 0
  thread 1 → addr 4096   バラバラのアドレス
  thread 2 → addr 8192   → 32 回の別々の転送になる
```

**同じ処理でも、データの並べ方で 10 倍以上変わります。** 構造体の配列（AoS）より配列の構造体（SoA）が好まれるのはこのためです。

---

<h2 className="slide-cont">メモリ階層とアクセスパターン（続き）</h2>

<Callout type="note">

これはハードウェアコース レッスン 1 で扱った **CPU のキャッシュライン**と同じ話です。CPU では 64 バイト単位で読むので連続アクセスが速く、GPU では warp 単位でまとめるので連続アクセスが速い。

**「連続したメモリを順に舐める処理が速い」**という原則は、CPU でも GPU でも変わりません。

</Callout>

## 演算律速かメモリ帯域律速か

**GPU に載せる価値があるかを判断する、最も実用的な観点です。**

```text
演算強度 (arithmetic intensity) = 演算回数 ÷ 読み書きしたバイト数
```

```text
低い（メモリ帯域律速）:
  ベクトルの加算   c[i] = a[i] + b[i]
    → 12 バイト読み書きして 1 回の加算 → 0.08 FLOP/byte
    → いくら演算器があっても、データを運びきれない

高い（演算律速）:
  行列積          C = A × B
    → 一度読んだデータを何度も使い回す → 数十〜数百 FLOP/byte
    → 演算器を使い切れる → GPU が本領を発揮する
```

| 処理 | 演算強度 | GPU 向き |
| --- | --- | --- |
| **行列積・畳み込み** | **高い** | **非常に向く** |
| FFT | 中 | 向く |
| ベクトル演算・要素ごとの加算 | 低い | 帯域ぶんしか速くならない |
| **LLM の decode**（レッスン 5） | **低い** | 帯域律速。演算器は遊ぶ |
| ソート・探索 | 低い + 分岐 | 条件による |

---

<h2 className="slide-cont">演算律速かメモリ帯域律速か（続き）</h2>

<Callout type="field">

**「GPU は行列積が速い装置」**と理解しておくのが、判断としては実用的です。

AI が GPU で速いのは、処理のほとんどが行列積だからです。逆に言えば、**行列積に落とせない処理は GPU に載せても期待したほど速くなりません**。

「GPU を入れたのに 2 倍にしかならない」という場合、その処理はメモリ帯域律速である可能性が高いです。その場合、速くなる上限は

```text
GPU のメモリ帯域 ÷ CPU のメモリ帯域 ≒ 3350 ÷ 300 ≒ 11 倍
```

であって、演算性能の比（数十〜百倍）ではありません。レッスン 4 の `DRAM_ACTIVE` が高く `PIPE_TENSOR_ACTIVE` が低ければ、帯域律速だと分かります。

</Callout>

## カーネル起動のオーバーヘッド

**小さい処理を大量に投げる構成**では、計算以外のコストが支配的になります。

```text
カーネル 1 回の起動コスト ≒ 5〜10 マイクロ秒

  計算が 3μs で終わるカーネルを 1000 回起動
    → 計算 3ms に対して起動コスト 5〜10ms
    → 実行時間の大半が起動の待ち
```

対処は 2 つです。

| 手法 | 内容 |
| --- | --- |
| **カーネル融合** | 複数の処理を 1 つのカーネルにまとめる |
| **CUDA Graphs** | 一連のカーネル起動を記録して、1 回の投入で再生する |

```bash
# 起動回数とカーネルごとの時間を見る（レッスン 4）
nsys profile -o report --trace=cuda python app.py
nsys stats report.nsys-rep
```

<Callout type="tip">

**タイムラインで GPU の実行区間に細かい隙間が並んでいたら、起動オーバーヘッドを疑います。**

LLM の推論（レッスン 5）で CUDA Graphs が効くのは、decode が「小さいカーネルを層の数だけ繰り返す」構造だからです。vLLM などが既定で使っているのはこのためです。

</Callout>

## ホストと GPU の間の転送

レッスン 1 で見たとおり、CPU と GPU は PCIe で繋がっています（ハードウェアコース レッスン 5）。

```text
PCIe Gen5 x16 : 約 64 GB/s
H100 の VRAM  : 約 3350 GB/s        → 50 倍以上の差
```

**データを GPU に送って、計算して、返す。この往復が計算より長ければ、GPU に載せる意味がありません。**

```text
100MB のデータを送って、1ms の計算をして、100MB 返す

  転送: 100MB ÷ 64GB/s × 2 ≒ 3.1 ms
  計算: 1 ms
  → 転送が計算の 3 倍。CPU でやったほうが速いかもしれない
```

<Callout type="pitfall" title="GPU に向かない処理の特徴">

次のいずれかに当てはまるなら、GPU への移植は慎重に判断してください。

```text
✗ データが小さい            転送コストが計算を上回る
✗ 分岐が多い                warp divergence で並列度が落ちる
✗ 逐次依存が強い            前の結果が出ないと次に進めない処理は並列化できない
✗ 演算強度が低い            帯域ぶんしか速くならない
✗ 毎回ホストと同期する      GPU が待たされ続ける
```

逆に向くのは、**大量の同じ計算を、依存関係なく、連続したデータに対して行う**処理です。

「業務バッチを GPU で速くしたい」という相談の多くは、上の ✗ に該当します。**まず CPU 側で並列化やアルゴリズムの見直しをしたほうが、費用対効果が高いことが多い**です。

</Callout>

## 判断のための手順

<Callout type="field">

GPU 化を検討するとき、次の順で確認すると判断を誤りません。

```text
① 処理の中核は行列積・畳み込みか、それに落とせるか
     いいえ → 期待値を下げる。帯域比（約 10 倍）が上限

② 1 回あたりのデータ量は十分大きいか（転送コストを償却できるか）
     いいえ → CPU のほうが速い可能性が高い

③ 分岐や逐次依存が少ないか
     いいえ → 並列度が出ない

④ 既存のライブラリ（cuBLAS / cuDNN / RAPIDS / DALI）で書けるか
     はい → まずそれを試す。自前カーネルは最後の手段

⑤ 実測する
     レッスン 4 の SM_ACTIVE / DRAM_ACTIVE / TENSOR_ACTIVE で
     どこが律速かを確認してからチューニングする
```

**④ が重要です。** 自前の CUDA カーネルを書くより、cuBLAS や RAPIDS のような最適化済みライブラリを使うほうが、たいてい速く、保守も楽です。インフラ側からの提案としては「GPU 化しましょう」より「この処理を GPU 対応ライブラリに置き換えられますか」のほうが実りやすくなります。

</Callout>

## まとめ

- GPU は **32 スレッドの warp** 単位で同じ命令を実行する
- **分岐が割れると両方を順に実行する**（warp divergence）。if の多い処理は向かない
- メモリは**連続アクセス（コアレッシング）**が決定的に効く。CPU のキャッシュラインと同じ原理
- **演算強度が高い処理（行列積）が GPU の本領**。低い処理は帯域ぶんしか速くならない
- 帯域律速の処理で期待できるのは **10 倍程度**であって、演算性能の比ではない
- 小さいカーネルを大量に投げると**起動オーバーヘッドが支配的**になる。CUDA Graphs で削る
- **PCIe の転送が計算より長ければ、GPU に載せる意味はない**
- 向かないのは「小さい・分岐が多い・逐次依存・低演算強度・頻繁な同期」
- 自前カーネルより、**最適化済みライブラリへの置き換え**を先に検討する
