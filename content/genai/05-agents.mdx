## ワークフローとエージェント

レッスン 4 のツール呼び出しを何度も繰り返すと、モデルに仕事を進めさせられます。Anthropic の記事「Building effective agents」は、こうした仕組みをまとめて**エージェント的なシステム**と呼び、2 つを区別しています。

| | ワークフロー | エージェント |
| --- | --- | --- |
| 定義 | LLM とツールを、**あらかじめ決めたコードの道筋**で動かす | LLM が、**自分の進め方とツールの使い方を動的に決める** |
| 向いている場面 | 決まった仕事を、予測どおり一貫して処理したい | 柔軟さと、モデルによる判断が必要 |

記事は、**できるだけ単純な解決から始め、必要なときだけ複雑にする**よう勧めています。エージェント的なシステムは、性能を上げる代わりに**レイテンシと費用**を払うことが多く、多くの用途では、**1 回の LLM の呼び出しを、検索（レッスン 3）と例の提示で最適化すれば、通常は足りる**、としています。

---

## 決まった道筋で組む — 5 つのワークフロー

記事が挙げるワークフローの型です。どれも、LLM の呼び出しをコードでつないだものです。

| 型 | 中身 | 記事の例 |
| --- | --- | --- |
| プロンプトの連鎖 | 前の出力を次の入力にして、段階を踏む。途中にプログラムの検査を挟める | 文書の骨子を書く → 条件を満たすか確かめる → 本文を書く |
| 振り分け | 入力を分類して、専用の処理に回す | 簡単な質問は小さく安いモデルへ、難しい質問は高性能なモデルへ |
| 並列 | 独立した部分を同時に処理する／同じ仕事を複数回やって投票する | 1 つのインスタンスが応答を作り、別のインスタンスが不適切な内容を検査する |
| 指揮役と作業役 | 中心の LLM が仕事を分けて配り、結果をまとめる | 変更すべきファイルの数が事前に分からないコードの修正 |
| 評価役と改善役 | 1 つが作り、もう 1 つが評価して返す。これを繰り返す | 評価の基準がはっきりしている翻訳や検索 |

運用の仕事でも、「アラートを分類して担当の手順に回す（振り分け）」「調査の要約を書かせ、別の呼び出しで抜けを指摘させる（評価と改善）」のように当てはめられます。

## エージェントの正体はループ

記事は、エージェントは高度な仕事をこなせるが、**実装は多くの場合素直で、環境からのフィードバックに基づいてツールを使う LLM がループしているだけ**だ、と書いています。

<Figure name="agent-loop" caption="ツールを使い、結果を見て、次を決める。迷えば人に戻す" source="Anthropic — Building effective agents を元に作図" />

記事によると、エージェントは人の指示や対話から始まり、仕事が明確になると**計画して自分で進め**、必要なら人に情報や判断を求めに戻ります。進む途中では、ツールの結果やコードの実行結果といった**環境からの「事実」（ground truth）**を、毎回取りにいくことが重要だとしています。

一方で記事は、自律的に動く分だけ**費用が高くなり、誤りが積み重なりうる**とも書き、**サンドボックスの中での十分な試験と、適切な防護柵**を勧めています。

---

## 向いている仕事、向いていない仕事

記事が、顧客の事例から有望だとしている仕事には、共通点があります。**会話と操作の両方が要り、成功の基準がはっきりしていて、フィードバックのループが回り、人が意味のある監督をできる**ことです。

その代表としてコーディングのエージェントを挙げ、理由をこう書いています。

- コードの解は、**自動テストで確かめられる**
- エージェントは、テストの結果をフィードバックにして**繰り返し直せる**
- 問題の範囲がはっきりしていて、出来を客観的に測れる

ただし、テストで機能は確かめられても、システム全体の要件に合っているかは**人のレビューが欠かせない**、とも書いています。

基盤の仕事に当てはめると、**結果をコマンドで確かめられる仕事**（設定の差分の確認、ログの集計、手順書どおりの検証）は向いており、**やり直しのきかない操作**（本番の削除、再起動、ファームウェアの更新）は、人の確認を挟む設計にすべきだと考えられます。

## 枠をはめる — Claude Code の権限

エージェントに何をさせてよいかは、**権限**で決めます。例として、コーディングのエージェントである Claude Code のドキュメントを見ます（2026 年 10 月時点）。

| モード | ドキュメントの説明（要約） |
| --- | --- |
| `default`（Manual） | 各ツールを初めて使うときに許可を求める |
| `acceptEdits` | 作業ディレクトリ内のファイル編集と、`mkdir` などの一般的なファイル操作を自動で許可する |
| `plan` | ファイルを読み、読み取り専用のコマンドで調べるが、ソースは編集しない |
| `auto` | 定型の確認なしで動く。コマンドやネットワークの要求の前に、別の分類器が、依頼に沿った操作かを確かめる |
| `dontAsk` | 確認が必要な呼び出しをすべて自動で拒否する（事前に許可したものは動く） |
| `bypassPermissions` | 確認をとばす（どのモードでも自動では許可されない操作を除く） |

ドキュメントによると、許可・確認・拒否のルールは**拒否 → 確認 → 許可の順に評価され**、最初に当たったものが結果になります。たとえば `Bash(aws *)` を拒否すると、より狭い `Bash(aws s3 ls)` を許可していても**拒否が勝ちます**。許可のルールで、拒否に例外を作ることはできません。

## サンドボックス — OS に守らせる

権限の確認は、**人がその場で判断する**仕組みです。Claude Code のドキュメントは、作業ディレクトリの外への書き込みの確認も確認の 1 つにすぎず、**許可した Bash のコマンドは、ユーザーの権限で届くどこにでも書ける**と書いています。

そこで、OS が強制する境界として **Bash のサンドボックス**があります。ドキュメントの表から、既定の挙動を抜き出します。

| 対象 | 既定 |
| --- | --- |
| 書き込み | 作業ディレクトリ・ユーザーごとの一時ディレクトリ・追加したディレクトリだけ |
| 読み取り | **マシンのほとんど**。`~/.ssh` や `~/.aws/credentials` のような資格情報のファイルも含む（`denyRead` などで制限する） |
| ネットワーク | 直接は出られない。手元のプロキシが、許可したドメインかを確かめる（許可のリストは空から始まる） |
| 環境変数 | Claude Code から引き継ぐ。環境に入っている秘密情報も含む |

ドキュメントによると、サンドボックスは**既定では無効**で、**シェルのコマンドだけ**を囲みます（ファイル操作のツールや MCP サーバーは外で動く）。また macOS・Linux・WSL2 で動き、**ネイティブの Windows ではコマンドはサンドボックスなしで動きます**。

---

## まとめ

- **ワークフロー**は決めた道筋で LLM を動かし、**エージェント**は LLM が進め方を自分で決める。まず単純な解決から
- ワークフローの型は、連鎖・振り分け・並列・指揮役と作業役・評価役と改善役
- エージェントの正体は、**ツールを使い、結果（ground truth）を見て、次を決めるループ**。費用がかかり、誤りが積み重なりうる
- 向いているのは、**結果を確かめられ、フィードバックが回り、人が監督できる**仕事。やり直しのきかない操作は人の確認を挟む
- Claude Code の権限は**拒否 → 確認 → 許可**の順。拒否に許可で例外は作れない
- サンドボックスは OS が守る境界。ただし**既定は無効**で、**読み取りはほぼ全部（資格情報を含む）**が既定。ネイティブの Windows では効かない
