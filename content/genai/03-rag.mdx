## モデルが知らないことを、どう答えさせるか

レッスン 1 で見たとおり、モデルが応答のときに参照できるのは、学習で身につけたものと、コンテキストウィンドウに入れたものです。社内の手順書や、昨日の障害の記録は、学習には入っていません。

RAG（Retrieval-Augmented Generation）の論文（Lewis et al., 2020）は、言語モデルがパラメータに蓄えた知識は、**正確に取り出したり、更新したり、出典を示したりするのが難しい**と述べ、学習済みのモデルに**検索できる外部の記憶**を組み合わせる方法として RAG を提案しました。Claude のドキュメントの用語集は、RAG を、外部の知識や文書から関係するものを探して**コンテキストウィンドウに渡し**、答えを根拠に結びつける手法として説明しています。

<Callout type="tip" title="全部入るなら、全部入れる">

Anthropic の Contextual Retrieval の記事は、知識が **20 万トークン（およそ 500 ページ）より小さいなら、RAG を使わずに全部をプロンプトに入れればよい**と書いています（2024 年 9 月の記事。当時のモデルのウィンドウを前提にした目安）。プロンプトキャッシュ（レッスン 2）を使えば、毎回送る費用も下げられます。RAG は、全部は入らないときの方法です。

</Callout>

## 前処理と、質問が来たとき

<Figure name="rag-pipeline" caption="前もって文書を検索できる形にしておき、質問に近い断片だけをプロンプトに足す" source="Anthropic — Introducing Contextual Retrieval の RAG の説明を元に作図" />

Contextual Retrieval の記事は、典型的な RAG の流れを次のように説明しています。

| 段 | すること |
| --- | --- |
| 前処理 | 文書を、ふつう**数百トークン以下の断片（チャンク）**に分ける。埋め込みモデルで断片を**ベクトル**にし、意味の近さで探せるベクトル DB に入れる |
| 質問時 | 質問に**意味の近い断片**を探す（Embeddings のページによると、質問も `input_type` を query にして埋め込む）。上位の断片をプロンプトに足して、モデルに答えさせる |

基盤から見ると、RAG は**ベクトル DB という検索用のデータベースが 1 つ増える**ことです。運用の見立てとしては、文書が更新されたら、その断片を作り直して入れ直す仕組みも考えておく必要があります。

## 意味で探す、言葉で探す

**埋め込み**は、文章を、意味の近さを測れる数値の並び（ベクトル）にしたものです（Claude のドキュメントの Embeddings のページ）。似た意味の文章は近いベクトルになるので、言い回しが違っても探せます。

ただし記事は、埋め込みは意味の関係をよく捉える一方で、**決定的な完全一致を取りこぼすことがある**と書いています。例として挙げているのは、「Error code TS-999」という質問です。埋め込みはエラーコード一般の文書を見つけても、`TS-999` そのものを含む文書を逃しうる。そこで、単語の一致で順位を付ける古い手法 **BM25** を組み合わせます。

| 方法 | 得意なもの |
| --- | --- |
| 埋め込み（意味） | 言い換え、ぼんやりした質問 |
| BM25（単語） | エラーコード、ホスト名、コマンド名のような**一意な識別子や専門用語** |

記事は、両方で上位を探し、結果を統合してから上位 K 個をプロンプトに足す流れを示しています。基盤の文書は識別子だらけなので、単語での検索の価値は大きいと考えられます。

## 断片にすると、文脈が消える

記事が指摘する従来の RAG の弱点は、**断片にした時点で文脈が失われる**ことです。記事の例では、「その会社の売上は前の四半期より 3% 伸びた」という断片だけでは、どの会社のいつの話か分かりません。

対策として記事が提案する **Contextual Retrieval** は、埋め込む前と BM25 の索引を作る前に、各断片に**その断片が文書のどこの話かを説明する短い文（ふつう 50〜100 トークン）を付け足します**。この文は、文書全体と断片を Claude に渡して作らせます。

Anthropic 自身の実験として、記事は次のように報告しています（複数の分野の文書で、上位 20 個に正解が入らなかった割合を測ったもの）。説明文を付けた埋め込みだけで検索の失敗が **35% 減り**（5.7% → 3.7%）、説明文を付けた BM25 も組み合わせると **49% 減り**（→ 2.9%）、さらに検索結果の並べ替え（reranking）を加えると **67% 減った**（→ 1.9%）。

障害の記録でいえば、「再起動で解消」という断片には、**どのホストの、いつの、何の障害か**が付いていないと役に立ちません。記事も、断片の大きさ・区切り方・重なりの選び方が検索の性能に影響しうる、と書いています。

## 基盤から見た容量と索引

**ベクトルの容量**は、断片の数 × 次元 × 1 つの値の大きさで決まります。Claude のドキュメントが紹介する Voyage AI の埋め込みモデル（2026 年 10 月時点の Voyage 4 世代）は、既定で **1,024 次元**（256〜2,048 から選べる）、値は既定で **32 ビット（4 バイト）の浮動小数点**です。つまり 1 断片あたり 4 KB で、**1,000 万個の断片なら約 40 GB**（索引と元の文章は別）。ドキュメントによると、8 ビットの整数に量子化すれば 4 分の 1、1 ビットなら 32 分の 1 になります。

**検索の索引**について、PostgreSQL の拡張 pgvector の README（2026 年 10 月時点、v0.8 系）は次のように説明しています。

- 既定では**全件と比べる正確な検索**で、取りこぼしは無い（recall が完全）
- 索引を作ると、**取りこぼしを少し許して速くする近似検索**になる。索引を付けると、同じ質問でも結果が変わる
- 索引の種類のうち HNSW は、速さと取りこぼしの兼ね合いで IVFFlat より優れるが、**作るのが遅く、メモリを多く使う**。索引の作成は、グラフが `maintenance_work_mem` に収まると大幅に速い

<h2 className="slide-cont">基盤から見た容量と索引（続き）</h2>

pgvector の README が示す、索引のグラフがメモリに収まらなくなったときの表示です。

```text
NOTICE:  hnsw graph no longer fits into maintenance_work_mem after 100000 tuples
DETAIL:  Building will take significantly more time.
HINT:  Increase maintenance_work_mem to speed up builds.
```

README は、`maintenance_work_mem` をサーバーのメモリを使い切るほど大きくしないよう注意しています。また、初めに大量のデータを入れるときは、**データを入れてから索引を作るほうが速い**としています。

<Callout type="field" title="RAG は「データベースの運用」でもある">

ベクトル DB は、容量・メモリ・索引の作り直し・バックアップの対象になります。ミドルウェアコース レッスン 3 の PostgreSQL の運用が、ほぼそのまま当てはまります。文書の権限（誰がどの文書を見てよいか）を検索結果に反映させる設計も必要です。検索で見つけた断片は、そのままモデルに渡るからです。

</Callout>

## まとめ

- RAG は、**検索した文書をコンテキストウィンドウに足して**答えさせる。モデルの知識の更新・出典の提示の難しさを補う
- 知識がウィンドウに全部入るなら、RAG を使わず全部入れる選択肢もある（キャッシュと組み合わせる）
- 前処理で**断片 → ベクトル → ベクトル DB**、質問時に**近い断片を上位 K 個**探してプロンプトに足す
- 埋め込みは意味で探し、**BM25 は識別子や専門用語の完全一致**に強い。組み合わせる
- 断片は文脈を失う。**断片ごとに説明を付けてから埋め込む**（Contextual Retrieval）と、検索の失敗が減ったと報告されている
- ベクトルは 1,024 次元 × 4 バイトなら 1 断片 4 KB。近似検索の索引は速いが取りこぼしを許し、HNSW はメモリを多く使う
