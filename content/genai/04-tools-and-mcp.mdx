## モデルは「呼んでほしい」と返すだけ

レッスン 1〜3 のモデルは、文章を受け取って文章を返すだけでした。ツール呼び出し（function calling とも呼ばれる）を使うと、モデルに**外部の関数や API を使わせる**ことができます。

ただし、モデル自身が関数を実行するわけではありません。Claude のドキュメントによると、Claude は利用者の要求とツールの説明から**いつツールを呼ぶかを判断し**、**構造化された呼び出しを返します**。それを実行するのは、アプリケーション（クライアントツール）か Anthropic の基盤（サーバーツール）です。

<h2 className="slide-cont">モデルは「呼んでほしい」と返すだけ（続き）</h2>

ドキュメントの例（`get_weather`）に沿って往復を追います。

1. アプリケーションは、質問と一緒に、**使えるツールの定義**（名前・説明・入力の形 `input_schema`）を送る
2. モデルは、`stop_reason` を `tool_use` にして、**`tool_use` ブロック**（どのツールを、どんな入力で呼ぶか）を返す
3. アプリケーションがその操作を**実行する**
4. 結果を **`tool_result` ブロック**にして、もう一度要求を送る
5. モデルは結果を踏まえて答える

| 種類 | 実行する場所 | 例（ドキュメント） |
| --- | --- | --- |
| クライアントツール | **アプリケーションの中** | 自分で定義したツール、`bash`、`text_editor` |
| サーバーツール | Anthropic の基盤 | `web_search`、`web_fetch`、`code_execution` |

ドキュメントのとおり、**クライアントツールはアプリケーションの中で実行されます**。基盤から見ると、ここから、ツールはアプリケーションが動いている場所で、その権限で動くことになります（実装上の帰結）。`bash` のツールを与えれば、モデルの依頼でそのマシンのコマンドが動きます。

## モデルは、いつツールを呼ぶか

ドキュメントによると、既定（`tool_choice` が `auto`）では、モデルは毎回、ツールを呼ぶか直接答えるかを判断します。要求がツールの説明に合い、**答えがまだコンテキストに無い**ときに呼びます。システムプロンプトでこの境目を動かせるほか、`tool_choice` で呼び出しを強制することもできます。

<Callout type="pitfall" title="足りない入力を「推測」することがある">

ドキュメントは、ツールの必須の入力が足りないときの例を挙げています。Claude Opus は足りないことに気づいて聞き返すことがずっと多い一方、Claude Sonnet は聞き返すこともあれば、**もっともらしい値を推測して埋める**こともある、と書いています（場所を言わずに「天気は？」と聞いた例では、指定していない `New York, NY` が入った）。そして、この挙動は、曖昧なプロンプトや能力の低いモデルでは特に**保証されない**としています。

天気なら笑い話ですが、`restart_service(host=...)` のようなツールで**ホスト名を推測されたら**事故になります。破壊的なツールは、入力を推測で埋めさせない設計（実行前の確認、対象の限定）が要ります。

</Callout>

入力の形をスキーマに厳密に合わせたいときは、ツールの定義に `strict: true` を付けます（レッスン 2 の Structured outputs と同じ考え方）。

## ツールのつなぎ方をそろえる — MCP

ツールを使うアプリケーションと、ツールを提供するシステム（チケット管理、監視、ファイル、データベース…）の組み合わせごとに、つなぎ方を作っていては大変です。**MCP（Model Context Protocol）**は、そのつなぎ方をそろえる**オープンなプロトコル**です。Claude のドキュメントの用語集は、AI アプリケーションのための USB-C ポートのようなもの、とたとえています。

<Figure name="mcp-participants" caption="ホストは MCP サーバーごとにクライアントを 1 つ作る。サーバーはローカルにもリモートにも置ける" source="Model Context Protocol — Architecture overview を元に作図" />

| 参加者 | 役割（MCP のドキュメント） |
| --- | --- |
| **MCP ホスト** | AI アプリケーション（Claude Code、Claude Desktop、VS Code など）。1 つ以上のクライアントを管理する |
| **MCP クライアント** | ホストの中の部品。**サーバー 1 つにつき 1 つ**作られ、接続を保つ |
| **MCP サーバー** | 文脈や機能を提供するプログラム。ローカルでもリモートでもよい |

---

<h2 className="slide-cont">ツールのつなぎ方をそろえる — MCP（続き）</h2>

MCP は 2 つの層でできています。

- **データ層**: JSON-RPC 2.0 のメッセージ。サーバーが出すものは 3 種類で、**ツール**（操作を実行する関数）・**リソース**（ファイルの中身やレコードなどの文脈）・**プロンプト**（使い回せるひな形）。クライアントは `tools/list` で使えるツールを調べ、`tools/call` で実行する
- **トランスポート層**: **stdio**（同じマシンのプロセス間で直接やり取りし、ネットワークのオーバーヘッドが無い）と、**Streamable HTTP**（リモートのサーバー。HTTP の認証を使え、トークンの取得には OAuth を推奨）

ドキュメントによると、stdio のローカルなサーバーはふつう 1 つのクライアントに、Streamable HTTP のリモートなサーバーは多数のクライアントに応えます。仕様は版ごとに日付で管理されていて、2026 年 10 月時点の最新は 2026-07-28 版です。

基盤から見ると、リモートの MCP サーバーは **HTTP で提供されるサービス**です。社内のシステムを MCP で出すなら、通常の Web API と同じく、認証・認可・通信の暗号化・アクセスの記録を設計するのが妥当でしょう（このコースの助言）。

## 仕様が求める「同意」

MCP の仕様は、MCP が**任意のデータへのアクセスとコードの実行**を可能にする以上、実装する側がセキュリティと信頼に注意しなければならない、として、原則を挙げています。

- 利用者は、すべてのデータアクセスと操作に**明示的に同意し、理解していなければならない**
- ホストは、利用者のデータをサーバーに見せる前に、**明示的な同意**を得なければならない
- **ツールは任意のコードの実行に当たる**ので、相応の注意を払って扱う。特に、ツールのふるまいの説明（アノテーションなど）は、**信頼できるサーバーから得たものでない限り、信頼できないものとして扱う**
- ホストは、**ツールを呼ぶ前に利用者の明示的な同意**を得なければならない

仕様は同時に、MCP 自体はこれらの原則をプロトコルの水準では**強制できない**と書き、実装する側に、同意と認可の流れを作り込むよう求めています。使う側から見れば、どの MCP サーバーをつなぐかの判断も、自分たちに残ります。どの MCP サーバーをつなぐかは、どのソフトウェアをインストールするかと同じ判断になります。

## まとめ

- ツール呼び出しでは、モデルは**呼び出しの依頼（`tool_use`）を返すだけ**。実行して `tool_result` を返すのはアプリケーション
- クライアントツールは**アプリケーションの中で**実行される。`bash` を与えれば、そのマシンでコマンドが動く
- 必須の入力が足りないと、モデルによっては**推測で埋める**ことがある。破壊的なツールは推測させない設計にする
- **MCP** は、ツールや文脈のつなぎ方をそろえるオープンなプロトコル。ホストはサーバーごとにクライアントを作る
- サーバーが出すのは**ツール・リソース・プロンプト**。トランスポートは **stdio** と **Streamable HTTP**
- 仕様は、操作とデータの共有への**明示的な同意**と、**ツールの説明を鵜呑みにしない**ことを求める。プロトコルでは強制できない
