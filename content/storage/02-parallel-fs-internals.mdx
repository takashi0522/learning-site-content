## 部品と役割

AI 基盤コース レッスン 7 では、並列ファイルシステムが**メタデータとデータの経路を分ける**ことと、ストライピングの基本を見ました。このレッスンでは、Lustre の運用マニュアルを読みながら、その中身に入ります。

| 部品 | 役割（マニュアルの説明） |
| --- | --- |
| **MDS** / **MDT** | 名前とディレクトリを管理するサーバーと、その記憶装置。ファイル名・ディレクトリ・権限・**ファイルのレイアウト**を持つ。ファイルシステムには少なくとも 1 つの MDT があり、ルートディレクトリを持つ |
| **OSS** / **OST** | ファイルの中身の読み書きを受け持つサーバーと、その記憶装置。マニュアルは、1 台の OSS がふつう 2〜8 個の OST を受け持つと書いている |
| **クライアント** | 計算ノードなど。メタデータ用の MDC と、**OST ごとに 1 つ**のオブジェクト用クライアント（OSC）を持つ |

マニュアルは、ファイルシステム全体の帯域を次のように説明しています。

- ディスクの帯域は、OST の帯域の合計（ただしネットワークの帯域が上限）
- 全体の帯域は、**ディスクの帯域とネットワークの帯域の小さいほう**
- 容量は、OST の空きの合計

つまり、**OST を足せば容量も帯域も増える**のが基本の形です。

## 1 つのファイルの正体

<Figure name="lustre-file-layout" caption="ファイルは、MDT のオブジェクト 1 つと、OST のオブジェクト N 個でできている" source="Lustre Operations Manual 1.3 を元に作図。OST の数と 1MB は説明のための例" />

マニュアルによると、Lustre はファイルを **FID**（File IDentifier）で識別します。ローカルのファイルシステムの inode 番号に当たるもので、128 ビットの値です。MDT と OST をまたいで一意になるように作られています。

ファイルの中身がどこにあるかは、MDT のオブジェクトの**レイアウト**（layout EA と呼ばれる拡張属性）に書かれています。通常のファイルなら、MDT のオブジェクトは **1〜N 個の OST のオブジェクト**を指します。

- 1 個なら、中身は全部その 1 つのオブジェクトにある
- 2 個以上なら、中身は RAID 0 のように分けて置かれ、オブジェクトはそれぞれ別の OST にある

読み書きするとき、クライアントは**まず MDT からレイアウトを受け取り**、そのあとは**OSS と直接やり取り**します。中身の読み書きに MDS は関わりません。

## 同じファイルに、複数のノードから書ける

マニュアルは、クライアントから見ると**単一で、一貫した、同期された名前空間**が見えると書いています。そして、**複数のクライアントが同じファイルの別々の部分に同時に書き込み、同時に別のクライアントがそのファイルを読める**としています。

これを支えているのがロックです。Lustre には分散ロックマネージャ（LDLM）があり、OST のオブジェクトの**範囲（extent）ごとのロック**で、読み書き・ファイルサイズの取得・切り詰めを守ります（マニュアルの用語集）。

マニュアルは、この LDLM がファイルシステムのすべてのクライアントとサーバーのあいだでファイルの一貫性を保つと書いています。レッスン 1 の NFS は、nfs(5) のとおり close-to-open という弱い約束にとどめ、開いたままのクライアントには新しい中身を保証しませんでした。2 つの出典を並べると、Lustre はロックで同時のアクセスをそろえる側の設計だと言えます。複数のノードから 1 つの大きなファイルに書く使い方ができるのは、このためです。

<Callout type="note" title="応答しないクライアントは追い出される">

用語集によると、クライアントがサーバーの要求にタイムアウトまで応答しないと、サーバーはそのクライアントの状態を消します（**eviction**）。追い出されたクライアントは、そのサーバーに関わるキャッシュを捨てる必要があります。ロックを持ったまま応答しないクライアントのせいで、ほかのクライアントが待ち続けないための仕組みです。

</Callout>

## メタデータは 1 か所に集まりやすい

中身の読み書きは OST の台数ぶん並列になります。一方で、名前とレイアウトを持つのは MDT なので、ファイルを**作る・開く・属性を見る・消す**といった操作は MDS に向かいます（ここまでの構造から言えること）。ファイルの数が多いと、MDS が先に詰まりやすくなります。

マニュアルは、MDT を複数にする仕組み（**DNE**）を説明しています。

| 方式 | 何を分けるか |
| --- | --- |
| リモートディレクトリ（DNE1） | **サブディレクトリの木**を、別の MDT に受け持たせる。木ごとにメタデータの性能を足せるうえ、ある木の負荷がほかの木に響かない |
| ストライプディレクトリ（DNE2、Lustre 2.8 以降） | **1 つのディレクトリ**を、複数の MDT で受け持つ |

クライアントには、複数の MDT にまたがるディレクトリの木も、1 つの名前空間として見えます。

## 小さいファイルを MDT に置く — DoM

小さいファイルは、メタデータの操作のわりに中身が少なく、OST にとっても細かいランダムな I/O になります。Lustre 2.11 で入った **DoM**（Data on MDT）は、**小さいファイルの中身を MDT に直接置きます**。マニュアルは、小さいファイルの I/O が速くなるだけでなく、**大きなファイルの連続した I/O が小さなランダム I/O に邪魔されなくなる**としています。

DoM はファイルの先頭の範囲を MDT に置く設定です。それより先をどこに置くかを書かないと、書けなくなります。マニュアルの例です。

```bash
$ lfs setstripe -E 1M -L mdt /mnt/testfs/domdir
$ dd if=/dev/zero of=/mnt/testfs/domdir/testfile bs=1M
dd: error writing '/myth/tmp/pfl-mdt-only': No data available
2+0 records in
1+0 records out
1048576 bytes (1.0 MB, 1.0 MiB) copied, 0.00186441 s, 562 MB/s
```

1 MB を書いたところで `No data available`（`ENODATA`）で止まっています（エラーのパスはマニュアルの例のまま）。**ファイルの終わり（eof）までを覆うコンポーネント**が無いためで、マニュアルは次のように OST のコンポーネントを足す例を示しています。

```bash
lfs setstripe -E 1M -L mdt -E 1G -c1 -E eof -c4 /mnt/testfs/domdir
```

## ファイルの前と後ろで分け方を変える — PFL

上の 2 つ目のコマンドは、**PFL**（Progressive File Layout）の書き方です。1 つのファイルを範囲ごとの**コンポーネント**に分け、それぞれに別のレイアウトを付けます。

<Figure name="pfl-components" caption="範囲ごとに置き場所と分け方を変える。小さいファイルは先頭だけで終わる" source="Lustre Operations Manual 19.5 と 20 章の例を元に作図" />

マニュアルによると、PFL の狙いは、**利用者がファイルの大きさや同時に書く数を前もって知らなくても**、そこそこの性能が出るようにすることです。AI 基盤コース レッスン 7 で見たとおり、`stripe_count` の既定は 1 です（既定値はファイルシステムごとに設定され、ディレクトリやファイルの単位でも変えられる）。既定のままなら、大きなファイルも 1 つの OST にしか書かれません。PFL なら、ファイルが大きくなった部分だけを多くの OST に分けられます。

## 容量が余っているのに、書けない

マニュアルの 23 章に、偏ったファイルシステムの例が載っています。

```bash
client# lfs df -h
UUID                  bytes   Used  Available  Use%  Mounted on
testfs-MDT0000_UUID    4.4G 214.5M       3.9G    4%  /mnt/testfs[MDT:0]
testfs-OST0000_UUID    2.0G 751.3M       1.1G   37%  /mnt/testfs[OST:0]
testfs-OST0001_UUID    2.0G 755.3M       1.1G   37%  /mnt/testfs[OST:1]
testfs-OST0002_UUID    2.0G   1.7G     155.1M   86%  /mnt/testfs[OST:2]
testfs-OST0003_UUID    2.0G 751.3M       1.1G   37%  /mnt/testfs[OST:3]
testfs-OST0004_UUID    2.0G 747.3M       1.1G   37%  /mnt/testfs[OST:4]
testfs-OST0005_UUID    2.0G 743.3M       1.1G   36%  /mnt/testfs[OST:5]

filesystem summary:   11.8G   5.4G       5.8G   45%  /mnt/testfs
```

全体では **45%** しか使っていません。それでも、この状態で全 OST に分けて書こうとすると、マニュアルの例では次のように失敗します。

```bash
client# dd if=/dev/zero of=/mnt/testfs/test_3 bs=10M count=100
dd: writing '/mnt/testfs/test_3': No space left on device
```

---

<h2 className="slide-cont">容量が余っているのに、書けない（続き）</h2>

原因は **OST0002 だけが 86%** まで埋まっていることです。ファイルは OST に分けて置かれるので、**1 つの OST が満杯になれば、そこに置かれる部分が書けません**。全体の `df` だけを見ていると気づけません。

マニュアルによると、こうした偏りは、ストライプの設定の誤りや、全 OST に分けずに作った非常に大きなファイルで起きることが多いとされています。MDS は新しいファイルを満杯の OST に置くのをふつう自動で避けますが、**すでにその OST にあるファイルに書き足すとエラーになります**。

`lfs df` は、行の最後に OST や MDT の状態を出すことがあります。

| 表示 | 意味（マニュアル） |
| --- | --- |
| `D` | 劣化（RAID のディスクが故障、または再構築中）。新しい割り当てでは避けられる |
| `R` | 読み取り専用（ファイルシステムの破損を検出） |
| `S` | 空き容量が最低限を下回り、新しい割り当てに使われない |
| `I` | 空き inode が最低限を下回り、新しい割り当てに使われない |

ファイルの数で詰まっていないかは、`lfs df -i` で見ます。

## まとめ

- Lustre は、**MDS / MDT** が名前とレイアウトを、**OSS / OST** が中身を受け持つ。OST を足せば容量も帯域も増える
- ファイルは、**MDT のオブジェクト 1 つ（FID とレイアウト）**と、**OST のオブジェクト 1〜N 個**でできている。クライアントはレイアウトを受け取ってから OST と直接やり取りする
- 範囲ごとのロック（LDLM）があり、複数のクライアントが同じファイルの別々の部分に同時に書ける。マニュアルは、LDLM がファイルの一貫性を保つとしている
- 作る・開く・属性を見るはすべて MDS を通るので、ファイルが多いと MDS が先に詰まる。**DNE** で MDT を増やせる
- **DoM** は小さいファイルを MDT に置き、**PFL** はファイルの範囲ごとにレイアウトを変える。DoM で終わりまでを覆わないと `ENODATA` で書けなくなる
- 全体の使用率が低くても、**1 つの OST が満杯なら書けない**。`lfs df` で OST ごとに見る
