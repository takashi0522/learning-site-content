## キーと値を、HTTP で出し入れする

オブジェクトストレージは、**キー（名前）と値（中身）の組**を、HTTP の API で出し入れするストレージです。代表が Amazon S3 で、オンプレでも S3 と同じ形の API を持つ製品が多く使われます（たとえば Ceph の Object Gateway は、S3 の API の基本的なデータアクセスのモデルと互換だとしています）。このレッスンでは、S3 のドキュメントを例にします。

<Figure name="file-vs-object" caption="ファイルは木と途中からの読み書き。オブジェクトは平らなキーと丸ごとの出し入れ" source="Amazon S3 User Guide を元に作図" />

S3 のドキュメントによると、オブジェクトは**キー・バージョン ID・値・メタデータ**でできていて、**バケット**という入れ物に入ります。1 つのオブジェクトは、ドキュメントの表記で最大 50 TB（正確には 48.8 TiB）です（2026 年 10 月時点）。

---

## ディレクトリは無い — プレフィックス

S3 のキーは平らな文字列です。`train/shard-0001.tar` の `/` は、ディレクトリの区切りではありません。ドキュメントは、キーの先頭の文字列を**プレフィックス**と呼び、ディレクトリのように整理する手段として使えるが、**プレフィックスはディレクトリではない**と書いています。

一覧を取るときに、プレフィックスと区切り文字（`/` がよく使われる）を指定すると、1 つの階層だけを見るような一覧が返ります。木構造は、キーの名前の付け方と一覧の API で**見せているだけ**です。

一覧の API（`ListObjectsV2`）は、**1 回の要求で最大 1,000 個**のキーを返します。数千万個のオブジェクトを一覧するには、続きを指定して何万回も要求することになります。ファイルシステムの `ls` の感覚で「全部の一覧を取ってから処理する」と、それだけで時間がかかります。

## 整合性の約束

S3 のドキュメントは、整合性について次のように書いています。

| 約束 | 内容 |
| --- | --- |
| **書いたら読める** | PUT と DELETE は、すべてのリージョンで**強い read-after-write の一貫性**を持つ。PUT が成功を返したあとに始めた読み取り（GET や一覧）は、書いた内容を返す |
| **1 つのキーの更新は原子的** | あるキーを PUT している最中に別のスレッドが GET しても、返るのは古いデータか新しいデータのどちらかで、**途中まで書かれたデータや壊れたデータにはならない** |
| **同時に書く人のためのロックは無い** | 同じキーに 2 つの PUT が同時に来たら、**タイムスタンプが新しいほうが勝つ**。困るならアプリケーションの側でロックの仕組みを作る |
| **キーをまたぐ原子的な更新は無い** | あるキーの更新を、別のキーの更新に連動させることはできない |

レッスン 1 の NFS（close-to-open）やレッスン 2 の Lustre（範囲ごとのロック）と比べると、S3 は**キー単位で丸ごと入れ替える**ことだけを強く約束していて、**同時に書く人どうしの調整はしない**、という立場です。

<Callout type="pitfall" title="複数のファイルを「一度に」更新したつもりでも">

チェックポイントのように、複数のオブジェクト（重みのシャード、設定、状態）で 1 組になるものを書き換えるとき、S3 は**組全体を一度に入れ替える**ことを約束しません。読む側が、途中までしか入れ替わっていない組を読む可能性があります。たとえば、新しい組は別のプレフィックス（`step-1000/` のような）に書き、全部そろってから「どれが最新か」を指す小さなオブジェクトを最後に更新する、といった工夫をアプリケーションの側で行います（ドキュメントの言う「アプリケーションの側で作る」の一例）。

</Callout>

## 大きなオブジェクトは分けて送る

S3 には、1 つのオブジェクトを**部分（パート）に分けて送る**マルチパートアップロードがあります。ドキュメントは、オブジェクトが **100 MB** に達したら、1 回で送る代わりにマルチパートを検討するよう書いています。

| 項目 | S3 の上限（2026 年 10 月時点のドキュメント） |
| --- | --- |
| パートの大きさ | 5 MiB〜5 GiB（最後のパートには最小値が無い） |
| パートの数 | 最大 10,000 |
| オブジェクトの大きさ | 最大 48.8 TiB（10,000 × 5 GiB で決まる） |

ドキュメントによると、パートは**それぞれ独立に、どの順番でも**送れ、並列に送ることで帯域を有効に使えます。数十 GB のチェックポイントをオブジェクトストレージに置くときに効くのは、この仕組みです。

---

## 速さは「並列」で出す

S3 のパフォーマンスのドキュメントは、次のように書いています。

- **パーティションされたプレフィックス 1 つあたり**、少なくとも毎秒 3,500 回の書き込み系（PUT / COPY / POST / DELETE）と、5,500 回の読み取り系（GET / HEAD）の要求をさばける
- プレフィックスの数に上限は無く、**プレフィックスを分けて並列にすれば**それだけ伸びる（10 個に分ければ読み取りで毎秒 55,000 回）
- 伸びるのは徐々にで、その間は 503（Slow Down）が返ることがある
- 小さいオブジェクトのレイテンシは、おおむね 100〜200 ミリ秒

数字は Amazon S3 のものです。オンプレの S3 互換ストレージでは、製品と構成で変わります。それでも、**1 回の要求は遅いが、並列にすれば全体の帯域は出る**という性質は、HTTP の要求を単位にする以上、共通して考えておくべき点です。

小さいファイルを 1 つずつ順番に取りに行く読み方は、1 回ごとのレイテンシがそのまま積み上がります。AI 基盤コース レッスン 4 で見た「小さいファイルをシャードにまとめる」は、オブジェクトストレージでいっそう効きます。

## ファイルとしてマウントすると、何ができないか

オブジェクトストレージを、ファイルシステムのようにマウントする道具もあります。AWS の **Mountpoint for Amazon S3** は、その動きを細かく文書にしています。

Mountpoint のドキュメントは、**S3 のオブジェクト API で効率よく実現できない操作は提供しない**、そして POSIX の要求とぶつかるときは、**黙って受け付けるより早めに明示的に失敗させる**、という方針を書いています。具体的には次のとおりです（汎用バケットの場合）。

| 操作 | Mountpoint での扱い |
| --- | --- |
| 新しいファイルを書く | できる。ただし**先頭から順番に**書く。書いている途中のファイルは、書いているアプリケーションが閉じるまで読めない。ほかの S3 クライアントに見えるのはアップロードが終わってから |
| 既存のファイルの途中を書き換える | できない。上書きは起動時のフラグと `O_TRUNC` を付けた丸ごとの置き換えだけ |
| 名前の変更（`rename`） | 汎用バケットではできない（多数の API 呼び出しが要るため） |
| `chmod` / `chown` | できない。所有者と権限は起動時に決めた値になる |
| 同じファイルに複数のノードから書く | 調整されない。ドキュメントは、複数のインスタンスから同時に同じオブジェクトに書かないよう書いている |

<h2 className="slide-cont">ファイルとしてマウントすると（続き）</h2>

<Callout type="field" title="「マウントできたのに動かない」">

学習のコードやライブラリには、ファイルに**追記する**、一時ファイルに書いてから**名前を変えて置き換える**、といった書き方をするものがあります。こうしたコードは、オブジェクトストレージをマウントした場所では失敗します。Mountpoint のドキュメントは、高い読み取りの帯域が要る用途と、1 つのクライアントから新しいファイルを順番に書く用途に向けて作られていると書いています。

**読むのはマウント、書くのはローカルか共有ファイルシステムに書いてから API で送る**、のように役割を分けると、こうした制約にぶつかりにくくなります。

</Callout>

## まとめ

- オブジェクトストレージは、**キーと値を HTTP の API で出し入れする**。S3 の API と互換の製品がオンプレにもある
- キーは平らな文字列で、**プレフィックスはディレクトリではない**。一覧は 1 回あたり最大 1,000 個
- S3 は、**書いたら読める**一貫性と、**1 つのキーの丸ごとの入れ替え**を約束する。同時に書く人どうしのロックや、キーをまたぐ原子的な更新は無い
- 大きなオブジェクトは**マルチパート**で分けて並列に送る（パートは最大 10,000、最大 48.8 TiB）
- 速さは**プレフィックスを分けた並列**で出す。1 回の要求のレイテンシは大きい
- ファイルとしてマウントしても POSIX ではない。**追記・途中の書き換え・名前の変更**ができない場合がある
