## 「速い」には 3 つの意味がある

「このストレージは速い」と言うとき、指しているものは少なくとも 3 つあります。

<Figure name="storage-perf-axes" caption="帯域・IOPS・メタデータは別の性能で、測る道具も違う" source="道具と単位は fio・IOR・mdtest の各ドキュメントから。効く場面はこのコースの見立て" />

| 性能 | 何を数えるか | 主な道具 |
| --- | --- | --- |
| **帯域** | 1 秒に何バイト読み書きできるか | IOR、fio |
| **IOPS** | 1 秒に何回の I/O をこなせるか（小さな I/O で効く） | fio |
| **メタデータ** | 1 秒にファイルを何個作り・属性を見て・消せるか | mdtest |

3 つは連動しません。大きなファイルで数十 GB/s 出るストレージが、小さいファイルを数千万個作る負荷では詰まる、ということは普通に起きます（レッスン 2 の MDS の話）。**どの性能が足りないのかを先に決めてから測る**のが出発点です。

IOR のドキュメントによると、IOR は並列ストレージの性能を、さまざまなインターフェースとアクセスのパターンで測るためのベンチマークです。同じリポジトリに、メタデータの最大の速さを測る mdtest が入っています。どちらも MPI で複数のプロセスの足並みをそろえます。

## fio — 1 台で、負荷の形を指定して測る

fio は、**負荷の形をオプションで細かく指定して** I/O を発生させる道具です。

```bash
fio --name=randread --rw=randread --bs=4k --size=4g \
    --ioengine=libaio --iodepth=32 --direct=1 \
    --numjobs=4 --runtime=60 --time_based --group_reporting \
    --directory=/mnt/data/fio-test
```

| オプション | 意味（fio のドキュメント） |
| --- | --- |
| `rw` | I/O の形。`read`（順番に読む）、`randread`（ランダムに読む）、`write`、`randwrite` など |
| `bs` | 1 回の I/O の大きさ |
| `iodepth` | 同時に投げておく I/O の数。既定は 1 |
| `direct` | `1` でバッファを通さない I/O（多くは `O_DIRECT`）。既定は `false` |
| `numjobs` | 同じ仕事をするプロセス（またはスレッド）の数。既定は 1 |
| `runtime` / `time_based` | 実行時間の上限 / 読み終えても時間いっぱい繰り返す |
| `end_fsync` | 書き込みの段の最後に `fsync` する。既定は `false` |

---

<h2 className="slide-cont">fio（続き）</h2>

<Callout type="pitfall" title="iodepth を上げても、深くならないことがある">

fio のドキュメントは、`iodepth` を 1 より大きくしても**同期の I/O エンジンでは基本的に効かない**こと、そして Linux で `libaio` を使っても **`direct=1` を付けないとバッファ付きの I/O は非同期にならない**ため、狙った深さにならないことがある、と書いています。出力の `IO depths` の分布で、**実際にどの深さで動いたか**を確かめるよう勧めています。

</Callout>

`direct` の既定は `false` なので、何も付けなければ**ページキャッシュを通した I/O**を測ることになります。これが次のスライド以降の主題です。

## fio の出力を読む — 平均ではなく分布を見る

fio のドキュメントに載っている、書き込みのジョブの出力の例です（一部を抜粋）。

```text
  write: IOPS=88, BW=623KiB/s (638kB/s)(30.4MiB/50032msec)
    slat (nsec): min=500, max=145500, avg=8318.00, stdev=4781.50
    clat (usec): min=170, max=78367, avg=4019.02, stdev=8293.31
     lat (usec): min=174, max=78375, avg=4027.34, stdev=8291.79
    clat percentiles (usec):
     |  1.00th=[  302],  5.00th=[  326], 10.00th=[  343], 20.00th=[  363],
     | 30.00th=[  392], 40.00th=[  404], 50.00th=[  416], 60.00th=[  445],
     | 70.00th=[  816], 80.00th=[ 6718], 90.00th=[12911], 95.00th=[21627],
     | 99.00th=[43779], 99.50th=[51643], 99.90th=[68682], 99.95th=[72877],
  IO depths    : 1=85.0%, 2=13.1%, 4=1.8%, 8=0.1%, 16=0.0%, 32=0.0%, >=64=0.0%
```

- **`slat` / `clat` / `lat`**: 投げるまで / 投げてから終わるまで / 全体（`slat` と `clat` の和）
- **`clat percentiles`**: 完了までの時間の分布。**半分（50th）は 0.416 ms で終わっている**のに、**99th は 43.8 ms**。平均（`avg=4019`、約 4 ms）は、どちらの実態も表していない
- **`IO depths`**: 実際の深さの分布。この例では 85% が深さ 1 で動いている

学習のジョブは、遅い 1% の I/O を待たされることがあります。**平均ではなく、99th などの裾**を見ます。

## 測っているのは、ストレージか、メモリか

IOR のチュートリアルは、4 ノード・64 プロセスで Lustre を測る例で、ページキャッシュに数字が化かされる様子を順に見せています。

| 実行 | 書き込み（MiB/s） | 読み取り（MiB/s） | 何が起きているか |
| --- | --- | --- | --- |
| ① `-t 1m -b 16m -s 16`（共有の 1 ファイル） | 427 | 239 | 全プロセスが 1 つのファイルに書き、**ロックの取り合い**になっている |
| ② ①＋ `-F`（プロセスごとに別のファイル） | 33,645 | **149,473** | 読み取りは**直前に書いた中身がメモリに残っていて**、それを読んでいる |
| ③ ②＋ `-C`（隣のノードが書いたものを読む） | 41,326 | 3,310 | 読み取りは本物に近い。書き込みはまだメモリに書いて返っている |
| ④ ③＋ `-e`（書いたあと `fsync`） | **2,938** | **2,713** | ようやく、信じられる値 |

チュートリアルは、②の読み取り約 146 GB/s が本物なら、**4 台の計算ノードがそれぞれ 45 GB/s 超のネットワーク**を持っていなければならない、と指摘しています。数字が物理的にありえるかを、**ネットワークの帯域と突き合わせる**のが最初の確認です。

---

<h2 className="slide-cont">測っているのは、ストレージか、メモリか（続き）</h2>

チュートリアルが説明する仕組みは、Linux コース レッスン 3・4 で見たページキャッシュそのものです。

- 書き込みは、**メモリ上のファイルのコピー**に書かれた時点で終わる。ストレージへはあとからカーネルが書き出す
- 書き出したあとも、中身はメモリに残る。直後に読めば、ストレージに聞かずにメモリから返る

チュートリアルが挙げる避け方は次のとおりです。

| 何を測るとき | 避け方 |
| --- | --- |
| 書き込み | `fsync` までの時間を含める（IOR の `-e`）か、`O_DIRECT` でキャッシュを通さない |
| 読み取り | **自分が書いていないデータ**を読む（IOR の `-C` は隣のノードが書いた分を読ませる。ページキャッシュはノードをまたいで共有されないため） |
| 読み取り（root が使えるとき） | 測る前に `echo 1 > /proc/sys/vm/drop_caches` でページキャッシュを空にする |

チュートリアルはまた、IOR が作る負荷は**最大の性能を見せるためのもの**で、実際のアプリケーションの負荷を表すわけではない、とも書いています。

## mdtest — メタデータを測る

mdtest は、各 MPI プロセスが決めた数のディレクトリやファイルを**作り、属性を見て（stat）、消し**、それぞれの 1 秒あたりの回数を測ります。最後に、操作ごとに最大・最小・平均と標準偏差を出します（mdtest(1)。man ページは 1.8.3 版のもので、現在は IOR のリポジトリに入っています）。

```bash
mpirun -n 64 mdtest -n 10000 -u -F -d /mnt/lustre/mdtest
```

| オプション | 意味 |
| --- | --- |
| `-n` | 各プロセスが作る・見る・消す数 |
| `-u` | プロセスごとに別の作業ディレクトリを作る |
| `-F` / `-D` | ファイルだけ / ディレクトリだけで試す |
| `-w` / `-e` | 作ったファイルに書く / 読むバイト数（既定は 0） |

`-u` は、**1 つのディレクトリに全員で作る**か、**各自のディレクトリに作る**かを切り替えます。これは負荷の形そのものの違いで、次のスライドの IO500 も、この 2 つを easy と hard として別々に測っています。レッスン 2 の DNE で見たとおり、メタデータをどう分けて受け持つかとも関わります。

## ベンダーの数字は「どの負荷か」で読む

IO500 は、ストレージの性能を比べるためのベンチマークの組で（以下は 2026 年 10 月時点の About ページの説明）、**易しい負荷と難しい負荷**を分けて測ります。

| 区分 | 負荷（IO500 の説明） |
| --- | --- |
| ior-easy | 各プロセスが**自分のファイル 1 つ**に、最大の速さで書く・読む |
| ior-hard | **共有の 1 ファイル**に、47,008 バイトの記録を交互に書く・読む |
| mdtest-easy | 各プロセスが**自分のディレクトリ**に、0 バイトのファイルを作る・stat・消す |
| mdtest-hard | **共有の 1 ディレクトリ**に、3,901 バイトのファイルを作る・stat・読む・消す |

どの負荷も、読むのは**別のノードのプロセスが書いたデータ**です。前のスライドのキャッシュの罠を、ルールで避けています。

<Callout type="field" title="カタログの「◯◯ GB/s」を見たら">

その数字が easy と hard のどちらの形か、読み取りは自分が書いたデータか、書き込みは `fsync` まで含むか、ノード数とネットワークは何か、を確かめます。自分たちの学習が「大きなファイルを各自で読む」のか「小さいファイルを大量に開く」のかで、見るべき行が変わります。

</Callout>

## まとめ

- 「速い」には、**帯域・IOPS・メタデータ**の 3 つがある。道具は IOR / fio / mdtest と分かれる
- fio は負荷の形をオプションで決める。`direct` の既定は `false` で、`iodepth` は条件しだいで効かない。出力の `IO depths` で実際の深さを確かめる
- レイテンシは**平均ではなく分布（99th など）**で見る
- ベンチマークは、気をつけないと**ページキャッシュ（メモリ）を測る**。書き込みは `fsync` まで含め、読み取りは自分が書いていないデータを読む
- 結果が**ネットワークの帯域を超えていないか**を最初に確かめる
- mdtest はメタデータの操作を数える。1 つのディレクトリか、各自のディレクトリかで結果が変わる
- ベンダーの数字は、**easy と hard のどちらの負荷か**で読む
