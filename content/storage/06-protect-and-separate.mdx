## 冗長は、何から守っているか

レッスン 5 の 3 コピーやイレイジャーコーディングは、**ディスクやサーバーが壊れても**データを失わないための仕組みです。しかし、利用者が `rm` したり、壊れたデータで上書きしたりする操作は、正しい操作として**すべてのコピーに同じように反映されます**。冗長は、誤った操作からは守ってくれません。

<Figure name="protection-layers" caption="何が起きるかによって、守る手段が違う" source="このコースの整理。各手段の性質は本文の出典による" />

S3 のバージョニングのドキュメントが、バージョニングの目的を「意図しない利用者の操作とアプリケーションの障害から復旧しやすくする」と書いているのは、この差を埋めるためです。このレッスンでは、図の下の 3 段を順に見ます。

## スナップショット — ある時点に戻る

**スナップショット**は、ある時点の状態を読み取り専用で残したものです。Ceph の 2 つの例を見ます。

| | RBD（ブロック） | CephFS（ファイル） |
| --- | --- | --- |
| 作り方 | `rbd` コマンドや QEMU・libvirt・OpenStack などから | ディレクトリの下の隠しディレクトリ `.snap` に `mkdir` する（例: `mkdir /1/2/3/.snap/my-snapshot-name`） |
| 消し方 | `rbd` コマンド | `.snap` の下で `rmdir`。スナップショットを持つディレクトリは、先にスナップショットを消さないと消せない |

<Callout type="pitfall" title="ブロックのスナップショットは「クラッシュ整合」">

RBD のドキュメントによると、RBD はイメージの中のファイルシステムを知らないので、スナップショットは、マウントしている OS 側と調整しない限り**クラッシュ整合（電源を抜いた瞬間と同じ状態）**にとどまります。ドキュメントは、スナップショットの前に I/O を止めるよう勧めています。止めずに取ったスナップショットは、マウントし直す前に `fsck` が要ることがあります。`fsfreeze` でファイルシステムを凍結するか、仮想マシンなら `qemu-guest-agent` で自動的に凍結できます。

</Callout>

RBD のドキュメントは、スナップショットを使うには**動いている Ceph クラスタが必要**だとも書いています。ここから、クラスタそのものを失う事態に備えるには、スナップショットとは別に、別の場所へのコピーが要ると考えられます（この部分はドキュメントの記述からの推論です）。

---

## バージョニングと、消せない保存（WORM）

オブジェクトストレージでは、**バージョニング**がスナップショットに近い役割を持ちます。S3 のドキュメントによると次のとおりです。

- 既定では**無効**で、明示的に有効にする
- 有効にすると、削除しても本当には消さず、**削除マーカー**を置く。上書きすると、新しいバージョンができる。前のバージョンにいつでも戻せる
- **各バージョンはオブジェクトの丸ごとのコピー**で、差分ではない。3 つのバージョンがあれば、3 つ分の容量として課金される

チェックポイントを同じキーで何度も上書きすると、バージョンの数だけ容量が増えていきます。古いバージョンをいつ消すか（S3 なら Lifecycle の設定）も一緒に決めます。

さらに強い保護が **S3 Object Lock** です。WORM（write-once-read-many）のモデルで、決めた期間または無期限、オブジェクトのバージョンを**削除も上書きもできなく**します。バージョニングを有効にしたバケットでしか使えません。

| モード | ドキュメントの説明 |
| --- | --- |
| **governance** | 特別な権限を持たない利用者は、消すことも設定を変えることもできない。権限を与えた人は変えられる |
| **compliance** | **AWS アカウントの root を含め、どの利用者も**上書き・削除できない。保持期間も短くできない（保持期限より前に消す唯一の方法は、AWS アカウントそのものを削除すること） |

管理者の権限ごと乗っ取られる事態まで考えるなら、compliance のように「管理者でも消せない」保存が意味を持ちます。

## クォータ — 上限を決める

1 つのファイルシステムを複数のチームで使うとき、まず要るのが**クォータ**（使ってよい量の上限）です。製品ごとに、上限の掛け方と精度が違います。

**XFS** は、利用者やグループに加えて、**プロジェクトクォータ**でディレクトリの木ごとに上限を掛けられます。xfs_quota(8) の例です。

```bash
mount -o prjquota /dev/xvm/var /var
xfs_quota -x -c 'project -s -p /var/log 42' /var
xfs_quota -x -c 'limit -p bhard=1g 42' /var
```

木の中のファイルにプロジェクト番号を付け、その番号に上限（ここでは 1 GB）を掛けます。

---

<h2 className="slide-cont">クォータ — 上限を決める（続き）</h2>

**CephFS** は、ディレクトリの拡張属性で上限を掛けます（`ceph.quota.max_bytes` と `ceph.quota.max_files`）。ただしドキュメントは、制限を 2 つ明記しています。

- **協力的（cooperative）**: 上限で書き込みを止めるのは、マウントしている**クライアントの協力**による。改造されたクライアントや悪意のあるクライアントは止められない
- **厳密ではない（imprecise）**: 上限を超えてから少しして止まる。どれだけ超えるかは主に時間で決まり、一般に**上限を超えてから数十秒のうち**に止まる

**Lustre** のクォータも分散していて、マニュアルによると、最小の単位は **1 MB** で、正確な値は**静止した状態のファイルシステムでしか**計算できない、とされています。

<Callout type="field" title="クォータを「容量の保証」と読まない">

クォータは、使いすぎを抑えるための仕組みです。CephFS のドキュメントは、利用者を全く信頼できない環境では、クォータだけに頼ってシステムが満杯になるのを防ごうとしないよう書いています。クォータとは別に、**全体の空き**も監視します（レッスン 2 の OST や、レッスン 5 の OSD のように、1 か所が満杯になるだけで書き込みが止まりうる）。

</Callout>

## チームを分ける — ID の衝突

レッスン 1 で見たとおり、NFS では uid の**番号**がそのまま届きます。別々に管理されてきたクラスタや組織が 1 つのファイルシステムを共有すると、**同じ番号が別の人を指す**ことが起きます。

Lustre のマニュアルの 28 章は、この問題への仕組みとして **nodemap** を説明しています。

- クライアントの**ネットワーク上の識別子（NID）の範囲**ごとにポリシーのグループを作り、そのグループから来た uid / gid を、ファイルシステムの側の uid / gid に**対応づけて**扱う
- 所有者・権限・クォータの情報は、POSIX のまま保たれる
- **どのグループにも入らない NID からのアクセスは、既定で nobody に置き換えられる**
- クライアントの側には特別な設定は要らない

マニュアルは、これによって、uid や gid がぶつかる複数のサイトが 1 つの Lustre を衝突なく使える、としています。マニュアルが root_squash との関係を述べているわけではありませんが、NFS の `root_squash`（レッスン 1）を全利用者の対応づけに広げたもの、と考えると覚えやすいでしょう。

## まとめ

- 冗長（レプリケーション・EC）は**ディスクの故障**から守る。削除や上書きは全コピーに届くので、**誤操作からは守らない**
- **スナップショット**はある時点に戻るためのもの。RBD のスナップショットは、I/O を止めないと**クラッシュ整合**にとどまる。使うには動いているクラスタが要るので、クラスタの喪失への備えは別に考える
- S3 の**バージョニング**は削除マーカーと旧バージョンで戻れるようにする。各バージョンは丸ごとのコピーで容量を食う。**Object Lock** の compliance は root でも消せない
- **クォータ**は製品で性質が違う。CephFS は協力的で厳密ではなく、Lustre は 1 MB 単位で正確な値は静止時のみ。全体の空きは別に監視する
- 複数の組織で共有するなら、uid の**衝突**に備える。Lustre の **nodemap** は NID の範囲ごとに ID を対応づけ、知らない NID は nobody にする
