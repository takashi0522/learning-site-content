## NFS は、ファイルの操作を要求にして送る

NFS のクライアントは、アプリケーションが呼んだ `open` や `read` や `stat` を、**サーバーへの要求（RPC）**に変えて送ります。名前からファイルを探す `LOOKUP`、属性を聞く `GETATTR`、中身を読み書きする `READ` と `WRITE` などです。

ただし、毎回送っていては遅すぎます。そこでクライアントは、**カーネルの中にキャッシュを持ち、当たればサーバーに聞かずに返します**。NFS の振る舞いの大半は、このキャッシュをいつ信じ、いつ捨てるかで説明できます。

<Figure name="nfs-client-caches" caption="NFS クライアントのキャッシュ。当たればサーバーに問い合わせずに返す" source="nfs(5) の DATA AND METADATA COHERENCE を元に作図" />

バージョンは、指定しなければ**クライアントがまず 4.2 を試し、サーバーが対応している版まで下げて**決まります（nfs(5)）。v3 ではロックを別のプロトコル（NLM と NSM）で扱っていましたが、v4 ではロックも本体のプロトコルに入りました。

## 3 種類のキャッシュ

nfs(5) の説明を、キャッシュごとに整理します。

| キャッシュ | 中身 | いつ捨てる・確かめるか |
| --- | --- | --- |
| **データ** | ファイルの中身（ページキャッシュ） | 書いたものは、`close`・`fsync`・ロックの操作・メモリの逼迫のどれかでサーバーへ送る |
| **属性** | サイズ・更新時刻（mtime）など | ファイルは既定で **3〜60 秒**、ディレクトリは **30〜60 秒**のあいだ、サーバーに確かめずに使う |
| **ディレクトリエントリ** | 名前 → ファイルの対応（`LOOKUP` の結果） | 親ディレクトリの属性の期限が切れるまで使う。「無かった」という結果も覚える |

属性の保持期間は `acregmin` / `acregmax`（ファイル）と `acdirmin` / `acdirmax`（ディレクトリ）で決まり、`actimeo` で 4 つをまとめて設定できます（既定値は、このレッスンで確認した man7.org 版の nfs(5) によるもの）。

ディレクトリエントリのキャッシュは、**「そのファイルは無い」という結果（negative）も覚えます**。nfs(5) によると、クライアントはディレクトリの mtime の変化を見てエントリを捨てますが、その mtime 自体がキャッシュされた属性なので、変化に気づくまで時間がかかることがあります。

## close-to-open — NFS が守る約束

NFS は、複数のクライアントのキャッシュを常に一致させることはしません。nfs(5) は、それを完全に保つのは高くつくので、**多くのファイル共有で足りる弱い整合性**にとどめている、と書いています。その中心が **close-to-open** です。

<Figure name="nfs-close-to-open" caption="A の close のあとに B が open すれば、新しい中身が見える" source="nfs(5) の Close-to-open cache consistency を元に作図" />

- **open のとき**: キャッシュした属性が新しくても、必ずサーバーに属性を確かめる
- **close のとき**: 手元に溜めていた書き込みをサーバーへ送る（書き込みのエラーは `close` の戻り値で返る）

つまり保証されるのは、**「A が書いて close → そのあと B が open して読む」という順番のときだけ**です。B がずっと開いたままなら、古い中身を読むことがあります。

<h2 className="slide-cont">close-to-open（続き）</h2>

<Callout type="field" title="「別のノードで作ったファイルが見えない」">

学習ジョブのノード A がファイルを作り、別のノード B が `ls` やループで「できたか」を確かめている、という使い方はよくあります。B のクライアントは、ディレクトリの属性とエントリをキャッシュしているので、**A が作ったファイルに、しばらく気づかないことがあります**。直前に「無い」と確かめていれば、その結果も覚えています。

nfs(5) が挙げる選択肢は次のとおりです。

- `lookupcache=positive`: 「無い」という結果は毎回確かめ直す
- `lookupcache=none`: エントリを毎回確かめる（その分、要求が増える）
- `noac`: 属性をキャッシュしない。書き込みも同期になり、**性能への影響が大きい**

nfs(5) は、`noac` に頼るよりファイルロックを使うことを勧めています。ジョブの完了は、ファイルの有無ではなくジョブ管理（スケジューラ）の側で受け渡すほうが確実です。

</Callout>

## 書いたデータは、いつサーバーに届くか

`write` が返っても、データはまだクライアントの中にあることがあります。nfs(5) によると、何も指定しなければ（または `async` なら）、クライアントは次のどれかが起きるまで送るのを遅らせます。

- メモリが逼迫した
- アプリケーションが `sync` / `msync` / `fsync` を呼んだ
- `close` した
- `fcntl` でロックを取った・外した

Linux コース レッスン 4 の「write は永続化ではない」は、NFS ではクライアントとサーバーの 2 段で起きます。

| 段 | 設定 | 意味 |
| --- | --- | --- |
| クライアント | マウントの `sync` | 書き込みのたびにサーバーへ送ってから返る。整合性は上がるが、**性能への影響が大きい** |
| サーバー | エクスポートの `sync`（既定） | 変更を安定した記憶装置に書いてから応答する |
| サーバー | エクスポートの `async` | 書く前に応答する。exports(5) は、これは**プロトコルに違反する**動作で、サーバーが異常終了すると**データが失われたり壊れたりしうる**と書いている |

exports(5) によると、`sync` が既定になったのは nfs-utils 1.0.0 より後の版からです。古い手順書やブログの `async` をそのまま写していないかは、確かめる価値があります。

## サーバーが応答しないとき — hard と soft

サーバーが止まったときの動きは、`hard` と `soft` で大きく変わります。

| | `hard`（既定） | `soft` / `softerr` |
| --- | --- | --- |
| 応答が無いとき | **いつまでも再送する** | `retrans` 回の再送のあとで諦め、`EIO`（`soft`）か `ETIMEDOUT`（`softerr`）を返す |
| アプリケーションから見ると | 応答が戻るまで待ち続ける | エラーが返ってくる |

TCP の場合、`timeo` の既定は 600（**60 秒**。単位は 0.1 秒）で、再送のたびに待ち時間を延ばします。`retrans` の既定は TCP で 2 回で、その回数を超えると「server not responding」というメッセージを出します。

`soft` は止まらずに済むので魅力的に見えます。しかし nfs(5) は、**`soft` のタイムアウトは場合によってデータを黙って壊しうる**と警告し、**データの完全性よりも応答性が大事なときだけ**使うよう書いています。

`hard` のマウントでサーバーが止まると、プロセスは待ち続けます。Linux コース レッスン 2 で見た、`kill -9` でも消えない `D` 状態は、この形で現れることがあります。原因はプロセスではなくサーバー側なので、まずサーバーとネットワークを見ます。

## 権限は uid の「番号」で届く

従来の NFS の認証（`sec=sys`）では、**利用者を uid と gid の番号で表して**送ります。nfs(5) によると、ファイルの中身もこの番号も、通常は暗号化されずにネットワークを流れます。

ここから 2 つのことが起きます。

- **ノードごとに uid がずれていると、所有者が別人になる**。ノード A で uid 1001 の人が作ったファイルは、ノード B で uid 1001 の別の人のものに見える。uid は全ノードでそろえる必要があり、認証基盤 / PKI コース レッスン 5 の LDAP 連携はそのための手段の 1 つ
- **root はそのままでは届かない**。exports(5) によると、既定では uid 0 からの要求を匿名の uid（既定で 65534）に置き換える（`root_squash`）。クライアントの root でも、サーバー上のファイルを自由には扱えない

番号ではなく本人であることを確かめたいときは、`sec=krb5` で Kerberos を使います。`krb5i` は改ざんの検出、`krb5p` は暗号化まで加えます。nfs(5) は、その分の性能への影響を見込むよう書いています。

## 遅いときにどこを見るか — nfsiostat

`nfsiostat` は、マウントごとの統計を出します（中身は `/proc/self/mountstats`）。`nfsiostat 5` のように間隔を付けると、2 回目以降は**その間隔のあいだの値**になります。1 回目はマウントしてからの累計です。

```bash
nfsiostat 5 /mnt/data
```

nfsiostat(8) が説明する列のうち、切り分けに効くのは次の 3 つです。

| 列 | 測っている区間 |
| --- | --- |
| `avg RTT (ms)` | カーネルが要求を送ってから、応答を受け取るまで |
| `avg exe (ms)` | 要求を作ってから完了するまで。**RTT を含む** |
| `avg queue (ms)` | 要求を作ってから、送り出すまで |

定義から言えるのは次のことです。読み方の目安として使います。

- **RTT が大きい**: 送ってから応答が返るまで（ネットワークの往復とサーバーでの処理）に時間がかかっている
- **RTT に比べて exe が大きい**: exe は RTT を含むので、その差は送る前の待ち（`avg queue`）などクライアント側の時間を含む
- **`retrans` が 0 でない**: 再送が起きている。nfs(5) の言う、`timeo` の時間内に応答が来なかった要求があったということ

`-a` で属性キャッシュの、`-d` でディレクトリ操作の統計も出せます。接続の本数を増やす `nconnect` や、RDMA で運ぶ `proto=rdma` は、AI 基盤コース レッスン 7 で扱いました。

## まとめ

- NFS クライアントは、操作を RPC に変えて送る。**データ・属性・ディレクトリエントリ**をキャッシュし、当たればサーバーに聞かない
- 属性は既定でファイル 3〜60 秒、ディレクトリ 30〜60 秒保持する。ディレクトリエントリは「無い」という結果も覚える
- 整合性の約束は **close-to-open**。A の close のあとに B が open したときだけ、新しい中身が見える
- 書いたデータは close や fsync までクライアントに留まりうる。サーバーの `async` はプロトコル違反で、異常終了でデータを失いうる
- 既定の **`hard`** は応答までいつまでも待つ。**`soft`** は止まらないが、データを黙って壊しうる
- `sec=sys` では uid の番号がそのまま届く。uid は全ノードでそろえる。root は既定で匿名に置き換わる
- `nfsiostat` の **RTT と exe の差**で、遅さがネットワーク・サーバー側か、クライアントの中かを切り分ける
