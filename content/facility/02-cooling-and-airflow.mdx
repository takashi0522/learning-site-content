## サーバーは前から吸って後ろに出す

ほぼすべてのラックマウントサーバーは、**前面から冷気を吸い、背面へ熱気を排出**します。データセンターの冷却設計は、この前提の上に成り立っています。

<Figure name="hot-cold-aisle" caption="ラックを背中合わせに並べるのは、熱気と冷気を混ぜないため" />

**ラックの前面同士、背面同士を向かい合わせる**ことで、冷気と熱気が混ざらない通路ができます。これがホットアイル / コールドアイル構成です。

<Callout type="pitfall" title="1 台向きを間違えるだけで壊れる">

ラックの向きを間違えて設置すると、**そのラックは隣のラックの排気を吸い込みます**。吸気温度が一気に 10℃ 以上上がり、そのラックだけが慢性的に高温になります。

同様に、**ネットワーク機器には背面吸気・前面排気（逆流）のモデルがあります**。スイッチをサーバーと同じラックに入れる場合、エアフローの向きが揃っているモデルを選ぶ必要があります。多くのスイッチには「front-to-back」「back-to-front」の型番違いが用意されています。

「このスイッチだけ異常に熱い」「スイッチの周辺のサーバーが熱い」場合、エアフローの向きを確認してください。

</Callout>

## 冷気を漏らさない 3 つの基本

冷却の問題の大半は、冷却能力そのものではなく**冷気が意図しない経路で回り込んでいる**ことが原因です。

### ① ブランクパネル

ラックの空きスロットを塞がないと、**背面の熱気が前面に回り込みます**。

<Figure name="blank-panel" caption="空きスロットがあると、背面の熱気が前面へ回り込む" />

**最も安価で効果の大きい対策**です。1 枚数百円〜数千円のパネルで、吸気温度が数℃ 変わります。

---

### ② ケーブルによる排気の妨害

背面にケーブルが密集していると、熱気が抜けません。特に配線を後から足していった結果、**ケーブルの束が排気口を塞いでいる**というのはよくあります（レッスン 3 で扱います）。

### ③ 床下・天井の開口

フリーアクセス床のケーブル通線口が開けっ放しだと、そこから冷気が漏れます。ブラシ付きのグロメットで塞ぎます。

---

<h2 className="slide-cont">冷気を漏らさない 3 つの基本（続き）</h2>

<Callout type="tip">

**封じ込め（containment）**は、通路そのものを物理的に仕切って冷気と熱気を完全に分離する手法です。

- **コールドアイル封じ込め** … 冷気の通路を囲う
- **ホットアイル封じ込め** … 熱気の通路を囲い、天井裏へ返す

冷却効率が大きく上がり、空調の設定温度を上げられる（= 電気代が下がる）ため、新設のデータセンターではほぼ標準です。既設でも、天板とドアを追加する形で後付けできる製品があります。

</Callout>

## 吸気温度を見る

サーバーの健全性を示す指標として、**吸気温度（Inlet Temperature）**は CPU 温度より重要です。CPU 温度は負荷によって変動しますが、吸気温度は**設置環境そのもの**を表します。

```bash
# BMC 経由で取得
ipmitool sdr type Temperature
```

```text
Inlet Temp       | 22 degrees C      | ok      ← これが環境の実態
Exhaust Temp     | 41 degrees C      | ok
CPU1 Temp        | 58 degrees C      | ok
```

ASHRAE（米国暖房冷凍空調学会）のガイドラインが業界標準として使われています。

| 吸気温度 | 区分 | 状態 |
| --- | --- | --- |
| 18–27℃ | **推奨範囲** | 正常 |
| 15–32℃ | 許容範囲（クラス A1） | 動作はするが、ファンが高回転になり消費電力が増える |
| 32℃ 超 | 範囲外 | **スロットリングと故障率上昇のリスク** |

---

<h2 className="slide-cont">吸気温度を見る（続き）</h2>

<Callout type="field">

**吸気温度を監視項目に入れてください。** CPU 温度だけを見ていると、環境の悪化に気づくのが遅れます。

```bash
# 全サーバーの吸気温度を集めて比較する（1台だけ高ければ設置位置の問題）
for h in $(cat hosts.txt); do
  printf "%-20s " "$h"
  ipmitool -I lanplus -H "$h" -U admin -f /root/.ipmipw sdr get 'Inlet Temp' 2>/dev/null \
    | grep 'Sensor Reading'
done
```

ラック内の**上段ほど温度が高くなる**傾向があります（熱気は上昇するため）。同一ラック内で上下の差が 5℃ 以上あるなら、エアフローに問題があります。

</Callout>

### 温度上昇が性能に直結する

ハードウェアコース レッスン 2・6、GPU コース レッスン 2 で扱ったサーマルスロットリングが、ここで繋がります。

```bash
# CPU 側
sudo turbostat --interval 5      # 周波数の低下を確認
dmesg | grep -i 'thermal\|throttl'

# GPU 側
nvidia-smi -q -d PERFORMANCE | grep -A12 "Clocks Event Reasons"
```

**「同じ構成なのに 1 台だけ遅い」の原因が、ラック内の設置位置だった**ということは実際にあります。アプリケーションをいくら調べても見つかりません。

## 空冷の限界

1 ラックあたりに詰められる熱量には、空気の物理的な限界があります。

| ラック密度 | 冷却方式 |
| --- | --- |
| 〜5 kW | 一般的な空調で問題なし |
| 5–15 kW | 適切なエアフロー設計が必要（封じ込め推奨） |
| 15–30 kW | **封じ込め必須**。リアドア熱交換器なども検討 |
| 30 kW 超 | **空冷では現実的に困難。液冷を検討** |

GPU コース レッスン 2 で触れたとおり、**8 GPU（H100 SXM）ノードは 1 台で 10kW を超えます**。1 ラックに 3 台入れれば 30kW です。従来の空冷前提のデータセンターでは、**1 ラックに 1〜2 台しか入れられない**ということが起こります。

### 液冷

| 方式 | 内容 |
| --- | --- |
| **リアドア熱交換器** | ラック背面に水冷ラジエータを付け、排気を冷やして室内に戻す。**既設への後付けが比較的容易** |
| **D2C / DLC（cold plate）** | CPU・GPU に直接冷却板を当てて液体を循環させる。**高密度 GPU で主流** |
| **液浸（immersion）** | 機器ごと絶縁液体に沈める。冷却効率は最高だが、施設と保守の前提が大きく変わる |

---

<h2 className="slide-cont">空冷の限界（続き）</h2>

<Callout type="warning" title="液冷は施設側の対応が前提">

D2C を採用する場合、サーバーだけでは完結しません。

- **CDU**（Cooling Distribution Unit）— 冷却液を循環・分配する装置
- ラックへの**配管**と、漏水検知
- 冷却水の**温度・流量・水質**の管理
- 保守手順（機器の抜き差しにクイックコネクタの作業が加わる）

**「GPU サーバーを買ったが、データセンターが液冷に対応していない」は現実に起きます。** 高密度な GPU 構成を検討する段階で、設置先の対応状況を確認してください。対応していなければ、空冷版（PCIe 版など、GPU コース レッスン 1 参照）を選ぶか、ラックあたりの搭載台数を減らす判断になります。

</Callout>

## ファンと消費電力

吸気温度が上がると、サーバーはファンの回転数を上げて対応します。**ファンの消費電力は回転数の 3 乗にほぼ比例する**ため、この影響は小さくありません。

```text
回転数 2 倍 → 風量 2 倍 → 消費電力 8 倍
```

室温を下げすぎるのも、ファンを回しすぎるのも電力の無駄になります。ASHRAE が推奨範囲を 27℃ まで許容しているのは、**空調を冷やしすぎないほうが施設全体では効率的**だからです（レッスン 1 の PUE）。

```bash
# ファン回転数の確認
ipmitool sdr type Fan
```

```text
FAN1 RPM   | 6720 RPM  | ok
FAN2 RPM   | 6840 RPM  | ok
FAN3 RPM   | 15120 RPM | ok     ← 1つだけ突出 = 近傍の温度異常か他ファンの故障
```

<Callout type="field">

**ファン回転数の急上昇は、温度異常の早期シグナル**です。温度自体はまだ正常範囲でも、それを維持するためにファンが全力で回っている状態が捉えられます。

監視項目として、吸気温度とファン回転数をセットで入れておくことを勧めます。

- 吸気温度が上昇 → 環境（空調、エアフロー）
- 吸気温度は正常なのにファンだけ上昇 → 内部の問題（ヒートシンクの目詰まり、ファン故障、エアフローの内部阻害）

</Callout>

## まとめ

- サーバーは前面吸気・背面排気。**ホットアイル / コールドアイル**はこの前提の上にある
- ラックの向き、**スイッチのエアフロー方向**を間違えると排気を吸い込む
- **ブランクパネルは最も安価で効果の大きい対策**
- **吸気温度は設置環境の実態**を示す。CPU 温度より優先して監視する
- ASHRAE 推奨は 18–27℃。ラック内の上下差が 5℃ 超ならエアフローに問題
- 「1 台だけ遅い」の原因がラック内の位置だったことは実際にある
- **空冷は 30kW/ラック 付近が限界**。GPU 高密度構成では液冷が前提になる
- ファンの消費電力は回転数の 3 乗。**回転数の急上昇は温度異常の早期シグナル**
