## 順番を決めておく

障害対応でいちばん時間を失うのは、**思いついた順にコマンドを打つこと**です。調べる順序を決めておけば、原因がどの層にあるかを数分で絞り込めます。

考え方は 2 段階です。

```text
第1段階: システム全体のどの資源が詰まっているか（CPU / メモリ / ディスク / ネットワーク）
第2段階: その資源を誰が使っているか（プロセス、cgroup、接続先）
```

第 1 段階をすっ飛ばして特定のアプリのログを読み始めると、たいてい遠回りになります。

<Callout type="field">

**最初に「いつから」を確定させてください。** 監視のグラフでも、ユーザーの申告でも構いません。

「ずっと遅い」のか「10 分前から急に」なのかで、疑う対象が変わります。前者は負荷の増加や設定の劣化、後者はデプロイ、バッチ、ハードウェア障害です。時刻が分かれば、後で `journalctl --since` で一気に絞り込めます。

</Callout>

## 最初の 60 秒: 全体を見る

まずこの 6 つを順に打ちます。どれも読み取り専用で、システムに影響しません。

```bash
# ① いつから動いていて、負荷はどう推移したか
uptime

# ② 直近のカーネルメッセージ（OOM、I/O エラー、ハードウェア障害はここに出る）
dmesg -T | tail -30

# ③ CPU・メモリ・スワップ・I/O 待ちを一度に見る
vmstat 1 5

# ④ メモリの逼迫具合
free -h

# ⑤ ディスクの空きと inode
df -h ; df -i

# ⑥ 何が資源を使っているか
top -b -n1 | head -20
```

### 読み方

`uptime` のロードアベレージは、**Linux では R + D 状態のタスク数**でした（Linux コース レッスン 2）。CPU 使用率ではありません。3 つの数字の並びで傾向が分かります。

```text
load average: 24.51, 12.03, 4.88
              ↑1分   ↑5分   ↑15分
→ 右肩上がり。悪化の途中。今まさに何かが起きている

load average: 3.10, 9.87, 22.4
→ 右肩下がり。ピークは過ぎている。復旧中か、既に終わった事象
```

---

<h2 className="slide-cont">最初の 60 秒: 全体を見る（続き）</h2>

`vmstat 1 5` は 1 行に全部入っているので、最も費用対効果が高いコマンドです。

```text
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
18  0      0 412332  98244 2244192    0    0     8    24 4821 9932 94  4  2  0  0
```

| 列 | 見るポイント |
| --- | --- |
| `r` | **実行待ちタスク数**。CPU 数を超えていれば CPU 不足 |
| `b` | **割り込み不可待ち**。I/O 待ち。大きければストレージ側 |
| `si` / `so` | スワップイン/アウト。**0 以外が継続したらメモリ不足** |
| `wa` | I/O 待ちの CPU 時間割合 |
| `st` | **steal**。仮想環境で、ホスト側に CPU を取られている割合 |

<Callout type="tip">

`st`（steal time）が数%以上出ていたら、**そのゲストの中には原因がありません**。ホスト側が過密か、CPU クォータで制限されています。クラウドや仮想基盤上でのみ現れる列ですが、これを知らないとゲスト内を延々と調べることになります。

</Callout>

## 次の 4 分: 層を特定する

第 1 段階で当たりがついたら、その層を深掘りします。

### CPU が原因のとき

```bash
# 使用率順（%CPU で並ぶ）
top -b -n1 -o %CPU | head -15
ps -eo pid,ppid,user,pcpu,pmem,etime,cmd --sort=-pcpu | head -15

# コアごとの内訳。特定コアだけ 100% なら単一スレッドの処理
mpstat -P ALL 1 3

# どの関数で時間を使っているか（原因が読めないとき）
sudo perf top
```

`%sys`（カーネル内）が高い場合は、システムコールの多発やロック競合を疑います。`%usr` が高いなら、素直にアプリケーションの計算量です。

### メモリが原因のとき

```bash
# 使用量順
ps -eo pid,user,rss,vsz,cmd --sort=-rss | head -15

# OOM Killer が動いたか（最重要）
journalctl -k --since "1 hour ago" | grep -i "out of memory\|killed process"

# cgroup 側での OOM（コンテナはこちら）
grep -r . /sys/fs/cgroup/system.slice/*/memory.events 2>/dev/null | grep -v ' 0$'
```

**`available` が総メモリの 10% を切っていなければ、メモリは原因ではありません**（Linux コース レッスン 3）。`free` の少なさに惑わされないでください。

### ディスクが原因のとき

---

<h2 className="slide-cont">次の 4 分: 層を特定する（続き）</h2>

```bash
# デバイスごとの待ち時間と使用率
iostat -xz 1 5

# I/O を発生させているプロセス
sudo iotop -oPa      # -o は実際に I/O 中のものだけ

# 容量が原因の場合、どこが食っているか
du -xh --max-depth=1 / 2>/dev/null | sort -rh | head
```

`iostat` で見るのは `%util` ではなく **`r_await` / `w_await`（待ち時間 ms）** です。SSD では `%util` が 100% でも余裕があります（ハードウェアコース レッスン 4）。

### ネットワークが原因のとき

```bash
# ドロップとエラー
ip -s link
nstat -az | grep -iE 'drop|retrans|overflow'

# 接続状態の分布
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c | sort -rn

# ポートごとの接続数
ss -tan state established | awk '{print $4}' | rev | cut -d: -f1 | rev | sort | uniq -c | sort -rn | head
```

## 証拠を保全してから復旧する

ここが実務でいちばん大事な判断です。

<Callout type="warning" title="再起動すると原因は消える">

「とりあえず再起動」で復旧はしますが、**メモリの状態、プロセスの一覧、開いていたファイル記述子、ソケットの状態はすべて失われます**。同じ障害が再発したとき、また同じところから始めることになります。

サービス停止が許容できる数分があるなら、**最低限これだけは取ってから再起動してください。**

```bash
# 1行で最低限の状態を保存する
D=/var/tmp/incident-$(date +%Y%m%d-%H%M%S); mkdir -p $D
{ uptime; free -h; df -h; df -i; } > $D/summary.txt 2>&1
ps auxf > $D/ps.txt 2>&1
top -b -n1 > $D/top.txt 2>&1
ss -tanp > $D/ss.txt 2>&1
dmesg -T > $D/dmesg.txt 2>&1
journalctl --since "2 hours ago" --no-pager > $D/journal.txt 2>&1
vmstat 1 10 > $D/vmstat.txt 2>&1
echo "saved to $D"
```

30 秒程度で終わります。これがあるかないかで、事後の原因究明の成否が決まります。

</Callout>

### ベンダーサポートに出す場合

商用のディストリビューションやハードウェアのサポートに問い合わせる場合、包括的な情報採取ツールがあります。

---

<h2 className="slide-cont">証拠を保全してから復旧する（続き）</h2>

```bash
# RHEL 系
sudo sosreport      # 新しめの環境では sudo sos report

# Ubuntu / Debian 系
sudo apport-cli

# ハードウェアベンダーのログ（ハードウェアコース レッスン 6）
sudo ipmitool sel list > $D/sel.txt
```

**採取は復旧前に行ってください。** 再起動後に採取しても、障害時の情報は入っていません。

## 時刻で絞り込む

「いつから」が分かっていれば、ログの調査は一気に楽になります。

```bash
# 期間を指定して全ログを見る
journalctl --since "2026-09-19 14:00" --until "2026-09-19 14:30" --no-pager

# 前回の起動時のログ（再起動してしまった後の調査）
journalctl -b -1 -e

# 優先度 err 以上だけ
journalctl -p err --since "1 hour ago"

# カーネルのみ
journalctl -k --since "1 hour ago"
```

<Callout type="pitfall">

`journalctl -b -1` は「1 つ前の起動」のログです。**予期しない再起動の調査では、現在の起動（`-b`）ではなくこちらを見ます。** 落ちる直前に何が記録されていたかが、そこにあります。

なお、journald が永続化設定になっていないと再起動でログが消えます。`/var/log/journal` ディレクトリが存在するか確認してください（次のレッスンで扱います）。

</Callout>

## 判断を分ける

対応中は、次の 3 つを意識的に分けてください。混ざると判断を誤ります。

| | 目的 | 優先度 |
| --- | --- | --- |
| **復旧** | サービスを戻す | 最優先 |
| **証拠保全** | 後で調べられるようにする | 復旧の直前に 30 秒 |
| **原因究明** | 恒久対策を決める | **復旧後に落ち着いて** |

原因が分からないまま復旧させることは、失敗ではありません。**証拠さえ残っていれば、後から追えます。** 逆に、原因究明にこだわってサービス停止を長引かせるのは、たいていの場合よくない判断です。

---

## まとめ

- 調べる順序を固定する。**全体（どの資源）→ 個別（誰が）** の 2 段階
- `uptime` の 3 つの数字の傾向で、悪化中か収束中かが分かる
- **`vmstat 1 5` が最も情報密度が高い。`r` / `b` / `si` / `so` / `st` を見る**
- `st`（steal）が出ていたら、ゲストの中に原因はない
- **再起動の前に 30 秒で状態を保存する**。消えた証拠は戻らない
- 予期しない再起動の調査は `journalctl -b -1`
- 復旧・証拠保全・原因究明を分けて考える
