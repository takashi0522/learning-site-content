## 認証と認可は別の問題

日本語ではどちらも「認証」と呼ばれがちですが、**答えている問いが違います**。

| | **認証 (AuthN)** | **認可 (AuthZ)** |
| --- | --- | --- |
| 問い | **あなたは誰か** | **それをしてよいか** |
| 出力 | 主体の識別（ユーザー ID） | 許可 / 拒否 |
| 担当 | IdP（レッスン 5） | アプリケーション / ポリシーエンジン |
| 失敗時 | **401 Unauthorized** | **403 Forbidden** |

```text
401 Unauthorized : あなたが誰か分からない（ログインしてください）
403 Forbidden    : あなたが誰かは分かったが、権限がない
```

<Callout type="pitfall" title="認証だけして認可を忘れる">

最も多い実装ミスです。

```text
「ログインしていれば OK」という実装
  → ログインした別のユーザーが、他人のデータを見られる
```

```text
GET /api/orders/12345     ← このユーザーの注文か確認していない
GET /api/users/999/profile ← ID を書き換えれば誰のものでも見える
```

これは **IDOR**（Insecure Direct Object Reference）と呼ばれる典型的な脆弱性で、OWASP のリストでも上位に来ます。

**「誰か」が分かっただけでは何も守れません。** リソースごとに「この主体がこの操作をしてよいか」を必ず確認する必要があります。認証を IdP に任せても、**認可はアプリの責任として残ります**。

</Callout>

## 何をもって「本人」とするか

認証要素は 3 種類に分類されます。

| 要素 | 内容 | 例 |
| --- | --- | --- |
| **知識**（something you know） | 知っていること | パスワード、PIN |
| **所持**（something you have） | 持っているもの | スマートフォン、ハードウェアキー、**クライアント証明書** |
| **生体**（something you are） | 身体的特徴 | 指紋、顔 |

**MFA（多要素認証）は、異なる種類を組み合わせること**を指します。

```text
✗ パスワード + 秘密の質問        → どちらも「知識」。多要素ではない
✓ パスワード + TOTP アプリ       → 知識 + 所持
✓ パスワード + ハードウェアキー   → 知識 + 所持（最も強い）
```

<Callout type="note" title="MFA の方式による強度差">

| 方式 | 強度 | 弱点 |
| --- | --- | --- |
| SMS ワンタイムコード | 低 | SIM スワップ、傍受 |
| **TOTP**（Google Authenticator 等） | 中 | **フィッシングで中継されうる** |
| プッシュ通知承認 | 中 | 通知疲れによる誤承認 |
| **FIDO2 / WebAuthn** | **高** | **フィッシング耐性がある** |

FIDO2 が強いのは、**認証時にドメイン（オリジン）を検証する**ためです。偽サイトに誘導されても、鍵がそのドメイン用でなければ認証が成立しません。TOTP は「コードを読み上げさせて中継する」攻撃が成立しますが、FIDO2 では成立しません。

オンプレの IdP（レッスン 5 の Keycloak など）も WebAuthn に対応しています。**管理者アカウントだけでも FIDO2 にする**価値は大きいです。

</Callout>

## パスワードの扱い

```text
✗ 平文で保存
✗ 可逆暗号で保存（鍵が漏れたら全部漏れる）
✗ SHA-256 / MD5 で単純にハッシュ化   ← 速すぎる
✓ ソルト付きの「遅い」ハッシュ
```

<Callout type="warning" title="速いハッシュは総当たりに弱い">

SHA-256 は**高速であることが設計目標**のアルゴリズムです。GPU コースで見たような計算資源を使えば、**毎秒数十億回**の試行ができます。パスワード保存には不向きです。

パスワード用には、**意図的に遅く、メモリも消費する**アルゴリズムを使います。

| アルゴリズム | 特徴 |
| --- | --- |
| **Argon2id** | **現在の推奨**。メモリ消費を大きくでき、GPU での並列化に強い |
| bcrypt | 広く使われている。実績が長い |
| scrypt | メモリ困難性を持つ |
| PBKDF2 | 規格要件で必要な場合に |

**ソルト**（ユーザーごとに異なるランダム値）は、同じパスワードが同じハッシュにならないようにし、事前計算テーブル（レインボーテーブル）を無効化します。bcrypt や Argon2 はソルトを自動で扱います。

</Callout>

### 現在の推奨ポリシー

NIST SP 800-63B 以降、**従来の「常識」が否定されています**。

```text
✗ 定期的な強制変更          → 使い回しや規則的な変更を誘発する
✗ 複雑さの強制（記号必須等）  → 覚えられず付箋に書かれる
✓ 最低文字数を長くする（8文字以上、できれば12以上）
✓ 漏洩済みパスワードリストとの照合
✓ 流出の兆候があったときだけ変更を要求
```

---

<h2 className="slide-cont">パスワードの扱い（続き）</h2>

**「90日ごとに変更」は現在は推奨されていません。** 変更のたびに `Password01` → `Password02` のような規則的な変化が起き、かえって弱くなるためです。

## セッションとトークン

ログイン後、「この人は認証済み」という状態をどう保持するか。**2 つの方式があり、失効の扱いが決定的に違います**。

| | **セッション（ステートフル）** | **トークン（ステートレス / JWT）** |
| --- | --- | --- |
| 状態の保管 | **サーバー側**（DB / Redis） | **トークン自体に含む** |
| クライアントが持つもの | セッション ID | 署名付きの JWT |
| 検証 | ストアを引く | **署名を検証するだけ** |
| **失効** | **即座にできる**（ストアから消す） | **困難**（有効期限まで有効） |
| スケール | ストアが必要（レッスン 4 の Redis など） | **共有ストア不要** |
| サイズ | 小さい | 大きい（リクエストごとに送る） |

<Callout type="field">

**「JWT のほうが新しいから」で選ぶのは誤りです。**

決定的な違いは**失効**です。

```text
退職者のアクセスを今すぐ止めたい
  セッション : ストアから削除 → 次のリクエストで弾かれる
  JWT        : 有効期限が切れるまで有効。止める手段が無い
```

これに対処するため、実務では次の折衷になります。

```text
アクセストークン : 寿命を短くする（5〜15分）
リフレッシュトークン: 長め。こちらはサーバー側で管理して失効可能にする
  → 失効までの最大猶予 = アクセストークンの寿命
```

つまり**「ステートレスの利点を得つつ、失効のためにどこかで状態を持つ」**のが現実解です。完全にステートレスにすると、緊急時に止められません。

**社内システムのように、失効の即時性が重要でスケールが問題にならない場合、素直にセッション方式を選ぶのは今も妥当な判断です。**

</Callout>

### Cookie の属性

セッション ID やトークンを Cookie で運ぶ場合、属性の設定が防御の要になります。

```text
Set-Cookie: session=...; HttpOnly; Secure; SameSite=Lax; Path=/
```

| 属性 | 防ぐもの |
| --- | --- |
| **`HttpOnly`** | JavaScript からの読み取り（XSS で盗まれるのを防ぐ） |
| **`Secure`** | HTTP（平文）での送信 |
| **`SameSite=Lax` / `Strict`** | **CSRF**（別サイトからの自動送信） |

<Callout type="pitfall">

**トークンを `localStorage` に保存する設計は、XSS に対して無防備です。** JavaScript から読めるため、1 つでも XSS があれば全ユーザーのトークンが盗まれます。

`HttpOnly` Cookie であれば、XSS があってもトークン自体は読み出せません（その JavaScript がリクエストを送ることは防げませんが、トークンの持ち出しは防げます）。

SPA では `localStorage` が手軽なため広く使われていますが、**トレードオフを理解したうえで選んでください**。

</Callout>

## 自前実装を避ける

<Callout type="warning" title="認証は自分で作らない">

認証の実装には、見落としやすい落とし穴が多数あります。

- **タイミング攻撃** … 文字列比較の所要時間から情報が漏れる（定数時間比較が必要）
- **セッション固定攻撃** … ログイン後にセッション ID を再生成していない
- **パスワードリセットの穴** … トークンの推測可能性、有効期限、使い捨ての徹底
- **アカウント列挙** … 「ユーザーが存在しません」と「パスワードが違います」を区別すると、存在するユーザー名が分かる
- **総当たり対策** … レート制限、アカウントロック（ロックアウト自体が DoS になりうる）

**これらすべてを正しく実装し、維持し続けるのは、認証を専門としないチームには割に合いません。**

オンプレであっても、Keycloak のような実績のある IdP（レッスン 5）を立てるほうが、結果的に安全で安く済みます。**「外部サービスが使えないから自前で作る」は、選択肢の取り違えです。**

</Callout>

## 認可のモデル

| モデル | 内容 | 向く場面 |
| --- | --- | --- |
| **RBAC**（ロールベース） | ユーザーにロールを割り当て、ロールに権限を紐づける | **多くの業務システム** |
| **ABAC**（属性ベース） | 属性（部署、時刻、場所）と条件で判定 | 細かい制御が必要な場合 |
| ReBAC（関係ベース） | 「このドキュメントの所有者か」といった関係で判定 | 共有・協調が中心のサービス |

```text
RBAC の例:
  ユーザー tanaka → ロール "operator"
  ロール "operator" → 権限 "server:restart", "log:read"
```

<Callout type="tip">

**ロールは「職務」で設計し、「人」で設計しないでください。**

```text
✗ role: tanaka-permissions    → 人が増えるたびにロールが増える
✓ role: operator / auditor / admin
```

また、**ロールの数が権限の数に近づいてきたら、RBAC が破綻しかけているサイン**です。その場合は ABAC の導入か、リソース側でのオーナーシップ判定を検討します。

次のレッスンから、この認証を成立させる土台である PKI と証明書に入ります。オンプレで IdP や mTLS を組む場合、**自己認証局が前提になる**ためです。

</Callout>

## まとめ

- **認証（誰か）と認可（してよいか）は別問題**。401 と 403 の違いに対応する
- **認証だけして認可を忘れる**のが最も多い脆弱性（IDOR）
- MFA は**異なる要素**の組み合わせ。パスワード + 秘密の質問は多要素ではない
- **FIDO2 / WebAuthn はフィッシング耐性がある**。管理者だけでも導入価値が高い
- パスワードは **Argon2id / bcrypt** で保存する。SHA-256 は速すぎて不適
- **定期的な強制変更は現在は非推奨**
- セッションとトークンの決定的な違いは**失効のしやすさ**
- 完全ステートレスだと**退職者を止められない**。短命アクセストークン + 管理されたリフレッシュトークン
- `HttpOnly` / `Secure` / `SameSite` を必ず設定する
- **認証は自前実装しない**。オンプレでも既製の IdP を立てる
