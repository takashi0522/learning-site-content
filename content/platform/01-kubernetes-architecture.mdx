| `kube-apiserver` | コントロールプレーン | Kubernetes の HTTP API を提供する中心のサーバー |

| `kube-scheduler` | コントロールプレーン | まだノードに割り当てられていない Pod を探し、適したノードに割り当てる |

基盤から見ると、**etcd はクラスタの状態そのもの**です。バックアップと冗長の対象として、データベースと同じ扱いが要ります。

## コントローラ — 望む状態に近づけ続けるループ

ドキュメントは、コントローラを**部屋のサーモスタット**にたとえています。設定した温度が「望む状態」、実際の室温が「現在の状態」で、サーモスタットは機器をつけたり消したりして、現在の状態を望む状態に近づけます。

Kubernetes のオブジェクトは、望む状態を表す `spec` という欄を持ちます。コントローラは担当する種類のオブジェクトを見張り、現在の状態を `spec` に近づけます。ドキュメントによると、多くの場合コントローラは自分で操作するのではなく、**API サーバーにメッセージを送り**、その結果をほかの部品が実行します。

ドキュメントの Job の例では、Job コントローラは自分では Pod もコンテナも動かさず、**API サーバーに Pod を作るよう伝える**だけです。スケジューラがその Pod をノードに割り当て、割り当てられた Pod はそのノードの kubelet にとっての望む状態になります。

つまり Kubernetes では、**「やれ」という命令を出すのではなく、「こうあるべき」を書いておく**と、ループがそこへ近づけ続けます。何かが壊れても、ループが差を見つけて直しに行きます。

## Pod — 動かす単位

ドキュメントによると、**Pod** は Kubernetes で作って管理できる最小の単位で、1 つ以上のコンテナを、**ストレージとネットワークを共有させて**まとめたものです。Pod の共有の文脈は、Linux の namespace や cgroup といった、コンテナを隔離するのと同じ仕組みでできています（Linux コース レッスン 6）。

最も多い使い方は、**1 つの Pod に 1 つのコンテナ**です。ドキュメントは、Pod は**比較的短命で、使い捨ての**ものとして設計されていて、1 つだけ動かす場合でも、ふつうは Pod を直接作らず、**Deployment や Job といったワークロードのリソース**から作る、と書いています。Pod は、終わるか、消されるか、資源不足で追い出されるか、ノードが故障するまで、そのノードに留まります。

Pod の `status` の `phase` は、次の 5 つです。

| phase | 意味（ドキュメント） |
| --- | --- |
| `Pending` | 受け付けられたが、まだ動く準備ができていない。スケジュール待ちと、イメージのダウンロード中を含む |
| `Running` | ノードに割り当てられ、コンテナがすべて作られた。少なくとも 1 つが動いている |
| `Succeeded` / `Failed` | すべてのコンテナが終わった（成功 / 失敗） |
| `Unknown` | 状態を得られない。ふつうはノードとの通信の問題 |

`kubectl` の `STATUS` 欄に出る `CrashLoopBackOff` や `Terminating` は、表示のための値で、`phase` とは別物です（ドキュメントの注記）。

## Deployment で追う — 望む状態が Pod になるまで

ドキュメントの例では、`nginx` を 3 つ動かす Deployment を作ります。

```bash
kubectl apply -f https://k8s.io/examples/controllers/nginx-deployment.yaml
kubectl get deployments
```

```text
NAME               READY   UP-TO-DATE   AVAILABLE   AGE
nginx-deployment   3/3     3            3           18s
```

`READY` は「利用者に使える状態の数 / 望む数」です。Deployment は **ReplicaSet** を作り、ReplicaSet が Pod を作ります。

```bash
kubectl get rs
```

```text
NAME                          DESIRED   CURRENT   READY   AGE
nginx-deployment-75675f5897   3         3         3       18s
```

`DESIRED` が望む状態（3）、`CURRENT` が今動いている数です。この 2 つの差を埋めるのが、コントローラのループです。

## 失敗した更新は、途中で止まる

ドキュメントには、存在しないイメージに更新してしまった例が載っています。

```text
NAME                                READY     STATUS             RESTARTS   AGE
nginx-deployment-1564180365-70iae   1/1       Running            0          25s
nginx-deployment-1564180365-jbqqo   1/1       Running            0          25s
nginx-deployment-1564180365-hysrc   1/1       Running            0          25s
nginx-deployment-3066724191-08mng   0/1       ImagePullBackOff   0          6s
```

新しい ReplicaSet の Pod が 1 つ、イメージを取得できずに止まっています（`ImagePullBackOff`）。ドキュメントによると、Deployment のコントローラは、この**悪い更新を自動で止め**、新しい ReplicaSet を増やすのをやめます。どこまで進めるかは更新の設定（`maxUnavailable`、既定は 25%）で決まります。古い 3 つの Pod は動いたままなので、サービスは止まっていません。

基盤から見ると、`ImagePullBackOff` は**ノードからイメージのレジストリに届いていない**か、イメージの名前が誤っているかの合図です。GPU のノードが閉じたネットワークにあるなら、レジストリの置き場所とミラーは設計の対象になります。

## まとめ

- クラスタは**コントロールプレーン**（apiserver・etcd・scheduler・controller-manager）と**ワーカーノード**（kubelet・コンテナランタイム・kube-proxy）でできている
- コントローラは **API サーバーに伝え**、ほかの部品がその変化に反応して動く。etcd はクラスタの状態そのもの
- **コントローラ**は、`spec`（望む状態）に現在の状態を近づけ続けるループ。命令ではなく「こうあるべき」を書く
- **Pod** は、ネットワークとストレージを共有するコンテナの組で、短命な使い捨て。ふつうは Deployment などから作る
- Deployment → ReplicaSet → Pod。`DESIRED` と `CURRENT` の差を埋めるのがループ。悪い更新は途中で止まる
