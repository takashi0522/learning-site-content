## 1 台ずつ入れない

GPU 基盤の導入コース レッスン 4 では、OS・ドライバ・ミドルウェアを積む**順番**を見ました。このレッスンは、その最初の段、**OS をどうやって何百台にも入れるか**です。

USB メモリを挿して 1 台ずつインストーラを進めるやり方は、台数が増えると成り立ちません。そこで、サーバーの**ファームウェアがネットワークから起動し**、インストーラと設定を取りに行く仕組みを使います。電源の投入や「次はネットワークから起動せよ」という指示は、BMC から遠隔で出します（ハードウェアコース レッスン 6）。

## DHCP が「何を起動するか」を決める

ネットワークから起動するサーバーは、まず DHCP で IP アドレスと一緒に、**起動するファイルの名前と置き場所**を受け取ります。問題は、サーバーによって必要なファイルが違うことです。古い BIOS のサーバーと UEFI のサーバーでは、動かせるプログラムの形式が違います。

RFC 4578 は、PXE のクライアントが DHCP の要求に付ける情報を定めています。起動するサーバーが**自分と、起動前の実行環境を名乗り**、DHCP と起動のサーバーが正しいイメージを返せるようにするためです。

| DHCP のオプション | 中身 |
| --- | --- |
| 93: クライアントのシステムアーキテクチャ | 起動前の実行環境の種別 |
| 94: クライアントのネットワークインターフェースの識別子 | インターフェースの種別（現状は UNDI のみ）とその版 |
| 97: クライアントのマシンの識別子 | マシンを一意に表す 16 オクテットの値（GUID） |

RFC は、以前は MAC アドレスで見分けていたが、ドッキングステーションを共有すると複数の機械が同じ MAC になる、1 台が冗長や修理で複数の NIC を持つ、といった理由で足りなかった、と書いています。

---

<h2 className="slide-cont">DHCP が「何を起動するか」を決める（続き）</h2>

オプション 93 の値は IANA が管理しています。よく出会うものを抜き出します。

| 値 | 種別（IANA の表） |
| --- | --- |
| `0x00 0x00` | x86 BIOS |
| `0x00 0x07` | x64 UEFI |
| `0x00 0x0b` | ARM 64-bit UEFI |
| `0x00 0x10` | x64 UEFI boot from http |

最後の行のとおり、UEFI には **TFTP ではなく HTTP で起動ファイルを取りに行く**種別も登録されています。

DHCP サーバーは、この値を見て返す起動ファイルを選び分けます。iPXE のドキュメントの、ISC dhcpd の設定例です。

```text
option client-arch code 93 = unsigned integer 16;
if option client-arch != 00:00 {
   filename "ipxe.efi";
} else {
   filename "undionly.kpxe";
}
next-server X.X.X.X;
```

`next-server` は、起動ファイルを置いた TFTP サーバーのアドレスです。

## iPXE — ネットワークの起動を強くする

**iPXE** は、オープンソースのネットワーク起動のファームウェアです。PXE を完全に実装したうえで、**HTTP の Web サーバーからの起動**、iSCSI や FCoE の SAN からの起動、**InfiniBand のネットワークからの起動**、**スクリプトによる起動の制御**などを足しています（iPXE のドキュメント）。

NIC の ROM を書き換えなくても、既存の PXE から iPXE を**チェーンロード**（PXE で iPXE を読み込み、そこから先を iPXE に任せる）すれば、これらの機能を使えます。

<Callout type="pitfall" title="チェーンロードの無限ループ">

iPXE のドキュメントによると、チェーンロードした iPXE は起動すると**もう一度 DHCP を要求し**、DHCP サーバーが返すものを起動します。DHCP サーバーが iPXE そのものを返す設定のままだと、**PXE が iPXE を読み、その iPXE が iPXE を読み…という無限ループ**になります。ドキュメントが挙げる断ち方は 3 つです。

- iPXE と同じ場所に `autoexec.ipxe` というスクリプトを置く（自動で読まれる。ただし対応しない環境もある）
- DHCP サーバーで、**1 回目の要求にだけ iPXE を返し**、2 回目には本来の起動ファイルを返す
- 起動先の URL を書いたスクリプトを**埋め込んだ iPXE をビルドする**

</Callout>

iPXE のドキュメントは、UEFI のネットワーク起動は、UEFI の設計上の制約から BIOS の起動よりかなり遅くなりがちだ、とも書いています。

## 初回の起動で設定を流し込む — cloud-init

OS のイメージは全台で同じにしておき、**ホスト名・ネットワーク・ユーザー・鍵**などの個別の設定は、初回の起動で流し込む、という分け方ができます。そのための道具が **cloud-init** です。名前のとおりクラウドを主な対象にしていますが、データの取り元（データソース）を選べるので、ベアメタルでも使えます。

ドキュメントによると、cloud-init は起動を次の段階に分けて動きます。

| 段階 | すること（ドキュメント） |
| --- | --- |
| Detect | どのプラットフォームで動いているかを判定する |
| Local | 設定の取り元（データソース）を探し、ネットワークの設定を決める。**初回の起動なら**、古い MAC アドレスの名前付けなどの古い設定を消して、新しい設定を書く |
| Network | ネットワークが上がってから、利用者のデータ（user-data）を処理する。ディスクの準備などもここ |
| Config / Final | 残りの設定と、最後に走らせる処理 |

---

<h2 className="slide-cont">初回の起動で設定を流し込む（続き）</h2>

ベアメタルで使える取り元の 1 つが **NoCloud** です。ドキュメントによると、設定をローカルに置くこともできれば、**リモートのサーバーから取ってくる**こともできます。カーネルのコマンドラインに次の 1 行を渡すと、HTTPS のサーバーから設定を取ります。

```text
ds=nocloud;s=https://10.42.42.42/configs/
```

取ってくるのは 4 種類の設定です。

| 設定 | 中身 |
| --- | --- |
| `user-data` | 利用者がインスタンスを設定するための内容 |
| `meta-data` | プラットフォームが渡す情報。**`instance-id` は必須** |
| `vendor-data` | 既定の設定（user-data で上書きできる） |
| `network-config` | ネットワークの設定 |

ドキュメントは、GRUB でカーネルのコマンドラインに渡すときは、**エスケープしていないセミコロンが文の終わりと解釈される**と注意しています。上の 1 行は、そのままでは途中で切れることがあります。

## 全体を回す道具

ここまでの部品を組み合わせて、物理マシンの払い出しを自動にする道具もあります。その 1 つが OpenStack の **Ironic** です。

ドキュメントによると、Ironic は**物理マシン（ベアメタル）を払い出す**プロジェクトで、単独でも、OpenStack のクラウドの一部としても使えます。コミュニティの参照ドライバは、**PXE や IPMI** といったオープンな技術で幅広いハードウェアを扱い、ハードウェアのベンダーが自分のドライバを足せる構造です。OpenStack の Compute とネットワークのサービスと適切に組み合わせると、Compute の API で仮想マシンと物理マシンの両方を払い出せますが、物理サーバーの性質上、**ライブマイグレーションのような操作はできない**、とも書いています。

<Callout type="field" title="GPU サーバーで気をつけること">

GPU サーバーは、管理用・ストレージ用・計算ファブリック用と複数のネットワークにつながります（GPU 基盤の導入コース レッスン 2 の 4 系統）。どれでネットワーク起動するかを、ファームウェアの起動順と DHCP の範囲の両方で決めておく必要があります。起動に使うのはふつう管理系のネットワークで、計算ファブリックは使いません（このコースの整理）。

</Callout>

## まとめ

- 台数が多いと、**ネットワークから起動して OS を入れ、初回の起動で設定を流し込む**。電源と起動先の指示は BMC から
- DHCP は、要求に付いた**オプション 93（アーキテクチャの種別）**などを見て、返す起動ファイルを選ぶ。BIOS と UEFI、UEFI の HTTP 起動で値が違う
- **iPXE** は HTTP・iSCSI・InfiniBand・スクリプトでの起動を足す。チェーンロードは**無限ループ**に注意し、`autoexec.ipxe`・DHCP での出し分け・埋め込みスクリプトで断つ
- **cloud-init** は初回の起動で、データソースから設定を取り、ネットワークと利用者の設定を適用する。ベアメタルでは **NoCloud** でリモートから取れる
- 物理マシンの払い出しを自動にする道具に **Ironic** などがある（PXE と IPMI の参照ドライバ）
