## 学習と推論は別のシステム

「AI 基盤」と一言で言っても、**学習（training）と推論（inference）では要求されるものがほとんど逆**です。同じ設計で両方をまかなおうとすると、どちらも中途半端になります。

| | **学習** | **推論** |
| --- | --- | --- |
| ジョブの形 | 長時間（数時間〜数か月）、少数の大きなジョブ | 短時間、大量のリクエスト |
| GPU 数 | 数十〜数千枚を**同時に協調** | 1〜数枚で独立 |
| **ノード間通信** | **極めて多い**（集合通信） | ほぼ不要 |
| VRAM | 勾配・オプティマイザ状態で**モデルの数倍** | モデル + KV キャッシュ |
| ストレージ | **大量データの読み出し** + チェックポイント書き込み | モデルの読み込みのみ |
| 障害の影響 | **1 ノード落ちるとジョブ全体が止まる** | 該当リクエストのみ |
| 最適化の目標 | スループット（総処理時間） | **レイテンシ**（応答時間） |

<Callout type="field">

**この違いが、基盤の設計判断に直結します。**

- 学習クラスタ → ノード間ネットワークに投資する（InfiniBand、1:1 のオーバーサブスクリプション）
- 推論クラスタ → ネットワークは通常の Ethernet で十分。**GPU 台数と VRAM 効率**に投資する

推論基盤に InfiniBand を入れても、ほとんど使われません。逆に学習クラスタのネットワークをケチると、GPU コース レッスン 3 で見たとおり高価な GPU が通信待ちで遊びます。

**まず「何を動かす基盤か」を確定させてください。** ここが曖昧なまま機材を選ぶと、どちらにも最適化されていない構成になります。

</Callout>

## 学習ジョブの 1 ステップを分解する

分散学習の 1 イテレーションで何が起きているかを分解すると、**どこがボトルネックになりうるか**が見えます。

<Figure name="training-step" caption="GPU が計算しているのは ④ と ⑥ だけ。残りは別の資源に律速される" />

**GPU が実際に計算しているのは ④ と ⑥ だけです。** それ以外の時間、GPU は待っています。

| 層 | 遅いときの症状 | 確認方法 |
| --- | --- | --- |
| ① ストレージ | GPU 利用率が周期的に落ちる | `iostat`、データローダの待ち時間 |
| ② 前処理 | **CPU が飽和、GPU は低稼働** | `top`、`num_workers` を増やして変化を見る |
| ③ 転送 | `PCIE_RX` が高く `SM_ACTIVE` が低い | DCGM（GPU コース レッスン 4） |
| ④⑥ 演算 | `TENSOR_ACTIVE` が高い | **これが理想の状態** |
| ⑤ 通信 | GPU 数を増やしても速くならない | `nccl-tests`、レッスン 3 |

<Callout type="pitfall" title="GPU がボトルネックであることは、実は少ない">

高価な GPU を並べたのに性能が出ない、という相談のほとんどは **GPU 以外が原因**です。

GPU コース レッスン 4 で扱ったとおり、`nvidia-smi` の `GPU-Util` は当てになりません。`SM_ACTIVE` と `PIPE_TENSOR_ACTIVE` を見ると、**演算器が数% しか動いていない**ことが珍しくありません。

このコースで扱う InfiniBand（レッスン 2）、NCCL（レッスン 3）、ストレージ（レッスン 4）は、いずれも **④⑥ 以外の時間を削るための層**です。

</Callout>

## VRAM の見積もり

「このモデルは何枚の GPU で動くか」を判断するための計算です。**推論と学習で必要量が桁違いになります。**

### 推論

```text
必要 VRAM ≒ パラメータ数 × 精度のバイト数 + KV キャッシュ

例: 70B パラメータのモデル
  FP16 (2 バイト) : 70B × 2 = 140 GB   → H100 80GB では 2 枚必要
  INT8 (1 バイト) : 70B × 1 =  70 GB   → 1 枚に収まる
  INT4 (0.5)      : 70B × 0.5 = 35 GB  → 1 枚で余裕
```

推論では**量子化（低精度化）**によって必要 VRAM を大きく減らせます。精度の劣化と引き換えに、必要な GPU 台数が変わります。

### 学習

学習ではパラメータ以外に、**勾配とオプティマイザの状態**を保持する必要があります。

```text
Adam オプティマイザ + 混合精度の典型的な内訳（パラメータ 1 個あたり）

  FP16 のパラメータ      : 2 バイト
  FP16 の勾配            : 2 バイト
  FP32 のマスター重み    : 4 バイト
  Adam の 1 次モーメント : 4 バイト
  Adam の 2 次モーメント : 4 バイト
  ────────────────────────────────
  合計                    : 約 16 バイト / パラメータ

  70B モデル → 70B × 16 ≒ 1.1 TB
```

**推論で 140GB だったものが、学習では 1.1TB になります。** さらに活性化値（中間結果）のメモリが加わります。

この 16 バイトの内訳は ZeRO の論文（Rajbhandari et al.）が示したものです。それぞれがなぜ要るのかは、GPU の使われ方コース レッスン 1 で扱います。

<h2 className="slide-cont">VRAM の見積もり（続き）</h2>

<Callout type="note">

この差が、分散学習で ZeRO / FSDP のような**オプティマイザ状態を GPU 間で分割する手法**が必須になる理由です。分割すれば 1 枚あたりの必要量は減りますが、その分**通信が増えます**（レッスン 3）。

「VRAM を節約する」と「通信を減らす」はトレードオフの関係にあり、どちらを取るかがクラスタの構成に依存します。**ノード間が InfiniBand なら通信寄りに倒せますが、Ethernet ならメモリ寄りに倒さざるを得ません。**

</Callout>

## チェックポイントという特殊な負荷

学習は数日〜数か月かかるため、**途中で落ちても再開できるようにチェックポイントを保存します**。これがストレージに特徴的な負荷をかけます。

```text
チェックポイントのサイズ ≒ VRAM に載っている状態とほぼ同じ
  → 70B モデルなら 1 TB 前後

これを 1〜数時間おきに、全ランクが一斉に書き出す
  → 瞬間的に数百 GB/s の書き込みが発生する
```

**問題は、保存中は GPU が止まることです。**

```text
学習 30分 → チェックポイント保存 5分（GPU 待機）→ 学習 30分 → ...
  → 全体の 14% を保存に費やしている
```

対策はレッスン 4 で扱いますが、**設計段階でこの負荷を見込んでおく**必要があります。「学習データの読み出し」だけを想定してストレージを選ぶと、チェックポイント時に詰まります。

## 障害への耐性

<Callout type="warning" title="1 ノードの障害が、数千 GPU のジョブを止める">

分散学習は**全ランクが同期して進む**ため、1 つでも止まれば全体が止まります。GPU が 1000 枚のジョブで 1 枚が Xid 79（GPU コース レッスン 2）を出せば、**1000 枚分の計算が止まります**。

GPU の枚数が増えるほど、統計的に障害の発生確率は上がります。大規模クラスタでは「障害は起きるもの」として設計します。

- **チェックポイントを適切な間隔で取る**（障害時に失うのは前回保存以降の分だけ）
- 故障ノードを自動的に切り離し、**予備ノードで再開する**仕組み
- Elastic training（実行中にノード数を変えられる方式）の検討
- **Xid や ECC の監視を、ジョブのスケジューラと連動させる**

「チェックポイント間隔をどう決めるか」は、保存コスト（GPU が止まる時間）と障害時の損失（やり直す時間）のバランスです。ノード数が多いほど、間隔は短くすべきです。

</Callout>

## このコースで扱う層

<Figure name="ai-stack-layers" caption="どの層も GPU を待たせないためにある。詰まる場所はだいたい GPU 以外" />

下の層ほど、**後から変更するコストが高くなります**。InfiniBand を入れるかどうかは発注時点の判断で、後から追加するのは大規模な工事になります。逆に、ジョブスケジューラは後から入れ替えられます。

<Callout type="tip">

**設計の順序としては、下から決めていくのが安全です。**

1. どんなジョブを、何ノード規模で動かすか（レッスン 1）
2. ノード間ネットワークをどうするか（レッスン 2） ← **後戻りが最も難しい**
3. ストレージの構成（レッスン 4）
4. ジョブ管理の方式（レッスン 5、6）

「とりあえず GPU サーバーを買って、あとは動かしながら考える」という進め方だと、2 の段階で詰みます。

</Callout>

## まとめ

- **学習と推論は要求が逆**。同じ設計で両方をまかなおうとしない
- 学習の 1 ステップのうち、GPU が計算しているのは一部。**残りは待ち時間**
- 性能が出ないとき、**GPU が原因であることは実は少ない**
- 学習の VRAM は**パラメータ 1 個あたり約 16 バイト**。推論の 8 倍前後
- VRAM 節約と通信量はトレードオフ。**ネットワークの性能が選択肢を決める**
- チェックポイントは**瞬間的に巨大な書き込み**を発生させ、その間 GPU が止まる
- 規模が大きいほど障害は起きる。**切り離しと再開を設計に織り込む**
- 設計は下の層（ネットワーク）から決める。**後戻りのコストが違う**
