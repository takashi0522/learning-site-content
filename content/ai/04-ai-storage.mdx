## 2 つの、性質が正反対の負荷

AI 基盤のストレージには、**まったく違う 2 種類の負荷**がかかります。片方だけを想定して設計すると、必ずもう片方で詰まります。

| | **学習データの読み出し** | **チェックポイントの書き込み** |
| --- | --- | --- |
| 方向 | 読み（Read） | 書き（Write） |
| 頻度 | **常時** | 数十分〜数時間おき |
| パターン | **大量の小さいランダム読み** | **巨大な順次書き** |
| 同時実行 | 全ノードが常に読む | **全ノードが一斉に書く** |
| 求めるもの | **IOPS / メタデータ性能** | **瞬間的な帯域** |

## 学習データの読み出しがなぜ厳しいか

画像分類の学習を例にすると、性質がはっきりします。

```text
データセット: 1,000 万枚の画像、1 枚あたり平均 100KB（合計 1TB）

1 エポック = 全データを 1 回ずつ、ランダムな順序で読む
  → 1,000 万回の小さいランダム読み

GPU 8 枚 × バッチ 256 = 1 ステップで 2,048 枚
  → 毎秒 数千〜数万ファイルの読み出しが必要
```

**ここで効くのは帯域ではなく、IOPS とメタデータ操作の性能です。** ファイルを 1 つ開くたびに `open` / `stat` / `read` / `close` が走り、ネットワークファイルシステムではそれぞれが往復を伴います。

<Callout type="pitfall" title="NFS に小さいファイルを大量に置く構成">

**最もよくある失敗です。** 1TB のデータセットを NFS 上に 1,000 万ファイルとして置き、GPU ノードからマウントして読む構成。

帯域としては 10GbE で足りるように見えますが、**メタデータ操作のレイテンシがボトルネック**になります。1 ファイルあたり数ミリ秒かかると、毎秒数千ファイルという要求は満たせません。

症状は「GPU 利用率が周期的に落ちる」「データローダの待ち時間が長い」という形で現れます。

```bash
# データローダが待たされているかの簡易確認
# num_workers を増やして改善するなら CPU 前処理、変わらないならストレージ
```

</Callout>

### 対策 1: データ形式を変える

**小さいファイルをまとめて、大きな順次読み出しに変換します。**

---

<h2 className="slide-cont">学習データの読み出しがなぜ厳しいか（続き）</h2>

| 形式 | 内容 |
| --- | --- |
| **WebDataset** | 数百 MB〜数 GB の tar 形式のシャードにまとめる |
| TFRecord | TensorFlow 系の連結形式 |
| Parquet | 列指向。表形式データ向け |

```text
変更前: 1,000 万ファイル × 100KB → ランダム読み
変更後: 2,000 シャード × 500MB  → 順次読み

  シャード単位でシャッフルし、シャード内はバッファでシャッフルする
  → 学習上の要件（ランダム性）を保ちつつ、I/O は順次に近づく
```

**これだけで、ストレージ要件が一桁下がることがあります。** ストレージに投資する前に、まずデータ形式を検討してください。

### 対策 2: ローカル NVMe にキャッシュする

GPU ノードにローカル NVMe を積み、**初回だけ共有ストレージから読んでキャッシュする**構成です。

```text
1 エポック目 : 共有ストレージ → ローカル NVMe にコピーしながら学習
2 エポック目 : ローカル NVMe から読む（ハードウェアコース レッスン 4 の性能が出る）
```

データセットがローカル NVMe に収まるなら、最も費用対効果の高い解決策です。共有ストレージへの要求は「1 回読めればよい」まで下がります。

### 対策 3: 並列ファイルシステム

データセットがローカルに収まらない規模では、**並列ファイルシステム**を使います。

---

<h2 className="slide-cont">学習データの読み出しがなぜ厳しいか（続き）</h2>

| 製品 | 特徴 |
| --- | --- |
| **Lustre** | HPC で実績。メタデータサーバー（MDS）とデータサーバー（OSS）を分離 |
| **IBM Storage Scale (GPFS)** | 商用。運用ツールが充実 |
| **WEKA** | NVMe 前提。小さいファイルとメタデータに強い |
| BeeGFS / DAOS | — |

共通する考え方は、**データを多数のサーバーに分散し、クライアントが並列に読む**ことです。1 台のファイルサーバーの限界を超えられます。NFS との経路の違いやストライピング、ストレージ用のネットワークの分け方はレッスン 7 で扱います。

<Callout type="note">

並列ファイルシステムは強力ですが、**運用の専門性が必要**です。メタデータサーバーの負荷設計、ストライプ設定、障害時の復旧手順など、NFS とは別の知識が要ります。

規模が中程度なら、**「データ形式の最適化 + ローカル NVMe キャッシュ」で十分なことが多い**です。並列 FS の導入は、それでも足りないと実測で確認してからにしてください。

</Callout>

## オブジェクトストレージ

S3 互換のオブジェクトストレージは、**容量単価が安く、実質無制限に拡張できる**のが利点です。一方、レイテンシは高く、POSIX のファイルシステムとしては振る舞いません。

```text
典型的な構成:
  オブジェクトストレージ（原本・大容量・安価）
        │
        ▼ 学習開始時にプリフェッチ
  ローカル NVMe / 並列FS（キャッシュ層・高速）
        │
        ▼
  GPU ノード
```

**原本の置き場としてオブジェクトストレージ、実際に読む先はキャッシュ層**という二段構成が現実的です。学習ジョブから直接 S3 を読むと、レイテンシで GPU が待ちます。

## チェックポイント: 瞬間的な巨大書き込み

レッスン 1 で触れたとおり、チェックポイントは**サイズが VRAM 上の状態とほぼ同じ**になります。

```text
70B パラメータ、Adam、混合精度
  → 約 1.1TB のチェックポイント

これを 128 ノードが一斉に書き出す
  → 瞬間的に数百 GB/s の書き込み要求
```

### 保存中は GPU が止まる

```text
[ 学習 30分 ][ 保存 5分 ][ 学習 30分 ][ 保存 5分 ] ...
              ↑ GPU 全台が待機
  → 全体の約 14% を保存に費やしている
```

<Callout type="field">

**チェックポイント間隔は、次の 2 つのバランスで決めます。**

```text
保存のコスト   = 保存時間 ÷ 間隔        （常に払うコスト）
障害時の損失   = 平均で 間隔 ÷ 2        （障害が起きたときだけ）
```

ノード数が多いほど障害確率が上がるので、**大規模クラスタほど間隔を短く**すべきです。ただし保存が遅いと短くできないため、結局は保存の高速化が必要になります。

</Callout>

### 対策

---

<h2 className="slide-cont">チェックポイント: 瞬間的な巨大書き込み（続き）</h2>

| 手法 | 内容 |
| --- | --- |
| **非同期チェックポイント** | GPU → ホストメモリに退避したら学習を再開し、ディスクへの書き出しは裏で行う |
| **分散チェックポイント** | 各ランクが自分の担当部分だけを書く（全部を 1 ランクに集めない） |
| **階層化** | まずローカル NVMe に書き、裏で共有ストレージへ転送する |

PyTorch では `torch.distributed.checkpoint` が分散保存を、フレームワークによっては非同期保存を提供しています。**「保存中に GPU が止まる時間」を計測して、対策の要否を判断してください。**

## GPUDirect Storage

レッスン 2 で扱った GPUDirect RDMA（NIC ↔ VRAM）の、ストレージ版です。

```text
通常:
  NVMe → CPU のバウンスバッファ（ホストメモリ）→ GPU VRAM

GPUDirect Storage (GDS):
  NVMe → GPU VRAM （DMA で直接）
```

ホストメモリを経由しないため、**CPU 負荷が下がり、帯域とレイテンシが改善**します。データが大きく、前処理が不要（あるいは GPU 上で行う）ワークロードで効果があります。

```bash
# GDS が使える状態か確認
/usr/local/cuda/gds/tools/gdscheck -p
```

```text
 NVMe               : Supported
 NVMeOF             : Unsupported
 LUSTRE             : Supported
 WEKAFS             : Supported
 NFS                : Unsupported
```

<Callout type="warning">

**GDS は対応するファイルシステムでしか使えません。** 上の出力のとおり、通常の NFS では使えません。

また、**アプリケーション側が cuFile API に対応している必要があります**。単に GDS を有効化しただけでは効きません。NVIDIA DALI や一部のフレームワークが対応しています。

「GDS を入れれば速くなる」ものではなく、**ファイルシステム・アプリ・ドライバの 3 つが揃って初めて機能します。** 導入前に `gdscheck` で前提を確認してください。

</Callout>

## データローダ側の設定

ストレージを速くする前に、**アプリケーション側で取りこぼしていないか**を確認します。

```python
DataLoader(
    dataset,
    batch_size=256,
    num_workers=8,          # CPU コア数に応じて。前処理の並列度
    pin_memory=True,        # ホスト→GPU 転送が速くなる（ページロックメモリ）
    prefetch_factor=4,      # 各ワーカーが先読みするバッチ数
    persistent_workers=True # エポックごとのワーカー再生成を避ける
)
```

<Callout type="tip">

**切り分けの簡単な方法** です。

```text
num_workers を増やす
  → 速くなる      → CPU 前処理がボトルネック（CPU コアを増やす / 前処理を軽くする）
  → 変わらない    → ストレージがボトルネック
```

運用コース レッスン 1 と同じ考え方で、**変数を 1 つずつ動かして反応を見る**のが確実です。

また、GPU ノードの CPU コア数は軽視されがちですが、**GPU 1 枚あたり 8〜16 コア程度**は前処理のために必要とされます。GPU だけ豪華で CPU が貧弱な構成は、データ供給で詰まります。

</Callout>


ベンチマークでストレージではなくページキャッシュを測ってしまう罠や、fio・IOR・mdtest の使い分けは、ファイルストレージコース レッスン 4 で扱います（[ストレージの性能を測る](/courses/storage/measuring-performance/)）。

## まとめ

- AI 基盤のストレージには**読み（小さいランダム）と書き（巨大な順次）の2つの負荷**がかかる
- 学習データの読み出しで効くのは帯域ではなく **IOPS とメタデータ性能**
- **NFS に小さいファイルを大量に置く構成は詰まる**
- 最初に検討すべきは**データ形式**（WebDataset 等でシャードにまとめる）
- 次が**ローカル NVMe キャッシュ**。収まるなら最も費用対効果が高い
- 並列 FS は強力だが運用の専門性が要る。実測で必要性を確認してから
- オブジェクトストレージは原本置き場。**直接読まずキャッシュ層を挟む**
- チェックポイントは **VRAM とほぼ同サイズ**が一斉に書かれ、その間 GPU が止まる
- GDS は**ファイルシステム・アプリ・ドライバの 3 つが揃って**初めて効く
- **GPU 1 枚あたり CPU 8〜16 コア**を見込む。前処理で詰まる構成は多い
