## 帯域はチャネル数で決まる

メモリの性能には**レイテンシ**（1 回のアクセスにかかる時間、レッスン 1 の約 80ns）と**帯域**（単位時間あたりに運べる量）の 2 つがあります。このうち帯域は、構成から計算できます。

> 1 チャネルあたりの帯域 = 転送レート (MT/s) × 8 バイト

DDR のデータ幅は 64 ビット = 8 バイトです。

| メモリ | 1チャネル | 8チャネル構成 |
| --- | --- | --- |
| DDR4-2666 | 21.3 GB/s | 170 GB/s |
| DDR4-3200 | 25.6 GB/s | 205 GB/s |
| DDR5-4800 | 38.4 GB/s | 307 GB/s |
| DDR5-5600 | 44.8 GB/s | 358 GB/s |

現代のサーバー CPU は 1 ソケットあたり 8〜12 チャネルを持ちます。**このチャネルをすべて埋めないと、帯域はその分だけ失われます。**

<Callout type="pitfall" title="容量だけ合わせた構成は遅い">

「256GB 欲しい」という要件に対して、次の 2 通りの構成があったとします。

| 構成 | 容量 | 使用チャネル | 実効帯域 |
| --- | --- | --- | --- |
| 64GB × 4 枚 | 256GB | **4 / 8** | 約 102 GB/s |
| 32GB × 8 枚 | 256GB | **8 / 8** | 約 205 GB/s |

**容量は同じでも帯域は 2 倍違います。** 見積もりで枚数を減らすと、そのまま性能が落ちます。サーバーのメモリ構成は「容量」ではなく「チャネルを埋める枚数」から決めてください。

</Callout>

```bash
# 実装されている DIMM を、スロット・容量・速度つきで確認する
sudo dmidecode -t memory | grep -E 'Locator|Size|Speed|Configured|Rank|Manufacturer'
```

<h2 className="slide-cont">帯域はチャネル数で決まる（続き）</h2>

```text
Locator: DIMM_A1
Size: 32 GB
Speed: 3200 MT/s               ← DIMM の定格
Configured Memory Speed: 2933 MT/s   ← 実際の動作速度（ここが重要）
Rank: 2
```

`Configured Memory Speed` が定格より低いことがあります。CPU 側の上限、1 チャネルあたりの実装枚数、混在した DIMM の中で最も遅いものに引きずられる、といった理由です。

<Callout type="field">

**同じ型番の DIMM で揃えるのが原則です。** 容量・速度・ランク数が混在すると、全体が最も遅い条件に合わせられます。増設時に手元にあった別の DIMM を足した結果、既存分まで遅くなる、というのは実際によくある話です。

`Configured Memory Speed` を増設前後で比較する習慣をつけてください。

</Callout>

## ランクと DIMM の種類

同じ容量でも、内部構造の違いが性能と実装可能枚数に影響します。

**ランク**は、DIMM 内でデータ幅 64 ビットを構成するチップのまとまりです。`1Rx8`（シングルランク）、`2Rx4`（デュアルランク）のように表記されます。

- ランクが多いほど**バンクの並列度**が上がり、同じ速度でもわずかに性能が良い
- 一方でメモリコントローラの負荷が上がり、**1 チャネルに挿せる枚数が減る**、または速度が落ちる

サーバー向けの DIMM には種類があります。

| 種類 | 構造 | 用途 |
| --- | --- | --- |
| **UDIMM** | バッファなし | デスクトップ、小規模サーバー。容量に限界がある |
| **RDIMM** | アドレス/コマンド信号をレジスタでバッファ | サーバーの標準 |
| **LRDIMM** | データ線もバッファ | 大容量構成（1 ソケット 1TB 超など） |

**これらは混在できません。** マザーボードがどれに対応しているかは必ず仕様書で確認します。

## ECC: 訂正できるエラーと、できないエラー

サーバー用メモリは 64 ビットのデータに 8 ビットの冗長ビットを加えた 72 ビット幅で動作します。この冗長性により **SECDED**（Single Error Correct, Double Error Detect）が実現されます。

| エラー | 呼び名 | 挙動 |
| --- | --- | --- |
| 1 ビット誤り | **CE** (Correctable Error) | **自動訂正され、処理は継続する**。ログにだけ残る |
| 2 ビット誤り | **UE** (Uncorrectable Error) | 訂正不能。多くの場合システムが停止する |

重要なのは、**CE は「正常に動いている」のではなく「壊れかけている」サインだ**という点です。訂正されているため業務は止まりませんが、放置すると UE に進行します。

```bash
# EDAC 経由でのエラーカウント（メモリコントローラ・DIMM 単位）
grep . /sys/devices/system/edac/mc/mc*/csrow*/ch*_ce_count
edac-util -v

# rasdaemon を使っている場合（推奨。どの DIMM かまで記録される）
ras-mc-ctl --error-count
ras-mc-ctl --summary

# カーネルログ側
journalctl -k --grep="EDAC|Corrected|Machine Check"
```

<h2 className="slide-cont">ECC: 訂正できるエラーと、できないエラー（続き）</h2>

<Callout type="warning" title="CE の増加は交換の判断材料">

CE のカウントは**増加率**で見ます。

- 月に数件 → 宇宙線などによるソフトエラーの範囲。経過観察
- 日に何十件、特定の DIMM に集中 → **ハードエラー。交換を検討**
- 短時間に急増 → UE に至る前に予防交換

`ras-mc-ctl --error-count` は DIMM のラベル（`DIMM_A1` など）まで出せるので、`dmidecode` の `Locator` と突き合わせれば物理スロットを特定できます。交換作業の前にこの対応を取っておくと、現地作業が一度で済みます。

</Callout>

### メモリスクラビング

エラーは「読んだとき」に初めて見つかります。長期間読まれないページにビット誤りが蓄積すると、1 ビット誤りが 2 ビットに進行してから発見される、という事態が起こります。

これを防ぐため、多くのサーバーは **パトロールスクラブ**（バックグラウンドで全メモリを定期的に読み直し、CE を訂正して書き戻す）を備えています。BIOS/UEFI の設定項目にあるので、有効になっているか確認してください。

## メモリ RAS 機能

大規模サーバーには、ECC の先の可用性機能があります。

| 機能 | 内容 | 代償 |
| --- | --- | --- |
| **Rank Sparing** | 予備ランクを確保し、CE が閾値を超えたランクを置き換える | 予備分の容量が使えない |
| **Mirroring** | メモリを二重化する | **容量が半分、帯域も低下** |
| **ADDDC / SDDC** | チップ単位の故障を訂正する（Chipkill 相当） | ほぼなし。既定で有効なことが多い |

<Callout type="note">

Mirroring は容量を半分にする強い機能で、無停止が絶対要件のシステム以外では過剰です。通常は **ECC + パトロールスクラブ + CE 監視**の組み合わせで十分な水準になります。

まず CE を監視できる状態にすること。予兆を掴めていないのに RAS 機能だけ盛っても、運用としては機能しません。

</Callout>

## Linux 側から見たメモリ構成

ハードウェアの構成が OS からどう見えているかを確認します。

```bash
# NUMA ノードごとの容量と空き
numactl --hardware

# ノード別の詳細
cat /sys/devices/system/node/node0/meminfo | head -5

# ページサイズと HugePage の設定状況
getconf PAGESIZE
grep -i huge /proc/meminfo
```

Linux コースのレッスン 3 で扱った THP（Transparent Huge Pages）に加えて、**明示的な HugePages** を予約する方法もあります。DB が自分で管理する大きな共有メモリ領域には、起動時に予約した HugePages を割り当てるのが定石です。

```bash
# 2MiB ページを 4096 枚（= 8GiB）予約する
sudo sysctl -w vm.nr_hugepages=4096
grep HugePages /proc/meminfo
```

THP と違って断片化による割り当て遅延が起きないため、レイテンシが安定します。代わりに、予約した分は他の用途に使えなくなります。

## まとめ

- 帯域 = **チャネル数 × 転送レート × 8 バイト**。容量ではなくチャネルを埋める枚数で構成を決める
- `dmidecode` の `Configured Memory Speed` を見る。定格どおり動いているとは限らない
- DIMM は同一型番で揃える。混在すると最も遅い条件に揃えられる
- **CE は正常ではなく予兆**。増加率と DIMM への集中を監視する
- パトロールスクラブがないと、誤りが蓄積してから UE として発見される
- 大きな共有メモリを持つ DB には、THP より明示的な HugePages が適することが多い
