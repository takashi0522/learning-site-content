## 桁を覚える

性能問題の切り分けで最も役に立つのは、細かい数値ではなく**桁の感覚**です。1 回のアクセスにどれくらいかかるかを階層ごとに把握しておくと、「この処理がこの時間で終わるはずがない」という判断が即座にできます。

| 階層 | レイテンシ | 人間のスケールに直すと（1ns = 1秒として） |
| --- | --- | --- |
| L1 キャッシュ | 約 1 ns | 1 秒 |
| L2 キャッシュ | 約 4 ns | 4 秒 |
| L3 キャッシュ | 約 20–40 ns | 30 秒 |
| メインメモリ (DRAM) | 約 80–100 ns | 1 分 40 秒 |
| NVMe SSD | 約 20–100 μs | 6 時間 – 1 日 |
| SATA SSD | 約 100–500 μs | 1 – 6 日 |
| HDD（シーク込み） | 約 5–10 ms | **2 – 4 か月** |
| 同一データセンター内 RTT | 約 0.5 ms | 6 日 |
| 東京 – 大阪 RTT | 約 10 ms | 4 か月 |

右列が重要です。**DRAM とディスクの間には 3 桁以上の壁があります。** 「メモリに乗り切るかどうか」が性能を決定的に分けるのは、この断崖があるからです。

<Callout type="field">

この表を頭に入れておくと、見積もりが即座にできます。1 リクエストで 100 回のランダムディスク読み込み（HDD）が必要な処理は、それだけで 0.5〜1 秒かかります。ここにアプリケーションの改善余地はほとんどありません。キャッシュを挟むかストレージを替えるかの、どちらかしかありません。

</Callout>

## キャッシュラインという単位

CPU はメモリを 1 バイト単位では読みません。**キャッシュライン**という固定サイズの塊で読み込みます。x86-64 では **64 バイト**です。

つまり `int`（4 バイト）を 1 つ読むだけでも、その周辺 64 バイトがまとめてキャッシュに載ります。この性質から 2 つの重要な帰結が生まれます。

### 1. 連続アクセスは桁違いに速い

配列を順番に舐める処理は、1 回のメモリアクセスで 16 個分（64 ÷ 4）のデータが手に入ります。さらに CPU のプリフェッチャがアクセスパターンを検出し、先回りして読み込みます。

一方、ポインタを辿るリスト構造のランダムアクセスは、毎回キャッシュミスを起こします。**同じ要素数でも、10 倍以上の差がつくことがあります。**

### 2. False Sharing

別々のスレッドが「別々の変数」を更新していても、それらが**同じキャッシュライン上にある**と、キャッシュの一貫性を保つためにコア間で無効化が往復します。論理的には競合していないのに、物理的には競合している状態です。

```text
コア0 が変数A を更新 ──► ライン全体が無効化される
                          ↓
コア1 は変数B を読むだけなのに、ラインを取り直す（≒ DRAM アクセス）
```

これがマルチスレッド化しても速くならない、場合によっては**遅くなる**原因の一つです。

## NUMA: メモリに「遠い」「近い」がある

2 ソケット以上のサーバーでは、各 CPU が自分専用のメモリコントローラを持ちます。この構成を **NUMA**（Non-Uniform Memory Access）と呼びます。

<Figure name="numa-topology" caption="2 ソケットサーバーの NUMA 構成。リモートアクセスはソケット間接続を 1 本余計に通る" />

```bash
# NUMA 構成の確認
numactl --hardware
lscpu | grep -i numa

# ノードをまたぐアクセスが起きているか（numa_miss / numa_foreign が増えていないか）
numastat
```

---

<h2 className="slide-cont">NUMA: メモリに「遠い」「近い」がある（続き）</h2>

<Callout type="warning" title="大きなメモリを使うミドルウェア">

データベースやインメモリキャッシュのように数十 GiB を確保するプロセスが、ノードをまたいでメモリを使うと、アクセスの半分がリモートになり性能が安定しません。

対策としてプロセスを特定ノードに固定する方法があります。

```bash
# CPU もメモリも Node 0 に固定して起動
numactl --cpunodebind=0 --membind=0 /usr/local/bin/myapp
```

systemd なら `NUMAPolicy=` と `NUMAMask=` でも指定できます。ただし片方のノードのメモリしか使えなくなるため、**プロセスのメモリ使用量が 1 ノード分に収まる場合に限ります。**

</Callout>

## ストレージを構造から見る

HDD と SSD の差は「速い / 遅い」だけではなく、**得意なアクセスパターンが違う**という点が本質です。

| | HDD | SATA SSD | NVMe SSD |
| --- | --- | --- | --- |
| シーケンシャル読み込み | 150–250 MB/s | 500 MB/s | 3–7 GB/s |
| ランダム読み込み (4K) | **0.5–1 MB/s** | 50–100 MB/s | 200–600 MB/s |
| IOPS (4K ランダム) | 75–200 | 50,000–100,000 | 500,000–1,000,000 |
| キュー深度の効果 | ほぼなし | 中程度 | **非常に大きい** |

HDD のランダム性能が壊滅的なのは、物理的にヘッドを動かす必要があるからです。SSD には可動部がなく、この制約から解放されています。

NVMe が SATA より速い理由は、素子の性能だけではありません。**プロトコル構造が違います。**

- SATA (AHCI) … コマンドキューは **1 本、深さ 32**
- NVMe … キューは **最大 64K 本、各深さ 64K**

NVMe は CPU コアごとに独立したキューを持てるため、ロック競合がなく、並列度を上げるほど性能が伸びます。**シングルスレッドのベンチマークでは NVMe の真価は出ません。**

```bash
# デバイスの実効性能とキュー深度を観察する
iostat -xz 1
# aqu-sz（平均キュー長）が常時小さいなら、並列度が足りず性能を引き出せていない

# NVMe デバイスの情報
nvme list
nvme smart-log /dev/nvme0n1
```

## まとめ

- **DRAM とディスクの間には 3 桁の壁がある**。メモリに載るかどうかが性能を分ける
- CPU は 64 バイトのキャッシュライン単位で読む。連続アクセスが速いのはこのため
- False Sharing は論理的に競合していなくても性能を落とす
- マルチソケットでは NUMA のリモートアクセスが 1.5–2 倍のコストになる
- NVMe の速さはキュー構造に由来する。並列度を上げないと活きない
