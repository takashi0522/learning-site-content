## HDD: 物理法則による上限

HDD の性能は、機械的な動作時間で決まります。

```text
1回のランダム読み込みにかかる時間
  = シーク時間（ヘッドの移動）  約 4〜9 ms
  + 回転待ち（セクタが来るまで） 平均 = 1回転の半分
  + 転送時間                     ほぼ無視できる
```

回転待ちは回転数から計算できます。

| 回転数 | 1 回転 | 平均回転待ち | 実効 IOPS の目安 |
| --- | --- | --- | --- |
| 7,200 rpm | 8.33 ms | **4.17 ms** | 約 75–100 |
| 10,000 rpm | 6.00 ms | 3.00 ms | 約 125–150 |
| 15,000 rpm | 4.00 ms | 2.00 ms | 約 175–200 |

**1 本あたり 100 IOPS 程度** — これが HDD の物理的な上限です。何本束ねるか、キャッシュをどれだけ積むかでしか増やせません。

## SSD: 書けば書くほど事情が複雑になる

SSD には可動部がありませんが、NAND フラッシュ特有の制約があります。

### 読み書きの単位が非対称

```text
読み込み  : ページ単位（4〜16 KB）で可能
書き込み  : ページ単位で可能。ただし「消去済み」のページにしか書けない
消去      : ブロック単位（数百ページ = 数 MB）でしかできない
```

**上書きができません。** 既に書かれた場所を更新するには、ブロック全体を消して書き直す必要があります。

この非対称性から、次の動作が生まれます。

1. 更新は「別の空きページに書いて、元のページを無効としてマークする」方式で行う
2. 無効ページが増えると空きが減るので、**ガベージコレクション（GC）** が有効ページを別ブロックにまとめ、ブロックごと消去する
3. GC は内部的に読み書きを発生させる。これが **ライトアンプリフィケーション**

<Callout type="pitfall" title="新品では速く、使い込むと遅くなる">

出荷直後の SSD は全ブロックが消去済みで、GC が不要です。ベンチマークでカタログ値が出ます。

容量が埋まってくると、書き込みのたびに GC が動くようになり、**定常状態（steady state）の性能はカタログ値の数分の1になります**。

評価時は、容量の 8 割程度まで埋めて数時間書き込み続けた後の数値を見てください。空のドライブでの短時間計測は、本番の性能を表しません。

</Callout>

### セルの種類と寿命

1 つのセルに何ビット詰め込むかで、容量単価と寿命が変わります。

---

<h2 className="slide-cont">SSD: 書けば書くほど事情が複雑になる（続き）</h2>

| 種類 | ビット/セル | 書き換え耐性 (P/E) | 用途 |
| --- | --- | --- | --- |
| SLC | 1 | 約 100,000 回 | キャッシュ層 |
| MLC | 2 | 約 3,000–10,000 回 | 旧世代の高耐久品 |
| **TLC** | 3 | 約 1,000–3,000 回 | サーバーの主流 |
| QLC | 4 | 約 100–1,000 回 | 読み出し中心の大容量用途 |

多くの TLC/QLC ドライブは、一部の領域を **SLC モードで動かすキャッシュ**として使い、書き込みを一旦そこで受けます。短時間のバーストは速いのに、**大量に書き続けると突然遅くなる**のは、この SLC キャッシュを使い切ったためです。

### 寿命の指標: DWPD と TBW

```text
DWPD (Drive Writes Per Day) : 保証期間中、1日あたりドライブ容量の何倍書けるか
TBW  (Terabytes Written)    : 総書き込み可能量

例: 1.92TB, 1 DWPD, 5年保証
    → 1日あたり 1.92TB × 5年 × 365日 ≒ 3,500 TBW
```

ログ収集やデータベースの WAL のように書き込みが多い用途では、DWPD 3 以上の「書き込み重視モデル」を選びます。**容量単価だけで選ぶと、保証期間内に寿命が尽きます。**

```bash
# NVMe の寿命・書き込み量・温度
sudo nvme smart-log /dev/nvme0n1
```

<h2 className="slide-cont">SSD: 書けば書くほど事情が複雑になる（続き）</h2>

```text
percentage_used         : 42%          ← 想定寿命の消費率（100% で保証終了）
data_units_written      : 1,204,558,392 ← ×512KB が総書き込み量
media_errors            : 0
critical_warning        : 0
```

```bash
# SATA/SAS を含む汎用の確認
sudo smartctl -a /dev/sda
sudo smartctl -H /dev/sda      # 総合判定だけ
```

<Callout type="field">

`percentage_used` は単調増加します。稼働日数と突き合わせて、**保証期間より先に 100% に達しないか**を計算してください。

```text
例: 稼働 400日で percentage_used 42%
    → 100% まで約 950日 ≒ 2.6年
    → 5年保証だが、この使い方では2.6年で寿命
```

この計算をしておくと、計画的な交換ができます。壊れてから気づくのとはコストが違います。

</Callout>

## RAID: 冗長性の代償は書き込み回数

RAID は可用性のための仕組みですが、**書き込み性能に構造的なペナルティ**があります。

| レベル | 構成 | 1回の書き込みに必要な I/O | 容量効率 | 耐障害 |
| --- | --- | --- | --- | --- |
| RAID 0 | ストライプ | 1 | 100% | **なし** |
| RAID 1 | ミラー | 2 | 50% | 1本 |
| RAID 5 | パリティ 1 | **4** | (n-1)/n | 1本 |
| RAID 6 | パリティ 2 | **6** | (n-2)/n | 2本 |
| RAID 10 | ミラー+ストライプ | 2 | 50% | 各ミラー1本 |

RAID 5 が 4 回になる理由です。

```text
1ブロックを更新するには
  ① 古いデータを読む
  ② 古いパリティを読む
  ③ 新しいデータを書く
  ④ 新しいパリティを書く
= 読み2回 + 書き2回 = 4 I/O
```

### 必要なドライブ本数の見積もり

```text
要件: 10,000 書き込み IOPS を RAID 6 で実現したい
必要な物理 IOPS = 10,000 × 6 = 60,000 IOPS

HDD (100 IOPS/本)  → 600 本   ← 非現実的
SSD (50,000 IOPS/本) → 2 本 + 冗長分
```

**書き込みが多いワークロードで RAID 5/6 を HDD で組む構成は、この計算により成立しません。**

---

<h2 className="slide-cont">RAID: 冗長性の代償は書き込み回数（続き）</h2>

<Callout type="warning" title="RAID 5 と再構築中のリスク">

大容量ドライブで RAID 5 を組むと、1 本故障後の再構築中に問題が起きます。

- 再構築には**残り全ドライブの全面読み出し**が必要
- 18TB のドライブでは再構築に丸一日以上かかることがある
- その間に 2 本目が故障、あるいは読み取り不能セクタ（URE）に当たると**全データを失う**

大容量 HDD では RAID 6（2 本まで耐える）か RAID 10 を選ぶのが定石です。RAID 10 は再構築が対になるドライブのコピーだけで済むため、再構築時間もリスクも小さくなります。

</Callout>

<h2 className="slide-cont">電源断でデータを守っているもの（続き）</h2>

各層に「守る仕組み」があります。

| 層 | 保護機構 | 確認方法 |
| --- | --- | --- |
| RAID コントローラ | **BBU / スーパーキャパシタ** | `storcli` / `perccli` などのベンダーツール |
| SSD | **PLP (Power Loss Protection)** | データシート。エンタープライズ向けのみ搭載 |

<Callout type="pitfall">

**コンシューマ向け SSD には PLP がありません。** 電源断時、内部バッファ上のデータは失われ、`fsync()` が成功を返していても書かれていない場合があります。

データベースを載せるなら、PLP 搭載のエンタープライズ SSD を選んでください。ベンチマークでコンシューマ SSD が速く見えるのは、この保証を省いている分でもあります。

同様に、RAID コントローラの BBU が劣化すると、コントローラは自動的に write-back から write-through にモードを落とします。**「ある日を境にディスク性能が数分の一になった」場合、まず BBU の状態を確認してください。**

</Callout>

## Linux 側の I/O スケジューラ

```bash
# 現在のスケジューラ（[] で囲まれているものが有効）
cat /sys/block/nvme0n1/queue/scheduler
# [none] mq-deadline kyber bfq

# 変更
echo mq-deadline | sudo tee /sys/block/sda/queue/scheduler
```

| スケジューラ | 向き |
| --- | --- |
| `none` | **NVMe SSD**。並べ替えの必要がなく、オーバーヘッドがないのが最善 |
| `mq-deadline` | SATA SSD、HDD。レイテンシの上限を保証する |
| `bfq` | デスクトップ用途。対話性を優先する |

SSD に対して HDD 向けの並べ替えを行うスケジューラを使うと、CPU を消費するだけで効果がありません。**NVMe は `none` が原則です。**

```bash
# 実際の I/O の並列度とレイテンシ
iostat -xz 1
# r_await / w_await : 待ち時間（ms）
# aqu-sz            : 平均キュー長。小さすぎると並列度不足
# %util             : SSD では飽和の指標にならない（並列処理されるため）
```

<Callout type="note">

`%util` は「デバイスが何らかの I/O を処理していた時間の割合」です。1 度に 1 つしか処理できない HDD では飽和の指標になりますが、**数十の I/O を並列処理する NVMe では 100% でも余裕があります**。SSD の飽和を見るなら `await` の増加を見てください。

</Callout>

## まとめ

- HDD は **1 本 100 IOPS 前後**が物理的な上限。回転数から計算できる
- SSD は上書きできず GC が必要。**空のドライブのベンチマークは本番の性能を表さない**
- `percentage_used` と稼働日数から、保証期間内に寿命が尽きないか計算する
- RAID 5 は書き込み 1 回につき **4 I/O**、RAID 6 は 6 I/O。必要本数の見積もりに直結する
- 大容量ドライブの RAID 5 は再構築中のリスクが高い。RAID 6 か RAID 10 を選ぶ
- `fsync()` の保証は **BBU と PLP** が担保している。コンシューマ SSD にはない
- NVMe の I/O スケジューラは `none`。`%util` は飽和の指標にならない
