## なぜ境界があるのか

サーバーの上では、Web サーバーも監視エージェントも自分の書いたスクリプトも、すべて「ユーザープロセス」として動いています。これらはディスクに書き込み、ネットワークにパケットを出し、メモリを確保します。

しかし、**どのプロセスもハードウェアに直接触れていません**。触れているのはカーネルだけです。

この分離がなければ、1つのアプリケーションのバグが他のアプリケーションのメモリを壊し、ディスク全体を破壊できてしまいます。逆に言えば、私たちが「プロセスを再起動すれば直る」と期待できるのは、この境界が保たれているからです。

<Callout type="field">

障害対応で「OS ごと再起動するか、プロセスだけ再起動するか」を判断する場面があります。この判断は結局「壊れているのは境界のどちら側か」を見極める作業です。本コースはその判断材料を揃えることを目標にしています。

</Callout>

## 分離その1: 特権レベル

x86-64 の CPU には**特権リング**という実行モードがあります。Linux が使うのは 2 つだけです。

| リング | 呼び名 | 実行されるもの | できること |
| --- | --- | --- | --- |
| Ring 0 | カーネルモード | カーネル、デバイスドライバ | すべての命令、全物理メモリへのアクセス |
| Ring 3 | ユーザーモード | あらゆるプロセス | 制限された命令のみ |

Ring 3 で動いているコードが特権命令を実行しようとすると、CPU が**例外**を発生させ、制御が強制的にカーネルへ移ります。ソフトウェアの約束事ではなく、CPU の回路が保証する制約です。

たとえばページテーブルの基底アドレスを保持する `CR3` レジスタへの書き込みは特権命令です。もしユーザープロセスがこれを書き換えられたら、自分専用のメモリ空間という前提そのものが崩れます。

## 分離その2: アドレス空間

もう1つの分離は、仮想アドレス空間の分割です。x86-64 の 4 レベルページングでは、48 ビットのアドレス空間が上下に分かれています。

```text
0xFFFF_FFFF_FFFF_FFFF  ┐
                       │  カーネル空間 (128 TiB)
0xFFFF_8000_0000_0000  ┘  Ring 0 でのみアクセス可能

        （未使用の巨大な穴）

0x0000_7FFF_FFFF_FFFF  ┐
                       │  ユーザー空間 (128 TiB)
0x0000_0000_0000_0000  ┘  プロセスごとに中身が違う
```

各ページテーブルのエントリには **U/S ビット**（User/Supervisor）があり、これが 0 のページは Ring 3 から触れません。カーネル空間のアドレスをユーザープロセスが参照しようとすると、ページフォルトになります。

ここで重要なのは、**ユーザー空間の中身はプロセスごとに違う**のに、**カーネル空間の中身は全プロセスで共通**という点です。だからシステムコールでカーネルに入るとき、ページテーブルを丸ごと切り替える必要がありません。

<Callout type="note" title="Meltdown 以降の例外">

2018 年の Meltdown 脆弱性への対策として、KPTI（Kernel Page Table Isolation）が導入されました。これは上記の「共通マッピング」をやめ、ユーザーモード時にはカーネル領域をほぼマップしない方式です。安全になった代わりに、システムコールのたびにページテーブル切り替えと TLB フラッシュが発生し、システムコールの多いワークロードでは目に見える性能低下が起きました。

</Callout>

## 唯一の出入口: システムコール

境界を越える方法は 1 つだけ、**システムコール**です。x86-64 では `syscall` 命令を使います。

<Figure name="syscall-boundary" caption="境界を越える道はこれ 1 本だけ。だから strace で全部見える" />

`syscall` 命令は「カーネルの任意の場所へジャンプする」のではありません。飛び先は `MSR_LSTAR` というレジスタにカーネル起動時に設定されたエントリポイント 1 箇所に固定されています。ユーザー側が選べるのは `rax` に入れる**システムコール番号**だけです。

---

### ライブラリ関数とシステムコールは別物

ここは混同しやすいところです。

- `write()` … glibc が提供する**ラッパー関数**。中で `syscall` 命令を実行する
- `printf()` … glibc の**ライブラリ関数**。内部でバッファリングし、必要になったときだけ `write()` を呼ぶ
- `malloc()` … 同じくライブラリ関数。空きがあれば**システムコールを呼ばずに**返す。足りないときだけ `brk` や `mmap` を発行する

<Callout type="pitfall">

「`malloc()` はシステムコール」と覚えていると、メモリ使用量の調査で行き詰まります。プロセスが 1 MiB を malloc しても、カーネルから見た割り当ては発生しないことがあります。逆に `free()` してもメモリが OS に返らないのも同じ理由です。

</Callout>

## 実際に観察する

`strace` はプロセスが発行したシステムコールを記録します。理屈より、まず 1 度自分の目で見るのが早いです。

```bash
# コマンドが発行するシステムコールをすべて表示
strace -f ls /tmp

# システムコールごとの回数と所要時間を集計する（性能調査で最も使う形）
strace -c -f -p 1234

# ファイル関連だけに絞る。設定ファイルの探索順を調べるときに有効
strace -e trace=openat,stat -f nginx -t
```

`strace -c` の出力例です。

```text
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 58.21    0.004912          12       409        12 openat
 21.44    0.001809           4       402           read
 12.03    0.001015           2       406           close
```

`errors` 列に注目してください。`openat` が 12 回失敗しているなら、存在しないパスを繰り返し探しに行っています。設定ミスやライブラリ探索パスの問題がここに現れます。

<Callout type="warning" title="本番での strace">

`strace` は `ptrace` を使うため、対象プロセスはシステムコールのたびに停止・再開されます。システムコールの多いプロセスでは数倍の遅延が出ることがあります。本番環境では、オーバーヘッドの小さい `perf trace` や eBPF ベースのツール（`bpftrace` など）を検討してください。

</Callout>

## 境界を越えるコストと、それを避ける工夫

システムコールは関数呼び出しより明確に高価です。特権遷移、レジスタの退避、引数の検証が毎回入り、KPTI 環境ではページテーブル切り替えも加わります。

そのため Linux には「カーネルに入らずに済ませる」仕組みがあります。代表が **vDSO**（virtual Dynamic Shared Object）です。

```bash
# プロセスのメモリマップに vdso が現れる
grep vdso /proc/self/maps
```

`clock_gettime()` のような「カーネルが持つデータを読むだけで、書き込みも権限判定も不要」な処理は、カーネルが用意したコードとデータページをユーザー空間にマップしておき、Ring 3 のまま実行します。時刻取得を毎秒何万回も行うアプリケーションでは、この差が実測値に効いてきます。

同じ発想は他にもあります。

- **バッファリング**: `printf` が毎回 `write` を呼ばないのはこのため
- **`io_uring`**: システムコールを何度も呼ぶ代わりに、ユーザー空間とカーネルで共有したリングバッファに I/O 要求を積む
- **`sendfile` / `splice`**: ファイルからソケットへの転送を、ユーザー空間を経由せずカーネル内で完結させる

<Callout type="tip">

「システムコール回数を減らす」という視点を持つと、ミドルウェアのチューニング項目の意味が繋がって見えてきます。nginx の `sendfile on;` も、DB のコミット遅延書き込みも、根は同じ発想です。

</Callout>

## まとめ

- 分離は **特権レベル**（CPU が強制）と **アドレス空間**（ページテーブルが強制）の 2 層で成り立っている
- 境界を越える唯一の方法がシステムコールで、入口は 1 箇所に固定されている
- ライブラリ関数とシステムコールは別物。`malloc` や `printf` は必ずしもカーネルに入らない
- 境界越えにはコストがあり、vDSO・バッファリング・`io_uring` はそれを削るための仕組み
